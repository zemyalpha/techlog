# 컨텍스트 로트에서 서브에이전트까지: 긴 컨텍스트가 에이전트를 망가뜨리는 4가지 방식과 실전 처방

2026년의 프런티어 모델들은 수백만 토큰의 컨텍스트 윈도우를 갖췄다. 그런데 이상하다. 컨텍스트가 커질수록 에이전트는 오히려 이상해진다. 세션 초반에 지켰던 규칙을 무시하고, 같은 실수를 반복하고, 하지 말라한 도구를 호출한다. 모델이 멍청해진 게 아니다. 컨텍스트가 썩은 것이다.

Anthropic은 2025년 9월 엔지니어링 블로그 "Effective context engineering for AI agents"에서 이 문제를 정식으로 다뤘다. 핵심 주장은 단순하다. **컨텍스트는 무한한 자원이 아니라 한정된 자원이며, 토큰을 하나 추가할 때마다 회수해야 하는 비용이 발생한다**는 것. 이 글에서는 왜 긴 컨텍스트가 실패하는지, 실패의 유형은 무엇인지, 그리고 실전에서 어떻게 처방하는지 다룬다.

## 1. 컨텍스트 로트: 100만 토큰은 해결책이 아니라 위장된 문제다

"컨텍스트 로트(context rot)"라는 용어를 대중화한 것은 Chroma의 2025년 7월 기술 리포트다. 연구팀은 GPT-4.1, Claude 4, Gemini 2.5, Qwen3 등 **18개 프런티어 모델**을 대상으로, 태스크 난이도를 고정한 채 입력 길이만 늘리는 통제 실험을 진행했다. 결과는 모델을 가리지 않았다. 입력이 길어질수록 성능이 비일관적으로 저하됐다. 특히 주목할 점은, 널리 쓰이는 Needle in a Haystack(NIAH) 벤치마크가 어휘적 검색만 측정하기 때문에 이런 저하를 잡아내지 못한다는 것이다.

여기에 Databricks의 연구가 보탠다. Llama 3.1 405B급 모델에서도 **정확도는 약 32K 토큰 부근에서부터 떨어지기 시작**했다. 컨텍스트 윈도우가 1M이라고 선언된 모델조차 실제 추론 품질은 훨씬 이른 지점부터 무너진다. 윈도우가 크다는 것은 "들어갈 수 있다"는 뜻이지 "잘 처리한다"는 뜻이 아니다.

구조적 원인은 트랜스포머 그 자체에 있다. 어텐션은 모든 토큰 쌍이 서로를 참조하는 구조라 입력이 n개 토큰이면 n²개의 관계를 다뤄야 한다. Anthropic은 이를 "어텐션 예산(attention budget)"이라고 표현했다. 예산은 유한하므로, 저신호 토큰으로 창을 채우면 고신호 정보에 대한 처리 능력이 직접적으로 희석된다. 훈련 데이터에 긴 시퀀스가 짧은 시퀀스보다 드물다는 사실도 이 저하를 증폭시킨다.

실무적 결론은 명확하다. **"다 넣자"는 이제 스타일의 문제가 아니라 측정 가능한 안티패턴이다.** 긴 컨텍스트가 어울리는 용도는 요약과 팩트 검색뿐이며, 다단계 추론을 하는 에이전트라면 컨텍스트 길이를 늘리기 전에 무엇을 빼낼지부터 설계해야 한다.

## 2. 실패의 4가지 유형: Poisoning, Distraction, Confusion, Clash

Drew Breunig이 2025년 6월 에세이 "How Long Contexts Fail"에서 정리한 4가지 실패 모드는 이후 업계 표준 분류가 됐다. 하나씩 실전 증상과 함께 보자.

### 컨텍스트 포이즈닝 (Poisoning)

할루시네이션이나 잘못된 도구 출력이 컨텍스트에 들어간 뒤, 이후 모든 턴에서 그것이 사실처럼 재참조되는 현상이다. Google DeepMind가 Gemini 2.5 기술 리포트에서 직접 언급했는데, 포켓몬을 플레이하던 Gemini 에이전트가 게임 상태에 대한 오정보가 '목표' 섹션을 오염시키자 실현 불가능한 목표를 향해 같은 행동을 되풀이했다. 한 번 스캐치패드에 잘못된 고객 ID가 적히면 이후 모든 다운스트림 액션이 그 ID를 참조하는 것과 같은 구조다.

처방: 상태를 변경하는 사실은 읽는 시점이 아니라 **쓰는 시점에 검증**하고, 스캐치패드를 버전화해서 나쁜 턴 하나를 롤백할 수 있게 만든다.

### 컨텍스트 디스트랙션 (Distraction)

히스토리가 훈련된 지식을 압도하는 현상이다. Gemini 에이전트 사례에서 컨텍스트가 100K 토큰을 크게 넘기자, 모델은 새 전략을 합성하는 대신 방대한 과거 히스토리에 있는 행동을 반복하기 시작했다. "모델이 갑자기 게을러졌다"처럼 보이지만, 실제로는 컨텍스트가 모델을 압도한 것이다.

처방: 컴팩션(compaction, 이력 요약·치환)이 1차 레버다. 원시 툴 호출 로그는 요약으로 대체하라.

### 컨텍스트 컨퓨전 (Confusion)

불필요한 도구 정의나 문서가 컨텍스트에 있으면 모델은 그것을 쓴다. Berkeley Function-Calling Leaderboard의 결과는 충격적이다. **모든 모델이 도구가 하나일 때보다 여러 개일 때 성능이 낮아지고**, 심지어 관련 없는 함수만 주어진 시나리오에서도 불필요한 도구를 호출한다. 40개의 안 쓰는 툴 정의를 시스템 프롬프트에 넣는 것은 조용한 낭비가 아니라 매 턴 오답 확률을 올리는 행위다.

처방: 저스트인타임 도구 로딩. 현재 단계에 필요한 도구만 노출하고, 나머지는 탐색용 메타 도구 하나로 감춘다.

### 컨텍스트 클래시 (Clash)

새 컨텍스트가 오래된 컨텍스트와 모순될 때 발생한다. 사용자가 2턴째 한 말, 5턴째 검색된 문서, 스캐치패드의 이전 결정이 서로 충돌하면 에이전트는 멈추거나 코드 리뷰를 통과 못 할 이유로 한쪽을 고른다.

처방: 모순된 컨텍스트를 서로 다른 윈도우에 격리하는 **서브에이전트 구조**와, 시스템 프롬프트에 명시적인 충돌 해결 정책을 두는 것.

## 3. 처방의 프레임: Write, Select, Compress, Isolate

Anthropic, LangChain, Chroma가 각자 도달한 결론은 놀랍게도 같은 4전략 프레임워크로 수렴했다.

**Write (쓰기)** — 상태를 컨텍스트 밖 파일시스템에 외부화한다. 에이전트의 작업 메모리는 휘발성이므로, 결정된 사실은 마크다운 파일로 즉시 내려쓰게 한다. 다음 세션이나 서브에이전트는 그 파일을 읽어서 이어받는다.

**Select (선별)** — 미리 로딩하지 말고 필요한 순간에 검색한다. 사람이 브라우저 탭 50개를 다 읽지 않고 필요할 때 열듯, 코드베이스 전체가 아니라 현재 작업 파일과 심볼만 컨텍스트에 들어가게 한다.

**Compress (압축)** — 툴 호출 로그 같은 원시 출력은 요약으로 치환한다. 실전에서는 컴팩션을 주기적으로 트리거하는 게 핵심인데, 간단한 임계값 기반 예시는 이렇다:

```python
def maybe_compact(messages, token_count, threshold=60_000):
    if token_count < threshold:
        return messages
    # 도구 출력 원문은 버리고 결과 요약만 유지
    compacted = [m for m in messages if m["role"] == "system"]
    compacted.append({
        "role": "assistant",
        "content": summarize_with_llm(messages)  # 진행 요약 + 확정된 결정만
    })
    return compacted
```

요령은 "대화를 요약"하는 게 아니라 **확정된 결정 사항과 아직 열린 질문만 추려 새로운 최소 컨텍스트를 만드는** 것이다.

**Isolate (격리)** — 서브에이전트는 많은 사람이 '병렬화'를 위해 쓰지만, 본질은 컨텍스트 관리 장치다. 오케스트레이터는 조사·구현·리뷰를 각자의 깨끗한 윈도우에서 수행하고 결과 요약만 회수한다. 각 서브에이전트가 컨텍스트 로트에 노출되는 시간이 짧아지고, 실패 모드도 국소화된다.

## 4. AGENTS.md: 코드 에이전트를 위한 컨텍스트 계약서

이 프레임워크의 가장 빠른 실천법이 바로 프로젝트 루트의 지시 파일이다. AGENTS.md는 OpenAI Codex, Google Jules, Cursor, Factory 등이 공동으로 만든 개방 형식으로, 공식 사이트 기준 6만 개 이상의 오픈소스 프로젝트가 채택했다. README가 사람을 위한 것이라면 AGENTS.md는 에이전트를 위한 것이다.

CLAUDE.md, .cursorrules 같은 벤더별 파일과 달리 AGENTS.md 하나로 대부분의 코딩 에이전트를 커버할 수 있다는 것이 채택 이유다. 모노레포에서는 서브디렉터리마다 중첩 배치하면 에이전트가 트리에서 가장 가까운 파일을 우선 적용한다.

좋은 AGENTS.md는 짧고 절차적이다. 위치도 중요하다 — 컨텍스트 로트 연구들이 보여주듯 중간에 묻힌 정보는 회수율이 떨어지므로, 절대 지켜야 할 제약(보안, 아키텍처 원칙)은 파일 앞부분에 둔다.

```markdown
# AGENTS.md

## Build & Test
- 테스트: `pnpm test` (PR 전 전체 통과 필수)
- 타입 체크: `pnpm typecheck`

## Constraints (절대 규칙 — 최우선)
- `.env` 파일 절대 커밋 금지
- `src/legacy/` 하위 코드는 수정 금지, 래핑만 허용
- DB 마이그레이션은 항상 forward-only

## Conventions
- 커밋 메시지: `[도메인] 요약` 형식
- 에러는 예외 발생 대신 Result 타입 반환
```

여기에 한 가지를 더하자. 도구가 많은 프로젝트라면 컨텍스트 컨퓨전을 막기 위해 MCP 서버도 프로젝트별로 최소 구성으로 쪼개는 것이 좋다. 연결된 전체 도구 카탈로그가 시스템 프롬프트를 잠식하기 때문이다.

## 마치며: 컨텍스트는 설계 대상이다

핵심을 요약하면:

- **긴 컨텍스트는 보험이 아니다.** Chroma의 18개 모델 실험과 Databricks 연구 모두, 입력이 길어지면 성능이 실제로 하락함을 보여줬다. 윈도우가 아니라 어텐션 예산이 병목이다.
- **실패에는 패턴이 있다.** 포이즈닝·디스트랙션·컨퓨전·클래시. 증상이 "에이전트가 이상해졌다"로 보일 때 원인은 대부분 모델이 아니라 컨텍스트 품질이다.
- **처방은 4전략이다.** Write(외부화), Select(저스트인타임), Compress(압축), Isolate(격리). 도구 남용은 Berkeley 리더보드가 보여주듯 정확히 역효과다.
- **오늘 당장 할 수 있는 것.** 저장소에 AGENTS.md를 작성하고, 절대 규칙을 맨 앞에 두는 것. 30분이면 된다.

다음 세션부터 관찰해보라. 에이전트가 규칙을 어기기 시작하는 지점이 있다면, 그것은 모델의 한계가 아니라 컨텍스트가 썩기 시작한 신호다. 그때마다 물어야 할 질문은 하나다. "이 토큰, 정말 지금 필요한가?"
