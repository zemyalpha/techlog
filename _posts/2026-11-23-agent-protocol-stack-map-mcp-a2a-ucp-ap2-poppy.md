# 에이전트 프로토콜이 아홉 개인 시대, 결국 답은 계층이었다 — MCP·A2A·UCP·AP2·Poppy 스택 지도

MCP, A2A, AG-UI, A2UI, UCP, AP2, ACP, x402, 그리고 이번 주의 Poppy까지. 새 에이전트 프로토콜이 발표될 때마다 "이번엔 또 뭐가 다르지?"라는 한숨이 나온다. 심지어 약어조차 충돌한다. ACP는 IBM 계열의 Agent Communication Protocol을 가리키기도 하고, OpenAI 쪽 상거래 프로토콜을 가리키기도 한다.

그런데 이 프로토콜들을 하나씩 뜯어보면 이상한 점을 발견하게 된다. **대부분은 서로 경쟁하는 관계가 아니라는 것**이다. TCP와 IP와 HTTP가 경쟁하지 않듯, 이들은 각자 다른 계층의 문제를 풀고 있다. 이 글에서는 2026년 11월 현재의 에이전트 프로토콜 지도를 계층 구조로 정리하고, 각 계층이 어디까지 왔는지, 그리고 실무자가 무엇을 지금 도입하고 무엇을 기다려야 하는지를 정리한다.

## 한 질문으로 끝내는 프로토콜 선택

모든 프로토콜 선택은 "내 에이전트가 지금 무엇과 대화하는가"라는 질문 하나로 정리된다.

| 내 에이전트의 대화 상대 | 프로토콜 | 한 줄 요약 |
|---|---|---|
| 도구와 데이터 | **MCP** | API, DB, 파일을 에이전트에 연결 |
| 다른 에이전트 | **A2A** | 남이 만든 에이전트에게 일을 위임 |
| 사용자의 화면 | **AG-UI** | 에이전트가 하는 일을 사용자에게 실시간으로 보여줌 |
| 상점·비즈니스 | **UCP** | 검색, 장바구니, 결제를 하나의 표준으로 |
| 결제 승인 | **AP2** | 사용자가 정말 결제를 승인했는지 서명으로 증명 |
| 기업과 개인 에이전트 사이 | **Poppy** | 개인 에이전트가 기업에 자신을 소개하고 권한을 받음 |

이 테이블만 기억하면 된다. 나머지는 각 계층의 디테일이다.

## 1층: MCP — 에이전트의 손과 발

Model Context Protocol은 가장 아래 계층이다. 에이전트가 데이터베이스를 읽고, GitHub에 커밋하고, Slack에 메시지를 보내는 데 필요한 연결 규격이다.

2026년의 큰 변화는 거버넌스와 스펙 양쪽에서 왔다. 먼저 2025년 12월 9일, Anthropic은 MCP를 리눅스 재단 산하의 Agentic AI Foundation(AAIF)에 기증했다. 그다음 2026년 7월 28일 스펙에서는 프로토콜의 근본 구조가 바뀌었다. 세션 기반의 상태 유지 방식을 버리고 **무상태(stateless) 요청-응답 모델**로 전환한 것이다. 실무적으로는 이런 변화가 있다.

- 세션 핸드셰이크가 사라져 로드밸런서 뒤의 MCP 서버를 수평 확장하기 훨씬 쉬워졌다
- 클라이언트가 서버에 연결 전에 지원 기능을 물을 수 있는 discovery 호출이 생겼다
- Roots, Sampling, Logging은 deprecate되고 Tasks는 코어에서 공식 확장으로 빠졌다
- 구형 HTTP+SSE 전송은 Streamable HTTP로 마이그레이션이 권고된다

작년에 MCP 서버를 만들어둔 팀이라면 changelog를 먼저 읽어야 하는 이유다.

## 2층: A2A — 남의 에이전트에게 일 맡기기

MCP가 "내가 제어하는 도구"용이라면, A2A(Agent2Agent)는 "내가 소유하지 않은, 자기 두뇌가 있는 에이전트"용이다. 각 에이전트가 자신이 할 수 있는 일을 설명하는 **Agent Card**를 공개하면, 다른 에이전트가 이를 발견하고 작업을 위임한다.

A2A의 2026년 행보는 표준의 교과서적인 성숙 경로를 따랐다. 구글이 2025년 4월 발표하고 같은 해 6월 리눅스 재단에 기증했으며, 2026년 3월 12일 **v1.0 정식 버전**을 출시했다. JSON-RPC, gRPC, HTTP+JSON 바인딩을 갖췄고, 리눅스 재단 발표 기준 150개 이상 조직이 참여했다. 그리고 2026년 8월 27일, MCP가 속해 있던 AAIF로 합류하면서 사실상 같은 지배구조 아래에 놓였다.

Agent Card는 다음과 같은 형태다. 잘 알려진 경로(`/.well-known/agent.json` 등)에 공개하는 것이 관례다.

```json
{
  "name": "travel-policy-agent",
  "description": "사내 출장 정책을 검사하고 승인하는 에이전트",
  "url": "https://agents.example.com/a2a",
  "capabilities": { "streaming": true, "pushNotifications": true },
  "skills": [
    {
      "id": "policy_check",
      "name": "출장 정책 검사",
      "inputModes": ["text"],
      "outputModes": ["text"]
    }
  ]
}
```

## 3~4층: UCP와 AP2 — 에이전트가 물건을 사는 계층

상거래 계층의 **UCP(Universal Commerce Protocol)**는 구글이 주도하는 표준으로, 제품 검색부터 장바구니, 체크아웃, 주문 조회까지를 하나의 규격으로 묶는다. Stripe가 공식 문서에서 지원을 명시했고, Shopify 스토어에 기본 탑재되어 있다는 점이 채택의 실질적 추진력이다.

그 아래 **AP2(Agent Payments Protocol)**는 결제 승인의 신뢰 문제를 푼다. 에이전트가 "사용자가 이 결제를 승인했다"고 주장할 때, 서명된 승인(mandate)으로 그것을 증명하는 계층이다. 구글의 에이전트 커머스 이니셔티브로 공개되어 UCP와 짝을 이룬다.

즉 "에이전트가 쇼핑한다"는 한 문장 뒤에는 UCP(상점과의 상호작용)와 AP2(결제 승인 증명)라는 두 개의 서로 다른 문제가 숨어 있다.

## 최상층: Poppy — 개인 에이전트의 신분증

2026년 11월 13일, Sierra는 Personal Agent Protocol의 v1.0을 발표했다. 흥미로운 것은 방식이다. Poppy는 새 휠을 발명하지 않았다. **MCP, OpenAPI, UCP 같은 기존 표준 위에 인증(OAuth)과 권한 관리 계층을 얹은 조합 규격**이다. 개인 에이전트가 기업 사이트에 도착해 자신이 누구인지 밝히고, 무엇이 허용되는지 문의하고, 권한을 시간이 지나도 관리할 수 있게 해준다.

채택 속도가 이 프로토콜의 핵심 무기다. Shopify는 모든 가맹점에 대해 Poppy를 자동 활성화했고(각 스토어가 별도 구현 없이 Poppy 파일을 자동 게시), Meta의 AI 에이전트 Muse는 방문하는 모든 사이트에서 Poppy를 먼저 찾도록 설정됐다. 발표 시점 기준 100개 이상 기업이 디자인 파트너로 참여 중이다.

## 실전 의사결정: 지금 뭘 도입해야 하나

계층 지도가 있으면 의사결정은 단순해진다.

```
내 서비스가 에이전트에게 노출되어야 하나?
├─ 도구/데이터 수준 → MCP 서버를 만들 것 (Streamable HTTP로)
├─ 전문 에이전트를 외부에 제공 → Agent Card 공개 + A2A 지원
├─ 커머스 → UCP 확인, 결제 승인 필요하면 AP2
└─ 개인 에이전트 고객 유치 → Poppy 구현 킷 검토
```

몇 가지 실무 팁을 덧붙인다.

1. **아래 계층부터 도입한다.** MCP는 이미 검증 단계를 지났다. 반면 상거래 계층(UCP/AP2)은 참여사는 화려하지만 실제 트랜잭션 볼륨은 아직 초기다. 사내 도구라면 MCP만으로 충분하다.
2. **동음이의 약어를 조심한다.** 문서에서 "ACP"를 만나면 IBM 계열 에이전트 통신 프로토콜인지, 다른 것인지 맥락부터 확인하라.
3. **거버넌스를 확인한다.** MCP와 A2A는 모두 AAIF(리눅스 재단) 산하다. 반면 UCP·AP2는 구글 주도, Poppy는 Sierra 주도다. 표준의 중립성이 조직 도입 승인에 영향을 줄 수 있다.
4. **조합 규격의 이점을 활용한다.** Poppy처럼 기존 표준 위에 얹는 접근은 하위 호환성 리스크가 작다. 자체 프로토콜을 설계할 일이 있다면 같은 전략을 취할 것.

## 결론

- 에이전트 프로토콜은 난립이 아니라 **분업**이다. 도구(MCP) → 에이전트(A2A) → 상거래(UCP) → 결제(AP2) → 개인 에이전트 신원(Poppy)의 계층 구조다.
- MCP는 2025년 12월 AAIF 기증, 2026년 7월 무상태 전환으로 이미 "인프라"가 됐다. A2A도 v1.0과 AAIF 합류로 안정기에 접어들었다.
- 상층부(UCP, AP2, Poppy)는 채택 속도가 승부처다. Shopify 전 스토어와 Meta Muse의 Poppy 탑재는 초기 판도를 크게 움직였다.
- 오늘 할 일은 단순하다. **내 에이전트(또는 내 서비스)가 무엇과 대화하는가를 정의하고, 해당 계층의 최신 스펙 문서를 읽는 것.** 그 한 질문이 프로토콜 홍수의 해독제다.
