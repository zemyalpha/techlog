# RAG는 죽었다고 했는데 왜 아직 살아있나 — 백만 토큰 시대의 선택 기준

2024년 중반, 프런티어 모델들의 컨텍스트 윈도우가 백만 토큰을 넘어서면서 "RAG는 죽었다"는 선언이 반복해서 나왔다. 청킹, 임베딩, 벡터 인덱스, 검색 평가로 이어지는 파이프라인 전체를 삭제하고 그냥 프롬프트에 전부 넣으면 된다는 주장이었다. 2년이 지난 지금 결과는 어땠을까. RAG 프레임워크 사용은 오히려 늘었고, 롱컨텍스트 모델도 함께 성장했다. 둘 다 이긴 것이다.

이 글에서는 왜 둘 중 하나를 고르는 문제가 아니게 됐는지를 데이터로 풀고, 실제 서비스에서 코퍼스 규모·쿼리 유형·비용 구조에 따라 어느 쪽을 선택할지 판단할 수 있는 기준을 정리한다.

## 1. 두 접근은 같은 문제를 다른 방식으로 푼다

먼저 개념을 정확히 분리해야 한다. 혼동이 대부분의 잘못된 아키텍처 결정에서 출발한다.

- **RAG(검색 증강 생성)는 아키텍처 패턴이다.** 검색기(주로 벡터 데이터베이스)가 쿼리에 관련된 문서 조각만 찾아내고, 그 일부만 모델의 컨텍스트에 주입한다. *선택*이 핵심이다.
- **롱컨텍스트는 모델 능력이다.** 100만 토큰 이상의 프롬프트를 잘림 없이 처리한다. 무엇이 관련 있는지 모델 스스로 찾게 한다. *용량*이 핵심이다.

둘 다 "모델이 학습하지 않은 외부 지식에 접근하게 한다"는 같은 문제를 푸는데, 트레이드오프 구조가 근본적으로 다르다. 그래서 "어느 쪽이 낫냐"는 질문 자체가 틀린 질문이고, "이 기능에는 어느 쪽이 맞냐"가 올바른 질문이다.

## 2. 컨텍스트 창이 커져도 사라지지 않는 문제들

### 2-1. Lost in the Middle은 여전히 해결되지 않았다

가장 중요한 발견은 이것이다. 컨텍스트 창 크기와 상관없이, LLM은 핵심 정보가 프롬프트 **중간**에 위치할 때 성능이 확실하게 저하된다. 스탠퍼드 연구진이 문서화한 이 현상은 정확도가 컨텍스트의 시작과 끝에서 가장 높고 중간에서 떨어지는 U자 곡선을 그린다. 일부 프로덕션 비교에서는 관련 정보가 중간에 묻혀 있을 때 정확도가 30% 이상 떨어지는 것으로 측정되기도 했다.

1000만 토큰 창은 이 문제를 해결하지 못한다. **중간이 더 넓어질 뿐이다.** 50만 토큰 문서를 통째로 넣고 5,000 토큰짜리 정밀 검색 결과와 같은 정확도를 기대할 수 없는 이유다.

롱컨텍스트를 쓸 거라면 배치 전략으로라도 완화해야 한다:

```python
def build_context_with_position_awareness(retrieved_docs: list, query: str) -> str:
    """관련도 순 정렬 후, 가장 중요한 문서를 시작과 끝에 배치.
    Lost-in-the-middle 저하를 완화하는 컨텍스트 조립."""
    scored = [(doc, relevance_score(doc, query)) for doc in retrieved_docs]
    scored.sort(key=lambda x: x[1], reverse=True)

    top_docs = scored[:3]        # 최상위 관련도 → 컨텍스트 맨 앞
    bottom_docs = scored[-2:]    # 차상위 → 맨 뒤
    middle_docs = scored[3:-2]   # 나머지 → 중간 (덜 중요하므로)

    ordered = top_docs + middle_docs + bottom_docs
    return "\n\n".join(doc.content for doc, _ in ordered)
```

### 2-2. 모델마다 롱컨텍스트 내구성이 다르다

같은 100만 토큰 창이라도 모델에 따라 실제 성능 유지 구간이 다르다. 일부 모델은 12만 8천 토큰 입력에서 RAG 결합 성능이 오히려 개선되는 반면, 다른 모델군은 3만 2천 토큰을 넘기면 성능이 나빠지는 것으로 보고된다. 광고된 창 크기는 스펙이지, 신뢰 가능한 가용 창 크기가 아니라는 뜻이다. "컨텍스트 로트(context rot)"라 불리는 이 간극은 팀마다 자기 모델로 직접 측정해봐야 한다.

### 2-3. 비용과 지연 시간의 격차

제3자 프로덕션 비교 분석에 따르면, 쿼리당 비용은 RAG가 약 0.008센트, 롱컨텍스트가 약 10센트 수준으로 **1,000배 이상** 차이 난다. 응답 시간도 롱컨텍스트 쿼리는 수십 초 걸릴 수 있는 반면 타겟 검색은 1초 안팎이다. 매 요청마다 전체 컨텍스트를 다시 처리해야 하기 때문에, 규모가 커질수록 이 격차는 벌어진다.

다만 프롬프트 캐싱이 이 계산을 바꿨다. 코퍼스가 안정적이라면 캐시된 컨텍스트를 여러 쿼리에 재사용할 수 있어, 대략 20만 토큰 이하의 소규모·정적 코퍼스에서는 검색 인프라를 새로 짜는 것보다 풀 컨텍스트 + 캐싱이 검색 인프라보다 저렴할 수 있다. 캐싱을 쓰더라도 lost-in-the-middle 문제는 그대로 남는다는 점은 별개다.

## 3. 데이터가 말해주는 정확도 비교

롱컨텍스트와 RAG를 직접 비교한 평가 논문(arXiv 2501.01880, "Long Context vs. RAG for LLMs: An Evaluation and Revisits")의 핵심 결과는 이렇다:

- **롱컨텍스트는 Wikipedia 기반 질의응답에서 일반적으로 RAG를 앞선다.** 모델이 전체 맥락을 한 번에 보기 때문이다.
- **RAG는 대화 기반·일반 질의에서 우위를 보인다.** 검색된 요약 컨텍스트가 대화 맥락과 더 잘 맞물리기 때문이다.
- **요약 기반 검색(summarization-based retrieval)은 롱컨텍스트와 대등한 성능**을 보이지만, 단순 청크 기반 검색은 뒤처진다. 즉 RAG의 품질은 검색 방식 설계에 달려 있다.

요약하면 어느 쪽도 전면 승리하지 못한다. 과제 유형이 결정한다.

## 4. 선택 프레임워크: 코퍼스·쿼리·운영 조건

위 데이터를 판단 표로 압축하면 이렇다.

| 조건 | RAG 선택 | 롱컨텍스트 선택 |
|------|----------|----------------|
| 코퍼스 크기 | 수백만 문서 | 수백 페이지~소수 문서 (≈20만 토큰 이하) |
| 갱신 빈도 | 실시간·매일 변경 | 거의 정적 |
| 쿼리 유형 | 특정 사실 조회 | 문서 전체를 아우르는 종합 추론 |
| 비용 구조 | 대량 트래픽에 유리 | 소량 트래픽 + 캐싱 시 유리 |
| 출처 추적 | 인용·감사(audit) 필수 | 불필요 |
| 권한 관리 | 사용자별 접근 제어 필요 | 단일 사용자·단일 소유 |

특히 권한 관리는 자주 간과되는 항목이다. 전체 코퍼스를 하나의 프롬프트에 넣는 순간, 사용자별 접근 제어를 프롬프트 바깥에서 처리해야 한다. 검색 단계에서 권한 필터를 거는 RAG가 구조적으로 안전하다.

### 하이브리드가 2026년의 승자 패턴

실무에서 이기는 시스템 대부분은 하이브리드다. **검색으로 후보를 넉넉하게 좁히고, 롱컨텍스트 모델이 그 위에서 추론하게 하는 것.** 검색이 비용과 권한 문제를 해결하고, 롱컨텍스트가 종합 추론 품질을 담당한다.

```python
# 하이브리드: 관대한 검색(retrieval) + 롱컨텍스트 추론(reasoning)
async def hybrid_answer(query: str, top_k: int = 30):
    # 1단계 — 관대하게 검색 (recall 우선, precision은 모델이 처리)
    candidates = await vector_db.search(
        embed(query), limit=top_k,
        filter=user_permission_filter(user_id),  # 권한은 검색 단계에서
    )

    # 2단계 — 위치 인식 배치로 컨텍스트 조립 (2-1 참고)
    context = build_context_with_position_awareness(candidates, query)

    # 3단계 — 롱컨텍스트 모델이 전체를 보고 종합 추론
    return await llm.generate(
        system="다음 문서들만 근거로 답하라. 출처를 명시하라.",
        context=context,
        query=query,
    )
```

`top_k`를 5가 아니라 30처럼 넉넉히 잡는 게 포인트다. 검색 정밀도가 완벽하지 않아도, 모델이 넓은 컨텍스트에서 알아서 걸러낸다.

## 5. 흔히 하는 실수 세 가지

1. **"윈도우가 크니까 다 넣는다"** — lost-in-the-middle로 중간 정보 정확도가 떨어지고, 매 요청 비용이 토큰 수에 비례해 폭증한다. 먼저 코퍼스가 창에 실제로 들어가는지, 들어가도 모델의 가용 창 내인지 측정하라.
2. **청크 크기만 바꾸며 RAG 품질을 튜닝한다** — 평가 논문 결과가 보여주듯 요약 기반 검색이 청크 기반보다 대등하거나 낫다. 검색 방식 자체를 실험 대상에 포함시켜라.
3. **캐싱을 만능 해결책으로 착각** — 캐싱은 비용만 줄인다. 정확도 저하 패턴은 그대로다. 그리고 코퍼스가 조금이라도 바뀌면 캐시가 무효화된다.

## 결론

- 롱컨텍스트와 RAG는 경쟁 관계가 아니라 비용(용량)과 선택(검색)이라는 서로 다른 축의 해법이다. "RAG 죽음"론은 2년이 지나서도 실현되지 않았다.
- 창이 커져도 lost-in-the-middle은 남는다. 정보 배치 전략과 실사용 모델의 가용 창 측정이 선행되어야 한다.
- 비용·권한·갱신성에서 대규모 프로덕션은 여전히 RAG가 기본값이고, 소규모·정적 코퍼스 + 캐싱이면 롱컨텍스트가 이길 수 있다.
- 2026년의 승자 패턴은 하이브리드: 관대한 검색으로 후보를 모으고(권한 필터 포함), 롱컨텍스트로 종합 추론한다.

당장 시도해볼 첫 단계: 자기 서비스의 코퍼스 크기와 일일 쿼리 수로 연간 토큰 비용을 계산해보라. 그 숫자가 검색 인프라 구축 비용보다 크다면 답은 이미 나온 것이다.
