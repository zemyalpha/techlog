# 토큰을 늘리지 않고 레이어를 세 번 돈다 — Inkling 2 Mini 루프 트랜스포머 해부와 맥 실행 가이드

2026년 11월 20일, Thinking Machines Lab이 [Inkling 2 Mini](https://thinkingmachines.ai/news/inkling-2-mini/)를 공개했다. 이 모델이 흥미로운 이유는 파라미터 수가 아니라 구조다. 대부분의 로컬 LLM이 "더 작은 모델을 얼마나 잘 압축할까"를 추구할 때, 이쪽은 "같은 크기의 모델이 토큰 하나를 처리할 때 계산을 더 많이 하게" 만들었다.

결론부터 말하면, 총 26.4B 파라미터의 MoE 모델이 토큰당 3.4B 활성 파라미터만 쓰면서도, 에이전트 코딩 벤치마크에서 100B 미만 오픈웨이트 모델 중 최고 성적을 냈다. 메모리 풋프린트는 약 20GB. 맥북에서 돌아간다. 이 글에서는 이 구조가 왜 성능을 올리는지, 어느 영역에서는 올리지 못하는지, 그리고 실제로 로컬에서 실행하는 방법까지 다룬다.

## 루프 트랜스포머란 무엇인가

일반적인 트랜스포머는 토큰이 레이어를 순서대로 한 번씩 통과한다. 24개 레이어면 토큰당 정확히 24번의 순전파를 거친다. 계산량을 늘리려면 두 가지 방법밖에 없었다. 레이어를 더 쌓거나(파라미터 증가), 토큰을 더 생성하거나(추론 토큰 증가).

Inkling 2 Mini는 세 번째 길을 택했다. 공식 발표에 따르면 24개 레이어를 6개씩 네 블록으로 나누고, **중간 두 블록(12개 레이어)을 토큰마다 세 번 통과**시킨다. 첫 블록과 마지막 블록은 한 번만 돈다. 결과적으로 토큰 하나가 지나가는 유효 레이어 수는 6 + 12×3 + 6 = 48이다.

이게 가능한 이유는 루프가 "같은 가중치를 재방문"하는 것이기 때문이다. 저장 공간(파라미터)은 24레이어 분량 그대로인데, 계산량(depth)만 48레이어 분량으로 커진다. 같은 가중치를 여러 번 적용하면 정보가 손실되지 않을까 하는 의문이 자연스럽게 드는데, 실제로는 반대다. 중간 레이어는 추상적 추론을 담당하는 경향이 있어서(초기·말단 레이어가 임베딩 변환과 출력 분포에 더 가까운 역할을 한다), 이 부분을 반복 통과시키면 정제(refinement) 효과가 생긴다는 게 Thinking Machines의 설명이다.

수치로 정리하면 이렇다:

| 항목 | 수치 |
|------|------|
| 총 파라미터 | 26.4B |
| 토큰당 활성 파라미터 (스파스 라우팅) | 3.4B |
| 토큰당 유효 가중치 활성 (루프 반영) | 5.4B |
| 레이어 구조 | 24개, 6개씩 4블록, 중간 2블록 3회 루프 |
| 컨텍스트 | 1M 토큰 |
| 메모리 풋프린트 | 약 20GB (NVFP4 + MXFP8 혼합) |
| 라이선스 | Apache 2.0 |

여기에 하나 더 붙는다. Thinking Machines는 모델을 만들 때 [Inkling 2 Small 계열에서 전문가(expert)의 3분의 2를 가지치기(pruning)](https://thinkingmachines.ai/news/inkling-2-mini/)해서 크기를 줄이고, 대신 루프를 넣어 추론 능력을 회복시켰다고 밝혔다. 즉 "가지치기 + 루프 보상"이라는 조합이고, 이후 훈련은 메인 레시피를 그대로 따랐다고 한다.

## 성능은 어디서 오고, 어디서 안 오는가

벤치마크 숫자를 먼저 보자. Thinking Machines 발표 기준(모두 [공식 페이지](https://thinkingmachines.ai/news/inkling-2-mini/)와 [Hugging Face 발표](https://huggingface.co/blog/inkling2mini)에서 확인 가능한 수치):

- **DeepSWE v1.1: 48.2%** — 100B 미만 오픈웨이트 모델 중 1위
- **Vals Index v2.2: 46.5%** — 마찬가지로 동급 최고
- AA Index: 20.1
- SWE-bench Pro v2에서도 동급 최상위권 (공식 비교 차트 참조)

여기서 중요한 건 뭘 측정했느냐다. 발표문이 스스로 밝힌 한계가 핵심 통찰이다. **루프는 추론 능력을 올리지만 지식 저장량을 올리지는 못한다.** 사실성 벤치마크(AA-Omniscience, SimpleQA 계열)에서는 루프 수를 늘려도 점수가 개선되지 않았고, 같은 크기 모델의 평균적인 수준에 머문다. 지식은 총 파라미터 수의 함수이고, 루프는 같은 가중치를 재사용하므로 새로운 사실을 저장할 공간이 늘어나지 않기 때문이다.

반대로 개선되는 영역은 명확하다:

1. **직렬 추론(serial reasoning)** — 공식과 함께 출시한 연구용 가변 루프 변형(TML-d24-varloop-research) 실험에서, 루프를 1패스에서 3패스로 늘리면 CoT 없이 버티는 시간 지평(time horizon)이 16초에서 37초로 늘었다. 직렬 추론 벤치마크 성능은 훈련에 쓰인 5패스의 두 배인 10루프까지 계속 향상됐다.
2. **롱컨텍스트** — GraphWalks BFS, MRCR v2 같은 장문 과제에서 패스 수가 늘수록 성능이 올라갔다.
3. **에이전트 워크로드** — 위의 DeepSWE 결과가 이 범주다. 다만 지식이 부족한 부분은 검색과 도구 사용으로 보완하도록 훈련돼서인지, BrowseComp·DeepSearchQA 같은 검색형 과제에서는 동급 오픈웨이트 최고 수준이라고 발표문은 밝힌다.

이 구분은 실무적으로 중요하다. "26B 모델이 100B급 성능"이라는 헤드라인을 그대로 믿고 지식 집약 과제(사실 Q&A, 긴 도메인 문서 이해)에 투입하면 실망한다. 루프 트랜스포머의 성격은 "계산은 많이, 지식은 적게"다. 에이전트가 도구로 지식을 보완하는 구조라면 최적이고, 오프라인 폐쇄망에서 모델 자체 지식에 의존해야 한다면 답이 다르다.

또 하나 눈에 띄는 건 모니터링 가능성(monitorability)이다. 루프는 "생각을 토큰으로 적어 내려가는 대신" 내부에서 더 깊이 처리할 수 있게 해준다. 발표에 따르면 루프가 늘어나도 CoT는 짧아지지만 가독성은 유지됐고, 에이전트 사보타주(sabotage) 테스트 점수는 루프를 추가해도 높아지지 않았다고 한다. 추론을 눈에 보이지 않는 곳에서 수행하는 모델의 해석 가능성 문제를 루프 수를 변수로 바꿔가며 측정한 것 자체가 이번 릴리스의 연구적 가치다.

## 맥에서 직접 돌려보기

여기까지가 이론이고, 이 모델의 실용적 매력은 로컬 실행이다. NVFP4(마지막 4개 레이어는 MXFP8)로 학습·배포돼서 전체가 약 20GB다. [Hugging Face 블로그](https://huggingface.co/blog/inkling2mini) 기준 IQ4_NL 양자화 버전은 32GB GPU 메모리 또는 통합 메모리에 들어간다. M계열 맥 32GB 이상이면 된다. Thinking Machines 연구자들이 비행기 안에서 인터넷 없이 MacBook Pro(M5 Pro, 48GB)로 플레이 가능한 비행 시뮬레이터를 직접 만들어 시연한 것이 이 모델의 포지셔닝 그 자체다.

**가장 쉬운 방법 — Ollama:**

```bash
ollama run inkling-2-mini:26b-a5b-iq4_NL
```

Ollama 라이브러리에 이미 등록돼 있다(태그명의 a5b는 토큰당 5.4B 유효 활성을 가리킨다). 비전 입력과 도구 호출을 지원한다.

**서빙 엔진으로 쓰는 방법 — vLLM:**

```bash
vllm serve "thinkingmachines/Inkling-2-Mini"
```

llama.cpp도 지원된다. macOS·윈도우용 Llama App에서 GGUF 양자화(IQ4_NL 또는 Q8_0)를 고르면 되고, IQ4_NL은 원본 NVFP4를 다른 4비트 포맷으로 변환한 것이다. Q8_0은 거의 무손실이지만 메모리를 더 먹고 느리다.

**Python API로 가변 루프 실험:**

연구용 변형은 루프 수를 코드로 바꿀 수 있다:

```python
from transformers import AutoModelForMultimodalLM, AutoProcessor

model_id = "thinkingmachines/TML-d24-varloop-research"
processor = AutoProcessor.from_pretrained(model_id)
model = AutoModelForMultimodalLM.from_pretrained(
    model_id,
    text_config={"loop_num_passes": 2},  # 1~5 사이에서 조절
)
```

추가로 DSpark 초안 모델(drafter)이 같이 배포돼서 추측적 디코딩으로 속도를 더 끌어올릴 수 있다. Tinker 플랫폼에서 커스텀 파인튜닝도 지원한다.

라이선스는 Apache 2.0이라 상업적 사용에 제약이 없다. [Hugging Face 모델 카드](https://huggingface.co/thinkingmachines/Inkling-2-Mini)에서 직접 확인할 수 있다.

## 도입 전에 점검할 4가지

**첫째, 메모리 계산을 다시 하라.** 20GB 모델이라고 24GB 맥에 들어가는 건 아니다. IQ4_NL 기준 32GB 통합 메모리가 안전선이다. 운영체제와 KV 캐시(특히 컨텍스트가 길면)를 고려하면 48GB가 여유 있는 구성이다.

**둘째, 속도 비교는 "토큰당 5.4B" 기준으로 하라.** 루프 때문에 같은 MoE라도 활성 파라미터가 3.4B가 아니라 5.4B다. 3.4B급 모델과 토큰당 속도를 비교하면 실망한다. 파라미터당 처리량이 아니라 "동급 성능 대비 속도"로 비교해야 공정하다.

**셋째, 지식 과제에는 검색을 붙여라.** 앞서 봤듯 사실성은 동급 평균이다. RAG나 도구 사용을 붙이지 않고 폐쇄망 지식 Q&A로 쓰면 루프의 이점을 못 살린다.

**넷째, 지시 따르기 약점을 확인하라.** 모델 카드와 커뮤니티 평가에서 멀티턴·복합 제약 조건 지시 따르기(instruction following)는 동급 최고 수준이 아니라고 명시돼 있다. 긴 대화형 워크플로우보다는 한 작업을 길게 파고드는 에이전트 코딩에 더 맞는 성격이다.

## 결론

Inkling 2 Mini가 보여준 방정식은 단순하다. **성능 = f(파라미터, 토큰당 계산 깊이)**인데, 업계가 그간 앞의 항에만 올인했다면, 이번엔 뒤의 항을 무겁게 치환한 것이다. 파라미터를 줄여 메모리를 확보하고(전문가 가지치기), 줄어든 만큼 계산을 깊게 만들어(루프) 성능을 회복했다. 지식은 파라미터에 남아 있으므로 그 갭은 도구와 검색으로 메운다.

당장 시도해볼 것은 명확하다:

- 맥 32GB 이상 사용자라면 `ollama run inkling-2-mini:26b-a5b-iq4_NL` 한 줄로 오늘 밤 체험이 가능하다
- 에이전트 코딩 워크로드를 로컬로 옮기고 싶다면 DeepSWE v1.1 48.2%라는 숫자가 현재 로컬 모델의 실질적 상한선 기준점이 된다
- 루프가 늘어도 사보타주 성향이 오르지 않았다는 모니터링 결과와 가변 루프 변형은 온디바이스 에이전트의 안전성 연구 재료로 가치가 크다

로컬 LLM의 다음 경쟁이 "압축 기술"에서 "토큰당 계산 구조"로 넘어가고 있다는 신호로 읽는다. 루프 트랜스포머가 주류가 될지는 모르지만, 파라미터 수만 보던 모델 선택 기준에 "토큰당 유효 활성 파라미터"라는 새 열이 추가됐다는 건 분명하다.
