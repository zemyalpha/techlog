# 문서 CRDT냐 관계형 동기화냐 — 2026년 로컬퍼스트 동기화 엔진 선택 가이드

협업 앱이나 오프라인 지원 앱을 만들 때 "동기화를 직접 짤까, 엔진을 쓸까"는 이제 결정된 질문이다. 직접 만들면 충돌 해결, 부분 오프라인, 재접속 병합 전부를 스스로 다뤄야 한다. 문제는 그다음이다. **엔진 후보가 크게 두 진영으로 갈렸고**, 둘은 해결하는 문제 자체가 다르다.

한쪽은 **문서(document) CRDT**다. Yjs와 Automerge가 여기 속한다. 노션 문서처럼 사용자가 편집하는 하나의 거대한 트리 구조를 다루고, 키 입력 단위로 변경을 기록해 아무리 동시에 편집해도 자동으로 병합한다.

다른 쪽은 **쿼리 기반 관계형 동기화**다. Rocicorp의 Zero와 ElectricSQL이 여기 속한다. 화면에 필요한 데이터를 일반 쿼리로 지정하면 서버 데이터베이스의 해당 부분만 로컬 스토어로 흘러들어오게 만든다. UI는 항상 로컬을 읽고, 동기화는 뒤에서 조용히 일어난다.

이 글에서는 양쪽 진영의 실제 코드와 검증된 수치를 놓고 **어떤 상황에서 무엇을 골라야 하는지**를 정리한다.

## 진영 1: 문서 CRDT — Yjs와 Automerge 3

### Yjs: 사실상의 표준, 가장 넓은 생태계

Yjs는 브라우저에서 동작하는 CRDT 라이브러리로, 협업 에디터 시장에서 사실상의 표준 자리를 오래 지켜왔다(2026년 11월 기준 GitHub 스타 약 2.3만 개). 생태계가 넓다는 것이 최대 강점이다. `y-websocket`·`y-webrtc` 같은 네트워킹 모듈, ProseMirror·CodeMirror·TipTap·Monaco 같은 에디터 바인딩이 갖춰져 있어 텍스트 편집 UI를 붙이는 데 드는 노력이 가장 적다.

자바스크립트 구현 외에, Yjs의 알고리즘은 y-crdt 프로젝트를 통해 Rust로 포팅되어 `yrs` 크레이트로 공개되어 있고 Go·Python·.NET·Swift 포트도 함께 운영된다. 노드 서버와 파이썬 백엔드에서 같은 병합 로직을 재사용할 수 있다는 뜻이다.

시작 코드는 이렇게 짧다:

```javascript
import * as Y from 'yjs';

const ydoc = new Y.Doc();
const ytext = ydoc.getText('draft');

ytext.insert(0, '안녕하세요');
ytext.insert(5, ', 로컬퍼스트');

// 변경은 delta 단위로 관찰한다
ytext.observe(event => {
  console.log('변경됨:', ytext.toString());
});
```

`Y.Doc`가 곧 저장 단위다. 문서 하나가 이진 바이너리로 직렬화되고, 바이너리끼리 교환하면 어느 쪽에서 합쳐도 같은 결과가 나온다.

### Automerge 3: 메모리 문제를 10배로 줄인 릴리스

Automerge는 잉크앤스위치(Ink & Switch) 연구소에서 출발한 프로젝트로, 리포 README의 목표 선언이 상징적이다: "로컬퍼스트 앱을 위한 PostgreSQL이 되는 것." 코어는 Rust로 작성되어 WebAssembly로 자바스크립트에 노출되며, 풀타임 유지보수자가 붙어 있는 상태다(2026년 11월 기준 최신 버전 3.5.0). 변경 이력 전체를 저장해 오프라인 협업과 버전 관리를 지원한다는 점이 특징이다. 키 입력마다 고유 ID를 부여하는 방식이라 이력이 길어지면 메타데이터가 눈덩이처럼 불어났고, 이것이 오랫동안 Automerge의 최대 약점이었다.

2025년 7월에 나온 Automerge 3.0은 바로 이 지점을 공략했다. 압축된 칼럼 형식을 런타임에도 그대로 쓰도록 아키텍처를 다시 짰고, 공식 발표 기준으로 **메모리 사용량이 10배 이상 감소**했다. 대표 사례가 소설 『모비 딕』 전문을 붙여넣었을 때 Automerge 2에서 약 700MB를 쓰던 것이 **3.0에서는 1.3MB**로 줄었다는 것이다. 이력이 긴 문서의 로드 시간도 극적으로 개선되어, 17시간이 지나도 로드되지 않던 문서가 9초 만에 열린 사례가 공식 블로그에 소개됐다. 파일 형식은 2와 같고 API는 거의 하위 호환되므로 기존 사용자의 업그레이드 부담이 작다.

Automerge의 사용감은 이렇다:

```javascript
import * as A from '@automerge/automerge';

let doc = A.init();
doc = A.change(doc, d => {
  d.title = '회의록';
  d.items = [];
});
doc = A.change(doc, d => {
  d.items.push({ done: false, text: '동기화 엔진 조사' });
});

// 이력 기반 API — 버전 관리가 언어에 내장돼 있다
const [doc2, change] = A.getLastLocalChange(doc);
console.log('현재 문서:', A.getHeads(doc));
```

## 진영 2: 쿼리 기반 관계형 동기화 — Zero와 ElectricSQL

### Zero: "화면에 필요한 것만" 동기화

Rocicorp의 Zero는 발상 자체가 다르다. 문서 전체를 동기화하는 게 아니라, **앱 코드에서 작성한 일반 쿼리가 곧 동기화 범위가 되는** 구조다. 공식 문서의 첫 문장이 이것을 그대로 말한다: "쿼리가 Zero에서 데이터를 읽고 동기화하는 방식이다." 로컬에 정규화된 데이터스토어를 두고 읽기는 전부 로컬을 먼저 치고, `zero-cache`라는 중간 서버가 Postgres 논리 복제(logical replication)를 구독해 변경분을 증분으로 흘려보낸다.

```typescript
// Zero v1 공식 문서 예제 구성 — 쿼리 정의가 곧 동기화 범위다
import { defineQuery } from '@rocicorp/zero';
import { z } from 'zod';
import { zql } from './schema';

export const messagesByChannel = defineQuery(
  z.object({ channelID: z.string() }),
  ({ args: { channelID } }) =>
    zql.message.where('channelID', channelID)
);
```

`WHERE` 조건이 바뀌면 동기화되는 데이터도 바뀐다. 테이블 단위 동기화 규칙을 서버에 미리 정의해두는 전통적 방식과 가장 큰 차이점이다. 흥미로운 설계 하나 더: 쿼리 구현은 클라이언트와 서버에 각각 존재하는데, 서버 쪽에서 클라이언트 쿼리에 없는 추가 필터(예: 권한 검증)를 끼워 넣을 수 있다. 메인 리포는 `rocicorp/mono`로 공개되어 있고, React·SolidJS·React Native 통합을 공식 지원한다.

### ElectricSQL: Postgres 읽기 경로 + 에이전트 인프라로 확장

ElectricSQL은 Postgres를 소스로 하는 읽기 경로(read path) 동기화로 방향을 잡은 케이스다. 서버의 진실은 Postgres에 있고, 클라이언트가 필요한 부분만 로컬로 흘려보내는 모델이다. 2026년 들어 GitHub 리포의 자기소개가 "The agent platform built on sync"로 바뀌었고, 동기화 층을 AI 에이전트의 상태 관리 인프라로 쓰는 방향으로 재포지셔닝이 진행 중이다. 사람용 앱과 에이전트용 앱이 같은 Postgres를 바라보게 만든다는 그림이다.

## 그래서 무엇을 골라야 하나 — 4가지 판단 기준

1. **편집 단위가 '문서'인가?** 여러 사람이 한 캔버스·에디터를 동시에 편집한다면 문서 CRDT가 정답에 가깝다. 커서 단위 병합은 관계형 동기화로 흉내 내기 어렵다. 텍스트 편집 UI 바인딩이 필요하면 생태계가 가장 넓은 Yjs가 첫 후보다.
2. **데이터가 관계형이고 쿼리 패턴이 다양한가?** 채팅·대시보드·CRUD 앱이라면 Zero 스타일이 낫다. 화면별로 필요한 행만 동기화하므로 모바일 데이터 사용량과 초기 로드가 작아진다.
3. **변경 이력·타임트래블이 필요한가?** 감사 로그처럼 "과거 시점으로 돌아가 보기"가 제품 기능이라면 이력을 일급 시민으로 다루는 Automerge가 유리하다. 대신 문서가 커질수록 이력 관리 비용이 따라온다는 트레이드오프는 여전하다(3.0으로 많이 완화됐지만).
4. **서버 진실은 어디에 두나?** Postgres를 단일 진실원으로 유지하고 싶다면 Zero·ElectricSQL 계열이 자연스럽다. 문서 CRDT는 서버 없이 P2P로도 동작하지만, 그만큼 백엔드 아키텍처를 직접 설계해야 한다.

## 흔히 하는 실수 3가지

- **CRDT를 만능으로 생각한다.** CRDT는 동시 편집 병합을 보장할 뿐, 비즈니스 규칙(재고 차감, 잔액 검증 같은)의 무결성까지 보장하지 않는다. 규칙 검증은 여전히 서버 회로에 둬야 한다.
- **동기화 단위를 처음부터 크게 잡는다.** 문서든 쿼리든 동기화 단위가 커지면 초기 로드와 메모리가 먼저 무너진다. Automerge 3의 메모리 개선 사례가 보여주듯 이 설계는 나중에 고치기 어렵다.
- **오프라인 UX를 동기화 엔진에 맡긴다.** 충돌 병합과 "지금 오프라인입니다" 안내는 별개 문제다. 엔진을 도입해도 오프라인 상태 표시와 재접속 처리는 앱이 직접 만들어야 한다.

## 결론

- 동기화 엔진은 **문서 CRDT(Yjs·Automerge 3)**와 **쿼리 기반 관계형 동기화(Zero·ElectricSQL)** 두 진영으로 수렴했다.
- Yjs는 생태계와 에디터 바인딩, Automerge 3는 10배 이상의 메모리 절감과 내장 이력 관리가 무기다.
- Zero는 쿼리가 곧 동기화 범위가 되는 새로운 패러다임, ElectricSQL은 Postgres 읽기 경로를 에이전트 인프라로 확장 중이다.
- 선택 기준은 편집 단위(문서 vs 관계형), 이력 필요 여부, 진실원의 위치다.
- 첫 단계 추천: 지금 만들고 있는 앱의 화면 하나를 골라 "이 화면의 데이터를 문서로 표현할 수 있는가?"라고 물어보라. 그 질문에 대한 답이 진영을 정해준다.
