# OpenAI는 Git을 버리지 않고 서버만 갈아엎었다 — Pando 아키텍처 분석

2026년 11월 2일, OpenAI는 "Scaling Git at OpenAI"라는 엔지니어링 포스트에서 모노레포의 Git 백엔드를 처음부터 다시 만들었다고 발표했다. 이름은 **Pando**. 프로덕션에 들어간 지 반년이 지났지만 이번에 처음 전면 공개됐다.

흥미로운 점은 방향이다. Anthropic은 Git을 완전히 버리고 자체 버전 컨트롤 시스템 Scion을 만들었고, Cursor는 에이전트 전용 코드 포지인 Origin을 내놨다. 반면 OpenAI는 **Git 프로토콜과 클라이언트는 그대로 두고, 뒤에서 서빙하는 서버만 재설계**하는 길을 골랐다. 개발자와 Codex 에이전트는 여전히 평범한 `git push`, `git fetch`를 쓴다.

이 글에서는 Pando가 왜 필요했는지, 어떤 구조로 동작하는지, 그리고 이 결정이 Git 생태계 전체에 어떤 영향을 주는지 정리한다.

## 왜 Git 서버를 다시 만들었나

문제의 시작은 2025년 말이다. Codex가 도입되면서 한 엔지니어가 여러 작업을 동시에 돌리는 것이 일상이 됐다. 브랜치 수, 푸시 수, 머지 수가 폭발적으로 늘었고, 푸시 하나당 여러 CI 잡이 같은 커밋을 fetch하는 패턴까지 겹치면서 기존 Git 인프라가 버티지 못했다. OpenAI 발표 기준으로 모노레포의 분기별 커밋 증가율은 2024년 1분기 대비 2026년 4분기에 2,442%에 달했다. 푸시와 fetch가 느려지고 머지가 실패하면서, 신뢰성이 일부 구간에서 90% 아래로 떨어지기도 했다.

여기서 OpenAI가 던진 질문이 이 포스트의 핵심이다. "한계에 달한 것이 **Git 자체**인가, 아니면 **Git을 서빙하는 방식**인가?" 답은 후자였다. 이 판단의 근거와 구조를 이해하려면 일반적인 Git 서버가 어디서 병목인지 먼저 봐야 한다.

## 기존 Git 서버의 두 가지 가정이 병목이었다

Pando 팀은 관례적으로 당연하게 여겨지던 가정 두 개를 과감히 버렸다.

### 가정 1: 리포지토리 전체의 일관성

전통적인 Git 서버는 모든 브랜치(ref) 업데이트를 리포지토리 단위로 정렬한다. 모든 ref가 한 시점의 일관된 스냅샷을 이루도록 조율하는 것이다. 문제는 이 조율 자체가 단일 직렬화 지점이 된다는 것. 수천 명의 엔지니어와 에이전트가 동시에 push하면, 서로 전혀 관련 없는 브랜치의 push끼리도 한 대기줄에서 기다린다.

흔히 쓰이는 확장 방식 두 가지도 평가했다고 한다. 리포 복제본 간 ref 업데이트를 3단계 커밋(3PC)으로 조율하는 방식과, 공유 쓰기 로그(WAL)로 업데이트에 순서를 부여하는 방식. 둘 다 근본적으로 전역 조율 지점을 옮기기만 할 뿐 없애지는 못한다.

### 가정 2: 클라이언트마다 새 팩파일 생성

Git 서버는 fetch가 들어오면 클라이언트가 이미 가진 객체를 제외한 새 packfile(객체들을 압축해 묶은 Git의 전송 단위)을 그 클라이언트 전용으로 만들어 준다. CPU와 디스크 I/O를 많이 쓰는 작업이고, 클라이언트마다 내용이 달라 캐시도 어렵다. 읽기 트래픽이 폭증하면 서버는 팩 생성에 매몰된다.

또 하나: 서버는 push 전에 자신이 가진 모든 브랜치 목록을 광고(advertise)한다. 브랜치가 수백만 개가 되면 이 목록만으로 100 MiB를 넘는다고 OpenAI는 밝혔다.

## Pando의 설계: 인과적 일관성 + 팩파일 재사용

### 쓰기: 브랜치별 독립 조율

Pando는 리포지토리 전체 일관성 대신 **인과적 일관성(causal consistency)** 을 제공한다. 각 브랜치의 업데이트는 독립적으로 조율된다. 서로 관련 없는 브랜치의 push는 완전히 병렬로 진행되고, 같은 브랜치의 업데이트는 원자적 compare-and-swap 트랜잭션으로 엄격한 순서를 유지한다. 트레이드오프는 여러 브랜치를 동시에 읽는 클라이언트가 브랜치별로 서로 다른 시점을 볼 수 있다는 것. OpenAI의 판단은 이렇다 — 사람도 에이전트도 관심 있는 건 "한 브랜치 안의 순서"이지 전역 순서가 아니라는 것.

push가 들어오면 Pando는 팩파일을 언팩하지 않고 스트리밍하며 한 번에 검증해서 그대로 블롭 스토리지에 넣고, 새 브랜치 버전과 의존관계만 별도 메타데이터 스토어에 기록한다. 기본으로 광고하는 브랜치는 트렁크 하나뿐이라 브랜치 목록도 작게 유지된다.

### 읽기: 만들지 말고 이미 있는 바이트를 나눠줘라

fetch가 들어오면 Pando는 클라이언트가 가진 이력과 필요한 이력을 저장된 팩에 매핑하고, Git 프로토콜의 `packfile-uri` 기능으로 이미 만들어 둔 팩의 다운로드 링크를 돌려준다. 새 팩을 만들지 않고 **이미 존재하는 바이트를 재사용**한다.

배달은 **Express**라는 전용 서비스가 맡는다. 각 리전에 캐시를 두고 consistent hashing으로 라우팅하는, 사실상 CDN이다. OpenAI 발표 기준 캐시 적중률은 99%를 넘고, 표준 클라우드 VM에서 clone/fetch가 10 Gbps 링크를 포화시킨다.

### 컴팩션: LSM 트리에서 빌린 아이디어

push 하나하나가 작은 "L0" 팩을 만든다면, 하루 뒤에 뒤처진 클라이언트는 수만 개의 팩을 받아야 한다. Pando는 백그라운드 워커가 이 팩들을 **LSM 트리 컴팩션과 유사한 방식**으로 합친다. L0 팩들을 모아 기하급수적으로 크기가 커지는 cover를 만들고, 현재 모노레포는 L4까지 사용한다. 이 cover는 두 가지 역할을 한다. 압축률을 높이는 것, 그리고 ref 버전 위의 스킵 리스트처럼 동작해 fetch 협상이 로그 시간에 끝나게 하는 것. 참고로 RocksDB, LevelDB의 기반이 되는 바로 그 컴팩션 설계다.

## 숫자로 보는 결과

모두 OpenAI가 자체 모노레포에서 측정해 발표한 수치다(독립 검증은 불가능한 내부 수치라는 점은 유의하자).

- **미디언 push 지연시간 약 80% 감소** (약 5배 개선)
- **하루 거의 1 PB**의 Git 데이터 서빙 — 필요한 CPU는 "소수의 코어"
- 피크 시간당 **57 TB 이상**의 팩 전송, 그중 99% 이상이 로컬 캐시에서 서빙
- 머지 신뢰성은 90% 미만로 떨어지던 시기에서 **99.99%**로 회복
- 미디언 push 팩 크기 **20 KiB 미만**, p99도 3 MiB 미만 — 그래서 "같은 브랜치 재푸시 시 트렁크에 없는 것을 전부 다시 보낸다"는 비용이 감수할 만했던 것

## 에이전트가 에이전트 인프라를 지었다

Pando의 탄생 과정도 이 시대의 단면이다. OpenAI에 따르면 핵심 아키텍처는 엔지니어 1명이 설계하고, 구현은 Codex 에이전트 팀이 Rust로 수행했으며, 설계부터 프로덕션까지 **약 10주**가 걸렸다. 2026년 4월에 프로덕션 트래픽이 시작됐다.

검증 방식도 이례적이다. 표준 Git 대비 적합성 테스트, 경쟁 상태를 잡기 위한 결정론적 시뮬레이션 테스트, 에이전트가 Lean과 TLA+로 작성한 형식 명세로 만든 "Pando의 이론", 그리고 상시 에이전트 레드팀. 마이그레이션은 기존 시스템 앞에 읽기/쓰기 프록시로 시작해 양쪽을 동기화하며 단계적으로 옮기는 방식이었다.

## 오픈소스 Git으로 돌아가는 것들

Pando 자체는 내부 시스템이지만(OpenAI는 "공유할 방법을 검토 중"이라고만 밝혔다), 클라이언트 쪽 개선은 공개돼 있다. [github.com/openai/git](https://github.com/openai/git) 리포에서 확인할 수 있고, 일부는 이미 Git 업스트림에 반영됐다.

- 독립적인 팩의 **병렬 다운로드 및 인덱싱**
- **explicit haves** — 서버가 브랜치 tip을 별도로 알려줘 클라이언트가 `--force-with-lease`로 트렁크 기준 push를 안전하게 만드는 기능
- packfile-uri 전송의 tracing, 중단된 전송 정리, 재개 처리

흥미로운 건 `packfile-uri` 자체다. 이 기능은 2019년 Google 엔지니어가 제안했지만 서버 측 구현은 오랫동안 실험적 단계에 머물렀고, 대규모 실전 사용 사례가 없었다. Pando가 사실상 이 기능의 최대 스트레스 테스트가 된 셈이다.

실제로 openai/git 빌드를 써보려면:

```bash
git clone https://github.com/openai/git.git
cd git && make -j8 && sudo make install
# 병렬 팩 다운로드가 활성화된 git build
```

그리고 브랜치 안전 푸시는 이미 표준 Git에 있는 기능이니 팀에서 습관화할 만하다:

```bash
# 브랜치 tip이 내가 본 시점 이후 움직였으면 push 거부
git push --force-with-lease=refs/heads/feature:$(git rev-parse HEAD) origin feature
```

## 업계 전체가 같은 방향으로 간다

Pando는 혼자가 아니다. 세 회사가 각기 다른 답을 냈는데, 스펙트럼으로 보면 이해가 쉽다.

| 회사 | 접근 | Git 호환성 |
|------|------|-----------|
| **OpenAI** | Pando — Git 프로토콜 유지, 서버만 재설계 | 완전 호환 |
| **GitHub** | Git 스토리지와 컴퓨트 분리 재구축 (2026년 10월 발표, CPU 400만 코어 증설) | 완전 호환 |
| **Cursor** | Origin — 에이전트를 위한 코드 포지 (얼리 베타, `git clone/push`는 표준 Git 사용) | 상위 호환 |
| **Anthropic** | Scion — Git을 버리고 자체 VCS, 5개월 만에 완전 마이그레이션 | 비호환 |

Anthropic의 Scion 포스트는 Pando와 좋은 대조가 된다. CI만 하루 2,500만 번의 체크아웃을 처리하다 보니 "오프라인 분산 작업에 최적화된 Git의 속성이 확장을 방해한다"고 판단했고, Google의 Piper와 Meta의 Sapling의 교훈을 참고해 항상 온라인인 에이전트 전제로 설계했다. 다만 Anthropic 스스로 "Scion은 수만 명의 엔지니어나 대규모 에이전트 군집이 아니면 쓸 이유가 없다"고 못박았다. 반면 GitHub는 "Git 서버가 Git 클라이언트와 같은 방식으로 동작해야 할 필요는 없다"며 서버 아키텍처 혁신이라는 Pando와 같은 결론에 도달했다.

## 우리 팀에 남는 교훈

Pando는 대부분의 팀이 직접 쓸 수 없는 시스템이지만, 설계 교훈은 어디든 적용된다.

- **병목의 위치를 정확히 진단하라.** OpenAI는 "Git이 한계"가 아니라 "Git 서빙 방식이 한계"라고 진단했고, 그래서 20년 된 워크플로우를 지킬 수 있었다. 도구를 바꾸기 전에 프로토콜과 구현을 분리해서 생각해보자.
- **강한 일관성은 비용이다.** 리포지토리 전체 일관성을 포기하고 브랜치별 인과적 일관성만 유지해도, 대부분의 실제 워크로드에서는 문제가 없다. "무엇을 일관되게 유지할지"는 선택 가능한 설계 변수다.
- **읽기 확장의 답은 '생성하지 않기'다.** 클라이언트마다 새로 만들지 말고, 불변(immutable)한 덩어리를 캐시하고 그 링크를 나눠줘라. CDN이 20년 동안 증명한 패턴을 Git에 적용한 것이다.
- **에이전트 시대의 인프라는 에이전트가 만든다.** 설계 1명 + 에이전트 구현 팀 + 형식 명제 검증의 조합이 10주 만에 페타바이트급 시스템을 만들었다. 소규모 팀일수록 이 패턴의 레버리지가 크다.

AI 코딩 에이전트가 커밋을 몇 배로 늘리는 시대에, 소스 컨트롤 인프라는 다음 병목으로 떠올랐다. OpenAI의 대답은 의외로 보수적이었다 — Git을 버리는 게 아니라, Git을 위해 서버를 다시 쓰는 것. 그리고 그 과정에서 나온 개선들이 openai/git을 통해 업스트림으로 올라가고 있으니, 이 실험의 수혜자는 OpenAI만이 아닐 것이다.
