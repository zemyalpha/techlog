# 맥에서 로컬 LLM 속도는 메모리 대역폭이 결정한다

"맥북에서 30B 모델 돌리면 몇 tok/s 나올까?"라는 질문은 커뮤니티마다 답이 제각각이다. 같은 M4 Pro라도 RAM 용량, 양자화, 엔진(llama.cpp vs MLX)에 따라 두 배 이상 차이가 난다. 그런데 2026년 현재 공개된 벤치마크를 모아 보면 규칙이 꽤 명확하다. **토큰 생성(디코드) 속도는 GPU 코어 수가 아니라 메모리 대역폭이 결정하고, 나머지 변수는 이 Ceiling에 얼마나 가까이 가느냐의 문제다.** 이 글에서는 그 공식을 세우고, 실측 데이터가 공식과 얼마나 맞는지 검증한 뒤, 내 맥에서 어떤 모델을 돌릴지 판단하는 기준을 정리한다.

## 1. 왜 디코드는 메모리 바운드인가

LLM이 토큰을 하나 생성할 때는 모델 가중치 전체를 메모리에서 한 번 읽는다. 배치 크기 1인 인터랙티브 사용에서는 매 토큰마다 이 읽기가 반복되므로, 속도의 상한은 단순하다:

```
tok/s (이론 상한) = 메모리 대역폭 (GB/s) ÷ 모델 파일 크기 (GB)
```

Q4로 양자화한 8B 모델(약 4.5GB)을 614GB/s인 M5 Max에서 돌리면 이론 상한이 약 136 tok/s다. 실측은 보통 이 값의 60~80% 수준에 도달한다. llama.cpp 프로젝트가 유지하는 Apple Silicon 공식 벤치마크 스레드(discussion #4167)의 데이터를 분석한 Backend Roadmap의 검증 결과도 같은 결론이다. 측정치는 어떤 칩에서도 `대역폭 ÷ 파일 크기`를 넘지 않았고, 대역폭이 빠른 칩일수록 상한 대비 효율은 오히려 낮아지는(45~86% 사이) 패턴이 나타났다. 모델이 작고 메모리가 빨라질수록 어텐션·역양자화·동기화 같은 비(非)스트리밍 비용이 차지하는 비중이 커지기 때문이다.

GPU 코어 수는 여기서 거의 무관하다. llama.cpp 벤치마크에서 M2 Ultra의 60코어와 76코어 GPU의 F16 생성 속도는 각각 39.86, 41.02 tok/s로 사실상 동일했다. 같은 800GB/s를 공유하기 때문이다. 반면 프롬프트 처리(prefill)는 계산 바운드라 GPU 코어 수와 컴퓨트 파워를 그대로 반영한다. M5 세대는 프리필에서 특히 강해서, M5 Max 40코어는 7B F16 프리필에서 3,158 tok/s로 M4 Max(922 tok/s)의 3배 이상을 기록했다.

## 2. 칩별 대역폭 — 2026년 11월 기준 요약

Apple 공식 스펙과 llama.cpp 벤치마크 테이블을 교차 정리하면:

| 칩 | 대역폭 | Llama-2-7B Q4_0 생성 (tok/s) |
|---|---|---|
| M1 | 68 GB/s | 14.2 |
| M1 Max | 400 GB/s | 61.2 |
| M2 Ultra | 800 GB/s | 94.3 |
| M4 Max | 546 GB/s | 83.1 |
| M5 | 154 GB/s | 31.9 |
| M5 Max | 614 GB/s | 119.9 |
| M5 Ultra | 1.2 TB/s | 179.1 |
| M6 | 170 GB/s | 35.7 |

(생성 속도 출처: llama.cpp discussion #4167, 커밋 c1d0e7a 기준 측정값)

2026년에 새로 들어온 두 칩의 위치가 흥미롭다. M6(2026년 8월 발표)는 베이스 칩으로는 처음으로 170GB/s를 제공해 M5 대비 10% 빨라졌지만, Max급과는 여전히 3.6배 이상 격차가 있다. 반면 M5 Ultra는 최초의 쿼드다이 UltraFusion 설계로 1.2TB/s를 달성했는데, 이는 M3 Ultra보다 50% 높은 수치다. "맥 미니 M6로 로컬 LLM 돌리기"보다 "중고 M1/M2 Max"가 디코드 속도 자체는 더 빠를 수 있다는 얘기고, 이런 판단은 대역폭 표 한 장이면 된다.

주의할 점 하나: 통합 메모리라도 GPU가 전체 RAM을 자유롭게 쓰진 못한다. F16 7B 모델(12.55GB)이 베이스 칩에서 돌아가지 않는 이유는 `recommendedMaxWorkingSetSize` 제한 때문이다. macOS 15 이상에서는 다음으로 상한을 올릴 수 있다(mlx-lm 문서에도 안내돼 있다):

```bash
# 예: GPU가 쓸 수 있는 wired memory를 96GB로 상향
sudo sysctl iogpu.wired_limit_mb=98304
```

## 3. 공식에 MoE라는 예외를 더하면 진짜 그림이 나온다

위 공식에는 숨은 가정이 하나 있다. "모델 파일 전체를 매 토큰마다 읽는다"는 것. 하지만 **MoE(Mixture of Experts) 모델은 토큰마다 활성 파라미터만 읽으므로 분모가 급격히 줄어든다.** 이게 2026년 로컬 LLM 선택의 핵심이다.

Qwen3.5-35B-A3B(총 35B, 활성 약 3B)를 M5 Max에서 돌린 실측을 보자:

- llama.cpp, Q4_K_M: **94.1 tok/s** (llm-bench 프로젝트)
- 같은 하드웨어에서 Qwen3.5-9B Dense(활성 9B): **75.9 tok/s**
- Qwen3.5-122B-A10B(총 122B, 활성 10B, Q4_K_M): **42.9 tok/s**
- Qwen2.5-72B Dense(Q6_K): **7.9 tok/s**

총 파라미터가 3.5배 많은 122B MoE가 72B Dense보다 5배 이상 빠르다. 매 토큰 읽는 양(활성 파라미터)이 10B vs 72B로 차이 나기 때문이다. llm-bench의 결론도 동일했다. 35B-A3B MoE는 네 플랫폼(M5 Max, RTX 3090×2, DGX Spark, Ryzen AI MAX 395) 모두에서 9B Dense를 18~78% 앞질렀고, **대역폭이 낮은 하드웨어일수록 MoE의 이점이 컸다.** MoE의 전문가 선택이 통합 메모리에서 PCIe 병목 없이 이뤄진다는 점은 Apple Silicon에 특히 유리하게 작동한다.

정리하면 실전 공식은 이렇게 바뀐다:

```python
# dense: 파일 전체, MoE: 활성 파라미터 비율만 읽음
active_gb = total_gb * (active_params / total_params)  # 대략적 근사
toks_upper = bandwidth_gbps / active_gb
expected = toks_upper * 0.5   # 효율 50~70% 가정, 직접 측정으로 보정
```

MoE는 라우팅 오버헤드 때문에 효율 계산이 dense와 다르고(공유 가중치·게이트 등 분모 근사가 필요) 커뮤니티 분석에서도 MoE 계층은 dense 계층보다 라우팅 비용이 2~3배 크다고 측정되니, 위 근사는 어디까지나 첫 추정으로 쓰고 실측으로 교정하자.

## 4. 엔진 선택: llama.cpp가 만능은 아니다

같은 모델, 같은 맥에서도 엔진에 따라 크게 갈린다. Mac tok/s 검증 프로젝트가 공개 측정 92건을 모아 분석한 결과, llama.cpp 대비 MLX가 보통 1.3~1.8배 빠른 것으로 집계됐다. 대표적인 사례:

- M4 Max 128GB, Qwen3.5-35B-A3B: MLX 130.2 vs llama.cpp 72.4 tok/s (1.80배)
- M5 Max, Qwen3.5-27B 4bit 동급: MLX 31.6 vs llama.cpp Q4_K_M 24.3 tok/s (1.3배, 양자화 규격 맞춘 보정 비교)

M5 Max처럼 대역폭이 높아지면 llama.cpp의 스케일링이 좋아져 격차가 줄어든다는 커뮤니티 후기도 있다. 방향은 간단하다. **지원되는 모델이면 MLX 우선, 아니면 llama.cpp(GGUF).** 다만 2026년 4~5월경 기준 Ollama/LM Studio의 MLX 백엔드는 신규 모델 지원이 늦어 Qwen3.5·Gemma 4 일부가 GGUF로만 돌아가는 경우가 있었으니, 쓰려는 모델의 MLX 지원 여부를 먼저 확인해야 한다.

M5 세대에서는 한 단계 더 나간 선택지도 등장했다. M5의 모든 GPU 코어에 탑재된 Neural Accelerator를 Metal 4 텐서 API로 직접 쓰는 네이티브 런타임 BaseRT가 그것. M5 Pro에서 15개 모델 설정을 측정한 논문(arXiv 2607.19438)에 따르면 llama.cpp 대비 최대 6.4배, MLX 대비 최대 3.9배의 프리필 처리량을 보였고 디코드도 llama.cpp 대비 1.02~1.75배 앞섰다. 다만 디코드는 메모리 바운드라 신경가속기의 이점이 제한적이라는 점을 논문 스스로 명확히 밝히고 있고, 아직 프리프린트 단계 연구 결과라는 점은 감안하자.

## 5. 실전 체크리스트

**첫째, 컨텍스트 길이의 절벽을 조심하라.** M4 Pro 48GB에서 24GB급 MoE 모델을 돌린 실측에서 16K 컨텍스트까지는 27~28 tok/s가 나오다가 32K에서 9.3 tok/s로 떨어지고 첫 토큰까지 85초가 걸렸다. KV 캐시가 가용 메모리를 넘어 스와핑이 시작되는 지점이 있다. 모델 크기 + 예상 KV 캐시를 RAM 예산에 미리 넣어야 한다.

**둘째, 직접 측정하는 데는 5분이면 된다.** 어떤 블로그 수치보다 내 맥의 실측이 우선이다:

```bash
brew install llama.cpp
llama-bench -hf ggml-org/Llama-2-7B-GGUF:Q4_0 -p 512 -n 128 -ngl 99
# pp512 = 프리필, tg128 = 생성 tok/s
```

llama.cpp 벤치마크 스레드는 같은 커밋(c1d0e7a)에서 측정한 표를 유지하므로, 내 결과를 표와 바로 비교할 수 있다. 벤치마크 수치는 빌드 시점에 따라 달라진다(같은 M2 Ultra에서 2023년 빌드 94.27 → 2026년 빌드 125.21 tok/s) — **수치를 인용할 때는 반드시 빌드 버전을 함께 적자.**

**셋째, 프리필과 디코드를 분리해서 평가하라.** 챗봇처럼 긴 프롬프트를 한 번 넣고 답을 길게 받는 워크로드는 프리필이 지배한다. M5 Max에서 35B MoE의 프리필은 2,300~2,800 tok/s로 dense 27B(400~500 tok/s)의 5배 이상이다. 이런 용도라면 MoE의 이점이 디코드 차이보다 훨씬 크다.

## 결론

- 디코드 속도의 상한은 `대역폭 ÷ 토큰당 읽는 양`이고, 실측은 그 45~86%에 도달한다. 칩 스펙표만 있으면 구매 전에 속도를 예측할 수 있다.
- 2026년의 승자는 총 파라미터가 아니라 활성 파라미터다. M5 Max에서 122B MoE가 41~43 tok/s로 72B Dense(7.9 tok/s)의 5배 이상 빠르다.
- M6(170GB/s)은 대역폭 기준 베이스급이고, 프리필 성능은 M5 세대부터 세대차가 벌어진다. 대역폭 표를 보고 용도(따뜻한 챗 vs 긴 문서 요약)에 맞는 칩을 고르자.
- 엔진은 MLX 우선, 폴백 llama.cpp. BaseRT 같은 M5 신경가속기 런타임은 프리필에서 큰 이득을 보이지만 아직 초기 단계다.
- 어떤 수치든 빌드 버전과 출처를 붙여서 비교하라. llama-bench 5분 직접 측정이 가장 확실한 데이터다.

첫 단계는 간단하다. 오늘 `llama-bench`를 한 번 돌려서 내 맥의 pp512/tg128을 알아두는 것. 그 숫자가 있으면 위 공식의 효율 보정치를 본인 하드웨어에 맞게 고정할 수 있고, 이후 모든 모델 선택이 계산 가능해진다.
