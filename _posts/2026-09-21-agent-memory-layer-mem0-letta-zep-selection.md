# AI 에이전트는 왜 3일 만에 나를 잊어버리는가 — Mem0·Letta·Zep 메모리 레이어 선택 가이드

챗봇을 만들어 운영해 본 사람이라면 누구나 겪는 순간이 있다. 지난주에 분명히 "저는 커피를 안 마셔요"라고 말했는데, 오늘 다시 커피를 권한다. 버그가 아니다. LLM의 컨텍스트 윈도우는 세션 사이에 유지되지 않으며, 긴 대화 전체를 매번 다시 넣는 풀컨텍스트 방식은 비용과 지연 시간 때문에 현실적으로 못 쓴다. Mem0 팀이 논문에서 실측한 바에 따르면, 전체 대화 이력을 매번 처리하는 방식은 단일 상위 모델 시스템 대비 p95 지연 시간이 크게 늘고 토큰 비용도 수배에 달한다(arXiv 2504.19413).

그래서 2025~2026년 에이전트 개발의 화두는 "더 큰 컨텍스트"가 아니라 **외부 메모리 레이어**다. 컨텍스트 안에 다 담지 말고, 필요한 순간에 필요한 기억만 꺼내 주는 계층을 에이전트 옆에 두는 접근이다. 이 글에서는 현재 실무에서 가장 많이 쓰이는 세 가지 오픈소스 계열 솔루션 — Mem0, Letta(구 MemGPT), Zep — 의 아키텍처 차이와 검증된 성능 수치, 그리고 "어떤 문제에 무엇을 골라야 하는가"를 정리한다.

## 메모리는 하나가 아니다 — 먼저 종류를 구분하라

프레임워크를 비교하기 전에, "메모리"라는 단어가 최소 네 가지 다른 것을 가리킨다는 점을 짚어야 한다. 비교 글 대부분의 논쟁은 사실 이 분류를 섞어서 발생한다.

- **단기 기억**: 현재 프롬프트 + 최근 N턴. 모델과 오케스트레이션의 속성이며, 어떤 프레임워크도 대신 해결해 주지 않는다.
- **의미 기억(semantic)**: 시간이 흘도 변하지 않는 사실. "사용자는 미터법을 선호한다", "본사는 암스테르담에 있다" 같은 것.
- **에피소드 기억(episodic)**: 특정 시점에 일어난 일. "화요일에 사용자가 결제 플로우가 깨졌다고 말했고, 수요일에 해결됐다" 같은 것. 핵심은 "수요일 아침 기준으로 이 사실은 참였는가?"라는 질문에 답할 수 있어야 한다.
- **절차 기억(procedural)**: "어떻게 하는지". 성공한 도구 호출 시퀀스나 워크플로. 2026년 현재 네 프레임워크 모두 이 영역이 가장 취약하다.

이 분류에서 보면 세 솔루션의 차이가 선명해진다. **Mem0는 의미 기억에, Zep는 에피소드·시간 추론에, Letta는 에이전트 자체를 상태 저장 서비스로 만드는 것에 최적화돼 있다.**

## 세 가지 아키텍처

### Mem0 — 기존 에이전트에 붙이는 벡터 추출형 메모리 레이어

Mem0의 접근은 가장 단순하고 그래서 채택 장벽이 낮다. 새 메시지가 도착하면 추출 단계에서 원자적 사실을 뽑아내고, 각 사실을 임베딩해 `user_id`, `agent_id` 같은 구조화 메타데이터와 함께 저장한다. 검색 시 의미 유사도, BM25 키워드, 엔티티 매칭을 병렬로 계산해 하나의 랭킹으로 융합한다. 요약하면 **구조화된 메모 + 하이브리드 검색**이다.

실무에서 가장 매력적인 부분은 통합 코드의 짧음이다. 기존 에이전트 루프를 고칠 필요 없이 몇 줄을 추가한다:

```python
from mem0 import Memory

m = Memory()  # 오픈소스: 로컬 벡터스토어 기반

# 대화가 끝날 때마다 사실을 추출·저장
m.add("사용자가 커피를 마시지 않고 디카페인만 찾는다고 함",
      user_id="user_123")

# 다음 세션 시작 시 관련 기억만 꺼내 프롬프트에 주입
relevant = m.search("이 사용자의 음료 선호", user_id="user_123")
```

성능은 논문과 PyPI 문서로 이중 확인된다. Mem0 논문(arXiv 2504.19413, 2025년 4월)은 LOCoMo 벤치마크에서 OpenAI의 메모리 시스템 대비 LLM-as-a-Judge 지표 기준 26% 상대적 개선을 보고했고, 풀컨텍스트 방식 대비 p95 지연 91% 감소, 토큰 비용 90% 이상 절감을 측정했다. 2026년 4월 알고리즘 업데이트(PyPI 패키지 v2.x)에서는 단일 패스 추출과 엔티티 링킹을 도입해 LoCoMo 71.4→92.5, LongMemEval 67.8→94.4로 자체 벤치마크를 갱신했다고 밝혔다. 단 한 가지 주의: 이 수치는 **관리형 플랫폼 기준**이며 공식 문서도 오픈소스 SDK는 "방향성은 비슷하지만 동일한 숫자는 아니다"라고 명시하고 있으니, 도입 시 자체 워크로드로 재검증해야 한다.

### Letta — 에이전트가 곧 메모리인 상태 저장 런타임

Letta(구 MemGPT)는 방향 자체가 다르다. Mem0가 "라이브러리를 가져다 쓰는" 모델이라면, Letta는 **에이전트가 Letta 위에서 상태 저장 서비스로 살아있는** 런타임이다. MemGPT 논문에서 시작된 메모리 계층 구조 — 에이전트가 스스로 편집하는 코어 메모리 블록과 대용량 아카이브 저장소 — 가 프레임워크의 존재 이유다.

```bash
npm install -g @letta-ai/letta-code
letta          # 대화형 터미널 UI
letta server   # 로컬/셀프호스팅 앱 서버
```

에이전트가 "환불 분쟁을 어떻게 해결했는지"를 스스로 코어 메모리 블록에 적어 두면, 다음 세션의 같은 에이전트가 이를 상속받는다. 절차 기억에 가장 가까운 형태를 제공하는 셈이다. GitHub에서 24,800개 이상의 스타를 받은 Apache 2.0 프로젝트로, macOS/윈도우/리눅스 데스크톱 앱과 Slack·Telegram·Discord 채널 연동, SDK를 통한 임베딩까지 지원한다. 트레이드오프는 명확하다. 기존 오케스트레이션(LangGraph, 자체 루프 등) 위에 얹는 것이 아니라 에이전트 실행 자체를 Letta에 맡기는 구조라, 도입은 프로젝트 초기에 하는 편이 훨씬 싸다.

### Zep — 시간 지식 그래프로 "언제 참이었는지"에 답한다

Zep의 차별점은 시간(temporal)이다. 핵심 엔진인 Graphiti는 대화와 비즈니스 데이터로부터 엔티티-관계 그래프를 만들되, **모든 사실(edge)에 유효 시작/종료 시점을 기록한다**. 새 데이터가 이전 사실을 무효화하면 그 시점이 엣지에 저장되므로, "지난 수요일 아침에 이 사용자의 배송지는 어디였나?" 같은 질문에 그래프 조회로 답한다. 챗 메모리라기보다 시간이 흐르는 지식 그래프에 가깝다.

클라우드 SDK는 세 줄로 요약된다:

```python
import os
from zep_cloud.client import Zep

client = Zep(api_key=os.environ["ZEP_API_KEY"])
# thread에 메시지를 추가하고, 다음 턴에서 그래프로부터
# 조립된 컨텍스트 블록을 200ms 미만으로 받아온다
```

공식 문서는 서브-200ms 검색을 내세우고, Zep 논문(arXiv 2501.13956)은 MemGPT 팀이 자체 평가 지표로 삼았던 Deep Memory Retrieval 벤치마크에서 94.8% vs 93.4%로 MemGPT를 앞섰고, 기업 시나리오에 가깝다는 LongMemEval에서는 정확도 최대 +18.5%p, 응답 지연 90% 감소를 보고했다. 밑에 깔린 Graphiti 자체가 별도 오픈소스(Apache 2.0, GitHub 31,000 스타 수준)로 공개돼 있어 셀프호스팅 경로도 열려 있다. 단 사실마다 엣지를 만드는 그래프 구축 방식 특성상, 단순 선호 저장보다는 트랜잭션 이력·고객 상태 변화처럼 시간 축이 중요한 워크로드에서 투자 대비 효과가 크다.

## 선택 기준 — 세 개의 질문

세 솔루션의 문서를 읽고 나면 결국 마케팅 문구가 아니라 세 개의 질문으로 귀결된다.

**1. 이미 돌아가는 에이전트에 기억만 붙이는가?**
→ Mem0. 라이브러리 형태라 기존 런타임을 바꿀 필요가 없고, 호스팅/셀프호스팅을 모두 지원한다. "지난달 대비 가장 빠른 경로"가 목표라면 이게 답이다.

**2. 에이전트 자체가 상태를 가지고 자기 개선해야 하는가?**
→ Letta. 에이전트를 서비스처럼 주소 지정(addressable)하고, 코어 메모리를 스스로 편집하게 하려면 Letta의 런타임 모델이 필요하다. 단 기존 오케스트레이션과 병행 설계는 피하고 초기부터 Letta로 시작할 것.

**3. "언제 참이었는지"가 중요한가?**
→ Zep. 계약 변경, 주문 상태, 고객 이력처럼 사실이 시간에 따라 무효화되는 도메인이라면 temporal 그래프가 지불하는 구조적 대가를 할 만하다.

## 흔히 하는 실수 세 가지

- **메모리 레이어를 벡터 DB로 착각한다.** 벡터 검색은 세 솔루션 모두의 부품일 뿐이다. 사실 추출, 충돌 처리, 시간 인덱싱이 본체이며, pgvector에 임베딩 몇 개 넣는 것과는 해결하는 문제가 다르다.
- **벤치마크 숫자를 있는 그대로 믿는다.** Mem0의 2026년 수치는 관리형 플랫폼 기준이고, Zep의 DMR 수치는 Zep 팀이 측정했으며, Letta는 DMR 벤치마크를 만든 팀 자체다. 각자 자기가 유리한 지표를 내세운다. 도입 전에 자체 대화 로그로 2주간 A/B 평가하는 것이 어떤 벤치마크보다 정확하다.
- **절차 기억을 프레임워크에 맡긴다.** "어떻게 했는지" 기억은 2026년 현재 어느 솔루션도 일급으로 다루지 않는다. 성공한 도구 호출 시퀀스는 직접 저장하고 Few-shot 예시로 주입하는 별도 파이프라인을 갖추는 편이 안전하다.

## 결론

- 에이전트 장기 기억은 컨텍스트 확장의 대안이 아니라 필수 보완이며, 2026년 현재 실전 선택지는 Mem0(벡터 추출형 레이어), Letta(상태 저장 런타임), Zep(시간 지식 그래프)로 수렴해 있다.
- 검증된 수치만 보더라도: Mem0는 풀컨텍스트 대비 토큰 비용 90%+ 절감(논문), Zep는 LongMemEval 정확도 최대 +18.5%p·지연 90% 감소(논문), Letta는 DMR 벤치마크 원조이자 24.8k 스타의 런타임 생태계.
- 첫 단계 추천: 기존 에이전트가 있다면 Mem0를 하루 만에 붙여 보고, 사용자별 사실 충돌이 실제로 발생하는지 관찰하라. 시간 추론 필요가 확인되면 그때 Zep로, 에이전트 아키텍처를 새로 짜는 프로젝트라면 Letta를 검토한다.
