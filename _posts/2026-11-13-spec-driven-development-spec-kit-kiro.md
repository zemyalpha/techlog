# AI 코딩 에이전트가 코드를 쓰는 시대, 검토할 것은 스펙이다 — Spec Kit·Kiro 스펙 주도 개발 실전 가이드

에이전트에게 기능을 한 문장으로 요청하면 몇 초 만에 코드가 나온다. 문제는 그다음부터다. "돌아는 가는데 팀이 원하던 것과 다른" 코드가 수백 줄 쌓이고, 나중에 무엇이 근거로 작성됐는지 아무도 설명하지 못한다. AI 보조 개발의 고통은 이제 코드 생성 속도가 아니라, 생성의 근거를 통제하지 못하는 데서 온다.

이 지점에서 주목받는 접근이 **스펙 주도 개발(Spec-Driven Development, SDD)**이다. 스펙을 버전 관리하고 검토하는 1차 산출물로 삼고, 코드는 스펙으로부터 생성되는 파생물로 취급한다. 2026년 들어 GitHub가 Spec Kit를, AWS가 Kiro를 정식으로 밀고 있어 단순한 유행 이상의 흐름으로 자리 잡는 중이다. 이 글에서는 SDD의 개념적 틀과 실전 워크플로우, 도구 선택 기준을 공식 문서 기반으로 정리한다.

## 스펙 주도 개발은 무엇이고, 바이브 코딩과 뭐가 다른가

SDD의 핵심 발상은 단순하다. 채팅창에서 대화로 기능을 주문하고 결과물을 그대로 받아들이는 바이브 코딩과 달리, **코드가 생성되기 전에 요구사항을 문서로 고정하고 그 문서를 검토 체크포인트로 쓰는 것**이다.

일반적으로 스펙은 세 층위로 구성된다.

1. **요구사항(Requirements)** — 기능이 무엇을 해야 하는지. 사용자 스토리나 자연어 수용 기준 형태
2. **기술 설계(Technical Design)** — 어떻게 만들지. 컴포넌트, 데이터 모델, API 표면
3. **태스크 분해(Task Breakdown)** — 스펙을 독립적으로 검토 가능한 구현 단위로 쪼갠 것

AI 에이전트는 이 스펙에 대해 태스크 단위로 구현한다. 스펙이 변경되면 코드를 다시 생성하면 되므로, 스펙이 진짜 원본(source of truth)이 되고 코드는 컴파일 결과물에 가까워진다.

2026년 1월 30일 arXiv에 공개된 논문 "Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants"(Deepak Babu Piskala, AIWare 2026 제출)는 이 흐름을 스펙의 엄격함에 따라 세 수준으로 정리한다.

- **Spec-first** — 구현 전에 스펙을 먼저 쓰되, 코드는 여전히 사람이 직접 다듬는다
- **Spec-anchored** — 스펙을 구현의 닻으로 삼아 에이전트가 코드를 생성하고, 사람은 스펙 준수 여부를 검증한다
- **Spec-as-source** — 스펙이 사실상 원본 코드 역할을 하고, 코드는 완전히 파생 산출물이 된다

논문의 결론이 실용적인 이유는 여기서 "언제 SDD가 가치가 있고 언제 과한지"에 대한 판단 기준을 제공하기 때문이다. 모든 프로젝트가 세 번째 수준까지 갈 필요는 없다.

## GitHub Spec Kit 실전: 기존 에이전트 위에 얹는 스펙 워크플로우

GitHub의 Spec Kit는 오픈소스(MIT 라이선스) CLI와 템플릿 모음으로, 이미 쓰고 있는 코딩 에이전트 위에 specify → plan → tasks → implement 워크플로우를 얹는 방식이다. GitHub Copilot, Claude Code, Cursor, Gemini CLI 등을 지원한다.

설치는 PyPI의 specify-cli로 한다(uv 필요).

```bash
uv tool install specify-cli
specify init my-project --integration copilot
cd my-project
```

설치 후에는 터미널 명령이 아니라 에이전트 챗에서 스킬을 하나씩 호출하는 방식으로 진행한다. 2026년 11월 현재 공식 문서 기준 풀 패스는 다음과 같다.

```text
/speckit-constitution  # 프로젝트 원칙을 한 번 정의 (보안 원칙, 아키텍처 기준 등)
/speckit-specify       # 자연어 설명에서 기능 스펙 생성
/speckit-clarify       # 모호한 부분을 질문으로 좁혀 스펙에 반영
/speckit-plan          # 기술 스택·아키텍처 설계 산출물 생성
/speckit-checklist     # 스펙 검증용 품질 체크리스트 생성
/speckit-tasks         # 설계를 구현 가능한 태스크로 분해
/speckit-analyze       # 구현 전 위험 요소 분석
/speckit-implement     # 태스크 단위로 코드 구현
/speckit-converge      # 스펙과 코드의 일치 여부 정합
```

작은 기능이라면 specify → plan → tasks → implement의 짧은 경로로 충분하고, 운영 기능이라면 clarify, checklist, analyze를 품질 게이트로 끼워 넣는 것이 권장된다.

눈여겨볼 디테일이 하나 있다. Spec Kit는 현재 작업 중인 기능을 Git 브랜치가 아니라 `.specify/feature.json`에 기록된 기능 디렉터리로 추적한다. 브랜치를 체크아웃해도 활성 기능이 바뀌지 않으며, 옵트인 Git 확장을 켜면 `001-feature-name` 형태의 번호 붙은 브랜치로 작업을 정리할 수 있다. 스펙의 단위가 커밋이 아니라 "기능"이라는 설계 의도가 드러나는 부분이다.

Spec Kit의 강점은 벤더 종속이 없다는 것이다. 산출물은 그냥 리포지토리 안의 마크다운 파일이고, 에이전트는 무엇을 쓰든 바꿀 수 있다. 반대로 약점은 규율이 선택 사항이라는 점이다. 바쁜 날 `/speckit-specify`를 건너뛰고 바로 프롬프트를 날리는 것을 막아주지 않는다.

## AWS Kiro: 스펙을 강제하는 IDE

AWS의 Kiro는 반대편 끝에서 출발한다. VS Code를 포크해 만든 IDE로, **기획 단계를 코드 생성보다 앞에 두는 것을 플로우 자체에 강제**한다.

Kiro에서 기능을 만들면 다음 순서로 진행된다.

1. 의도를 평문으로 기술한다
2. Kiro가 `requirements.md`, `design.md`, `tasks.md`를 **EARS 표기법**(Easy Approach to Requirements Syntax)으로 생성한다
3. 사람이 스펙을 검토하고 수정·승인한다
4. 승인된 스펙에 따라 코드가 단계별로 구현되며, 파일 변경이 스펙 요구사항으로 역추적된다

여기에 저장 이벤트로 린트를 돌리는 Hooks, `.kiro/steering/` 디렉터리의 프로젝트 코딩 표준 파일, 네이티브 MCP 연동이 더해진다.

가격은 2026년 11월 현재 공식 페이지 기준으로 Free(월 50 크레딧, 오픈 웨이트 모델과 Claude Sonnet 4.5), Pro(월 $20, 1,000 크레딧), Pro+(월 $40, 2,000 크레딧), Pro Max(월 $100, 5,000 크레딧), Power(월 $200, 10,000 크레딧)이며, 추가 크레딧은 개당 $0.04다. 2인 이상 팀은 좌석당 월 $20에 500 크레딧이 포함된 풀링을 쓸 수 있다.

Kiro를 쓸지 고민하는 AWS 사용자에게 중요한 사실 하나. Amazon Q Developer는 2027년 4월 30일에 지원이 종료되며, AWS는 Kiro를 공식 후속으로 안내하고 있다. 신규 가입이 이미 막힌 상태이므로 Q 기반 워크플로우를 쓰고 있었다면 마이그레이션 계획을 세울 시점이다.

두 도구 사이에 **BMAD-METHOD**라는 세 번째 선택지도 있다. 단일 파이프라인 대신 분석가, PM, 아키텍트, 개발자 역할의 전문 에이전트 팀을 시뮬레이션해 같은 스펙-설계-구현 흐름을 단계별로 진행하는 방식으로, Spec Kit보다 프로세스에 대한 의견이 강하고 Kiro보다 개방적이다.

## 어떤 도구를 골라야 하나

| 구분 | GitHub Spec Kit | AWS Kiro | BMAD-METHOD |
|------|----------------|----------|-------------|
| 형태 | 오픈소스 CLI + 템플릿 | 완전한 IDE | 오픈소스 메서드 |
| 에이전트 | 자유롭게 선택 | Kiro 내장 | 자유롭게 선택 |
| 종속성 | 없음 (MIT) | AWS 생태계 | 없음 |
| 규율 | 선택 사항 | 플로우로 강제 | 프로세스 강함 |

기준을 단순화하면 이렇다.

- **이미 Claude Code나 Cursor 등 에이전트가 정착했고, 워크플로우만 바꾸고 싶다** → Spec Kit
- **팀 전체가 하나의 IDE에서 스펙 검토까지 끝내고 싶고, AWS 인프라를 쓴다** → Kiro
- **프로세스 역할 분리까지 실험해보고 싶다** → BMAD-METHOD

## 실패 모드: 스펙은 의식이 아니라 살아있는 문서여야 한다

SDD 도입에서 가장 흔한 실패는 스펙을 한 번 쓰고 버리는 입회 의식으로 취급하는 것이다. 실제 코드는 운영하며 계속 바뀌는데 스펙이 그대로면, 스펙은 최신 코드와 어긋나는 거짓 문서가 된다. **코드와 어긋난 스펙은 스펙이 없는 것보다 나쁘다.** 에이전트는 그 스펙을 근거로 삼아 잘못된 방향으로 코드를 계속 생성하기 때문이다.

둘째, SDD는 오버헤드가 실재한다. 요구사항 문서와 기술 설계를 검토하는 시간이 들기 때문에 주말 프로토타입에는 맞지 않는다. 앞서 소개한 논문과 실무 가이드 모두 같은 결론을 준다. 기여자가 여럿이거나, 유지보수 기간이 길거나, 구현 착수 전에 요구사항 승인이 필요한 프로젝트에서 SDD의 사전 비용이 회수된다.

셋째, 스펙의 엄격함 수준을 프로젝트에 맞춰라. 모든 것을 spec-as-source까지 밀 필요는 없다. 내부 도구라면 spec-anchored에서 멈추고, 사람이 직접 다루는 핵심 모듈은 spec-first면 충분하다.

## 결론

- SDD는 스펙을 버전 관리·검토하는 1차 산출물로, 코드를 파생물로 격상시키는 워크플로우다. 바이브 코딩의 "빠르지만 근거 없는" 문제를 검토 체크포인트로 해결한다
- GitHub Spec Kit는 MIT 라이선스 CLI로 기존 에이전트에 얹는다. `/speckit-*` 스킬 시퀀스로 스펙-설계-태스크-구현을 진행한다
- AWS Kiro는 스펙 퍼스트 IDE다. EARS 표기법으로 스펙을 생성하고 구현을 역추적한다. Amazon Q Developer는 2027년 4월 지원 종료 예정
- 스펙의 엄격함은 spec-first / spec-anchored / spec-as-source 세 수준 중 프로젝트에 맞는 지점을 고르는 것이 핵심
- 가장 흔한 실패는 스펙 부패다. 스펙이 코드를 따라가지 못하면 SDD를 접는 것이 낫다

당장 시도해볼 첫 단계는 가볍다. 진행 중인 프로젝트 하나에서 `uv tool install specify-cli`로 Spec Kit를 초기화하고, 다음에 추가할 작은 기능 하나를 `/speckit-specify`로 스펙부터 작성해보라. 기존 에이전트와 워크플로우는 그대로 둔 채, 스펙 검토라는 체크포인트 하나만 추가하는 것이다. 그 체크포인트에서 잡히는 잘못된 가정 하나가, 나중에 갈아엎게 될 수천 줄의 코드를 줄여준다.
