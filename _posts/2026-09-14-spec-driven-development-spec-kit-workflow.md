# AI 코딩 에이전트 시대, 코드 대신 스펙이 산출물이 된다

Claude Code나 Copilot Coding Agent에 "로그인 기능 만들어"라고 말하고 돌아왔을 때, 원하는 것과 다른 방향으로 수십 개 파일이 수정돼 있던 경험이 있다면 이 글의 대상 독자다. 문제는 에이전트의 능력이 아니라 **지시의 산출물이 코드라는 점**에 있다. 대화 몇 번으로 코드가 대량 생성되는 시대에는 그 코드가 "무엇을 위해 존재하는지"를 담은 문서가 오히려 희소해진다.

이 문제의식에서 2025년부터 "스펙 주도 개발(Spec-Driven Development, SDD)"이 AI 코딩의 주요 흐름으로 자리 잡았다. SDD는 새로운 발명이라기보다 오래된 아이디어의 회귀다. 스펙을 소스 오브 트루스로 삼고, 코드를 그로부터 생성·검증되는 이차 산출물로 격하시키는 방향으로 워크플로를 뒤집는 것. 2026년 2월 arXiv에 발표된 가이드 논문("Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants", arXiv:2602.00180)은 이를 체계화하며 실무자를 위한 의사결정 프레임워크를 제시한다.

## 스펙 엄격성의 3단계: 어디까지 스펙에 담을 것인가

논문이 제시하는 가장 유용한 구분은 스펙의 엄격성을 세 수준으로 나눈 것이다. 도구를 고르기 전에 자기 팀이 어느 수준에 필요한지 먼저 정하는 것이 순서다.

**1단계 — Spec-first (스펙 우선)**: 구현에 앞서 스펙을 먼저 작성하지만, 이후 개발이 진행되면 스펙과 코드가 서로 어긋날 수 있다. 스펙은 출발점이지 계약은 아니다. 프로토타입이나 빠른 탐색 단계에 적합하다.

**2단계 — Spec-anchored (스펙 고정)**: 스펙을 기준점으로 삼아 코드 변경 시 스펙과의 일관성을 검증한다. PR 리뷰에서 "스펙의 이 조항을 구현한 것인가"를 묻는 식이다. 스펙과 코드가 함께 진화하지만, 어긋나면 알림이 온다.

**3단계 — Spec-as-source (스펙=소스)**: 스펙이 곧 소스다. 코드는 스펙에서 생성된 산출물이며, 사람이 직접 편집하는 대상이 아니다. 극단적으로는 코드를 재생성해도 스펙만 보존되면 된다. 현재는 특수한 도메인(설정 생성, API 스키마 등)에서만 현실적이다.

AI 에이전트를 쓰는 대부분 팀은 1단계와 2단계 사이에 있다. "스펙을 쓴다"는 말은 같아도 어느 수준을 목표로 하는지에 따라 필요한 도구와 프로세스가 완전히 달라지므로, 이 3단계 구분은 도구 선택의 첫 질문이 된다.

## GitHub Spec Kit: specify → plan → tasks → implement

SDD를 실무에 적용하는 대표 도구는 GitHub의 **Spec Kit**이다. 2025년 첫 커밋 이후 1년 만인 2026년 8월 21일 1.0.0을 출시했고, 공식 리포 기준 13만 개 이상의 스타를 받으며 AI 코딩 도구 생태계에서 가장 빠르게 성장한 프로세스 툴킷이 됐다. 특정 에이전트에 종속되지 않고 Claude Code, Copilot, Gemini CLI 등 주요 코딩 에이전트와 함께 쓸 수 있다는 점이 채택을 넓힌 요인이다.

핵심은 네 단계 커맨드 워크플로다. 설치는 uv로 한다:

```bash
uv tool install specify-cli
specify init my-project --integration claude
cd my-project
```

프로젝트 초기화 후 에이전트 안에서 슬래시 커맨드로 프로세스를 진행한다.

**1) `/speckit.constitution` — 원칙 수립.** 기능 스펙보다 먼저 프로젝트의 헌법을 정의한다. 코드 품질 기준, 테스트 요구 수준, 일관성 규칙 등 이후 모든 스펙과 구현에 적용되는 상위 원칙이다.

```
/speckit.constitution Create principles focused on code quality,
testing standards, user experience consistency, and performance requirements
```

**2) `/speckit.specify` — 스펙 작성.** 무엇을 왜 만들지를 기술한다. 중요한 규칙은 기술 스택을 언급하지 않는 것. "SQLite를 쓰고 Vite로 빌드하고"가 아니라 "앨범은 날짜별로 묶이고, 드래그앤드롭으로 재배치할 수 있고, 앨범은 중첩되지 않는다"처럼 요구사항과 이유만 쓴다. 스펙이 구현 세부와 분리돼야 나중에 스택을 바꿔도 스펙이 살아남는다.

**3) `/speckit.plan` — 구현 계획.** 이 단계에서 기술 스택과 아키텍처를 정한다. 앞선 사례라면 "Vite + 바닐라 JS, 이미지는 업로드하지 않고 메타데이터만 로컬 SQLite에 저장" 같은 결정을 내린다. specify와 plan이 분리돼 있어 요구 변경과 구현 변경이 서로를 오염시키지 않는다.

**4) `/speckit.tasks` → `/speckit.implement` — 실행.** 계획을 검증 가능한 태스크 리스트로 쪼개고, 에이전트가 태스크를 순서대로 실행한다.

이 구조의 이점은 "무엇"과 "어떻게"의 분리다. 프롬프트 하나에 요구사항과 구현 지시를 섞어 넣으면 에이전트가 요구사항을 임의로 재해석해도 원인을 추적할 수 없다. Spec Kit에서는 스펙 파일과 계획 파일이 리포지토리에 커밋되므로, 에이전트가 엉뚱한 방향으로 가면 어느 문서의 어느 조항을 잘못 읽었는지 특정할 수 있다.

## AWS Kiro: 스펙을 작업 단위로 삼는 IDE

같은 문제에 다르게 접근하는 사례가 AWS의 **Kiro**다. Kiro는 스펙 기반 개발을 에이전틱 IDE 안에 내장한 제품으로, requirements → design → tasks로 이어지는 스펙 문서를 IDE 차원의 작업 단위(unit of work)로 다룬다. Spec Kit가 "어떤 에이전트든 쓸 수 있는 프로세스 레이어"라면, Kiro는 "스펙이 에디터 경험에 녹아든 통합 환경"이라는 대비가 성립한다. 팀이 이미 특정 에이전트로 통일돼 있다면 Spec Kit 방식이, 프로세스를 통째로 도구에 맡기고 싶다면 Kiro 방식이 자연스럽다.

## 언제 SDD가 과한가

논문이 반복해서 강조하는 점은 SDD가 만능이 아니라는 것이다. 스펙 작성 자체가 비용이므로, 다음 경우에는 더 단순한 접근이 낫다:

- **일회성 스크립트나 프로토타입** — 스펙을 쓰는 시간이 구현보다 길다. spec-first 미만은 굳이 형식화할 필요가 없다.
- **요구사항 자체가 탐색 중인 경우** — 뭘 만들지 모르는 상태에서 스펙을 고정하면 오히려 잘못된 계약을 만든다.
- **개인 단기 프로젝트** — 헌법, 스펙, 계획, 태스크의 4단계 문서는 협업과 장기 유지보수를 위한 오버헤드다. 혼자 쓰고 버릴 코드라면 프롬프트 직접 지시가 빠르다.

반대로 SDD의 효용이 커지는 경우는 명확하다. 여러 에이전트(또는 여러 사람)가 같은 리포지토리에서 작업할 때, 스펙이 없으면 각자의 컨텍스트가 전부 프롬프트 히스토리에만 존재하게 되고, 세션이 바뀌면 그 지식이 사라진다. 스펙 파일은 커밋되는 산출물이므로 세션과 무관하게 지식이 유지된다. "컨텍스트 엔지니어링"의 관점에서 보면 SDD는 에이전트에게 매번 다시 설명해야 하는 지식을 파일로 외재화하는 작업인 셈이다.

## 결론: 첫 단계 제안

- 스펙 엄격성 3단계(spec-first / spec-anchored / spec-as-source) 중 자기 팀의 목표 수준을 먼저 정하라. 도구는 그 다음 문제다.
- Spec Kit의 핵심 구조는 **무엇(specify)과 어떻게(plan)의 분리**다. 이 분리만 취해도 에이전트의 임의 재해석을 크게 줄일 수 있다.
- 시작은 간단하다: `uv tool install specify-cli` 후 기존 프로젝트에 `specify init --here`를 실행하고, 다음 기능 하나를 `/speckit.specify`부터 시작해 보라.
- 이미 진행 중인 프로젝트라면 헌법(constitution)부터 작성하라. 기능 스펙보다 상위 원칙이 에이전트 출력의 일관성에 더 크게 기여한다.
- SDD는 목적이 아니라 수단이다. 스펙이 코드보다 오래 살아남는 경우에만, 그 비용을 지불할 가치가 있다.
