# 아젠틱 서빙은 채팅 서빙과 다른 게임이다: vLLM AgentX 최적화에서 배우는 KV 캐시·병렬성·라우팅 설계

LLM 추론 인프라를 설계할 때 대부분의 문서와 튜토리얼은 여전히 '채팅' 워크로드를 가정합니다. 짧은 프롬프트가 들어오고, 몇백 토큰의 응답이 나가고, 요청은 서로 독립적입니다. 그런데 이 가정은 이미 깨졌습니다. OpenAI가 2026년 8월 12일 발표한 엔터프라이즈 사용 데이터에 따르면, 2026년 6월 기준 엔터프라이즈 고객의 Codex + ChatGPT 출력 토큰 합계에서 Codex, 즉 에이전트 루프가 차지하는 비중이 64%에 달합니다. 채팅이 아니라 에이전트가 이제 메인 워크로드입니다.

에이전트 워크로드는 요청 모양 자체가 다릅니다. 하나의 세션이 수십 턴에 걸쳐 이어지고, 매 턴마다 지금까지의 대화 전체에 도구 결과만 붙여서 다시 보냅니다. 입력은 계속 커지는데 새로 계산할 부분은 작고, 출력은 짧습니다. 이런 트래픽을 채팅용으로 튜닝된 서빙 스택에 그대로 올리면 GPU 메모리는 KV 캐시로 넘치고, 첫 토큰 지연(TTFT)은 급증하고, 비용은 통제 불능이 됩니다.

vLLM 팀이 2026년 9월 8일 발표한 "vLLM x AgentX" 포스트는 이 문제를 풀 스택 전체를 공개한 문서입니다. SemiAnalysis의 공개 벤치마크인 AgentX — 실제 에이전트 코딩 트레이스로 구성 — 에서 DeepSeek V4 Pro, MiniMax M3, Kimi K3로 측정한 결과를 바탕으로, 데이터 플레인(KV 캐시), 실행 플레인(병렬성·커널), 컨트롤 플레인(P/D 비율·스케줄링)의 최적화를 설명합니다. 이 글은 그 내용을 실무 관점에서 재구성하고, 특히 "뭐가 먹히고 뭐가 안 먹혔는가"를 정리합니다.

## 워크로드 특성: AgentX 트레이스가 말해주는 것

SemiAnalysis AgentX 벤치마크의 실제 에이전트 트레이스 통계는 아젠틱 서빙의 난이도를 한눈에 보여줍니다.

| 지표 | 값 (중앙값) |
|------|------------|
| 세션당 턴 수 | 43턴 |
| 입력 길이 | 142K 토큰 |
| 출력 길이 | 444 토큰 |
| 프리픽스 캐시 히트율 | 96% 이상 |
| 서브에이전트 포함 세션 | 44% (포함 시 중앙값 4개 롤아웃) |

입출력 비율이 roughly 300:1이라는 점이 핵심입니다. vLLM이 5월에 발표한 Mooncake 통합 포스트의 Codex/SWE-bench Pro 코퍼스 분석에서도 평균 131:1의 입력 대 출력 비율과 94.2% 캐시 히트율이 나왔는데, AgentX 트레이스는 이보다 더 극단적입니다. 매 턴 142K 토큰을 받지만 새로 prefill할 것은 도구 결과 정도이고, 나머지 96% 이상은 엔진이 이미 본 프리픽스입니다.

이 특성이 서빙 스택에 만드는 압력은 세 가지입니다.

1. **프리픽스 캐시 압박**: 모든 턴이 전체 대화를 재생하므로, 많은 세션을 동시에 돌리려면 턴 사이에 KV 캐시를 오프로드해야 합니다. 이게 GPU 간, P/D 분리 인스턴스 간, 레플리카 간에 효율적으로 동작해야 합니다.
2. **실행 효율**: 긴 컨텍스트 + 타이트한 지연 요구 조합이므로, 병렬성·커널·스케줄링·스페큘러티브 디코딩을 새로운 요청 모양에 맞게 재조정해야 합니다.
3. **P/D 비율 탐색**: 세션과 서브에이전트마다 컨텍스트 길이와 히트율이 크게 달라서, 처리량 최적의 prefill/decode 비율을 찾기 어렵고 그 최적점도 동시성에 따라 이동합니다.

## 데이터 플레인: KV 캐시를 따뜻하게, 계산 가까이에

### 하이브리드 KV 캐시 관리

vLLM의 출발점은 PagedAttention 이래의 자산인 페이지 단위 관리를 최신 하이브리드 모델로 확장하는 것입니다. 슬라이딩 윈도우 어텐션, 선형(순환) 어텐션, 풀 어텐션이 섞인 모델은 캐시 블록의 크기와 수명이 제각각이라 정적 분할이 안 됩니다. vLLM은 하나의 균일한 메모리 페이지를 기본 할당 단위로 삼고, 단일 공유 블록 풀로 관리합니다. 풀 하나로 관리하면 동시성·컨텍스트 길이·재사용 패턴에 따라 수요 기반으로 재할당할 수 있습니다.

DeepSeek V4 사례는 구체적입니다. 초기 KV 캐시 레이아웃이 캐시 타입별로 92개의 분할된 텐서를 할당했는데, 새 packed 레이아웃은 모든 캐시 그룹과 레이어를 블록당 하나의 연속 배킹 할당에 저장합니다. 이렇게 바꾸자 디스크립터와 P/D 전송 오버헤드가 줄고, FP4 인덱서 활성화 시 KV 캐시 메모리를 약 10% 절약합니다.

### 분산 KV 캐시 풀: Mooncake Store

GPU 메모리를 넘어서는 프리픽스를 보존하기 위해 vLLM은 Mooncake Store를 통합했습니다. 5월 발표 당시 실제 에이전트 트레이스 재생에서 처리량 3.8배, TTFT 46배 감소, 엔드투엔드 지연 8.6배 감소를 기록했고, GB200 60대까지 거의 선형 확장됐습니다. 9월 포스트에서는 이 위에 몇 가지가 더 얹혔습니다.

- **계층형 오프로딩**: `standalone-store` 모드로 CPU 풀과 디스크 티어를 자유롭게 확장. vLLM 워커는 순수 요청자가 됩니다.
- **아키텍처 동등성**: 스파스·컴프리스트·선형 어텐션 등 신규 아키텍처에서도 오프로딩이 비동기 스케줄링, P/D 분리, 스페큘러티브 디코딩과 함께 정상 동작합니다.
- **세션 인지 프리픽스 유지**: 하이브리드 모델의 프리픽스 재사용은 재사용 경계의 선형 상태나 슬라이딩 윈도우 캐시 보존이 필요합니다. 매 토큰 스냅샷은 비싸므로 두 정책을 조합합니다 — (1) 인터벌 기반 유지: 매 턴 끝의 프롬프트 캐시/선형 상태를 자동 보존, (2) Marconi 방식 선택적 유지: 같은 프리픽스가 두 번째 관측될 때 체크포인트를 유지. 이후 동일 프리픽스 요청이 재사용합니다.

## 실행 플레인: 병렬성은 모델 아키텍처를 따라야 한다

이번 포스트에서 가장 교훈적인 부분입니다. 결론부터: **병렬성 전략은 모델 아키텍처에 종속적이며, 하나의 모델에서 검증된 전략이 다른 모델로 이식되지 않는다.**

### Kimi K3: DCP가 먹힌다

Kimi K3는 MLA(잠재 어텐션)로 KV를 단일 잠재 공간에 압축합니다. 텐서 병렬(TP)은 이 잠재 캐시를 랭크마다 복제하므로 비효율적입니다. 대안은 디코드 컨텍스트 병렬성(DCP) — KV 캐시를 시퀀스 차원으로 샤딩해 랭크당 1/N만 보유하는 방식입니다.

```bash
# vLLM에서 DCP 활성화 (DeepSeek-V2-Lite 예시)
vllm serve deepseek-ai/DeepSeek-V2-Lite \
    --tensor-parallel-size 2 \
    --decode-context-parallel-size 2
```

MLA 디코드는 메모리 바운드라 컨텍스트가 길어질수록 각 스텝에서 어텐션 비중이 커지는데, DCP는 이를 샤딩해 스텝을 짧게 만듭니다. KV 복제를 피하면 더 많은 시퀀스를 띄울 수 있어 처리량도 올라갑니다. vLLM의 8월 DCP 포스트는 롱컨텍스트 아젠틱 워크로드에서 TP 대비 최대 3배 처리량을 보고했습니다.

DCP의 비용은 통신입니다. 시퀀스로 샤딩했으니 매 MLA 디코드 레이어마다 어텐션 전 쿼리 gather와 후 부분 출력 리덕션이 필요합니다. vLLM은 NCCL을 우회하고 symmetric-memory 버퍼로 GPU끼리 직접 읽고 쓰게 해서, 통신을 계산 커널에 융합했습니다. 결과는 레이어당 지연 약 13% 감소입니다.

단, 스케일업 도메인이 커지면 최적이 바뀝니다. NVL72급 시스템에서는 와이드 EP + 데이터 병렬(DEP)이 DCP보다 잘 늘어납니다 — 랭크당 배치가 3을 넘는 시점부터 DEP16이 DCP8을 앞섭니다.

### DeepSeek V4: DCP가 안 먹힌다

같은 잠재 어텐션 계열인데도 DeepSeek V4는 사정이 다릅니다. 컴프레스드 스파스 어텐션 스택에 인덱서와 컴프레서가 추가로 붙어 있어, 컨텍스트 병렬성이 이 하위 레이어 전부를 분할·조율해야 합니다. vLLM 팀이 통신-계산 오버랩과 커널 최적화에 크게 투자한 뒤에도 DCP는 DEP를 이기지 못하고 타잉 수준이었습니다.

대신 V4에서는:
- **PCP(prefill context parallelism)**가 긴 프리필에 최적 — 32K 프롬프트에서 PCP8이 TP8 대비 2.65배 프리필 속도업, TTFT 대폭 감소. 단 디코드 상태를 복제하므로 전용 프리필 워커에 적합.
- **DEP**가 대부분의 V4 구성에서 기본값 — 요청과 디코드 토큰을 데이터 병렬 랭크에 분산하고 어텐션 경로를 완전 로컬로 유지합니다.

### 스케줄링: 긴 프리필이 짧은 턴을 막지 않게

아젠틱 트래픽은 "긴 프리픽스 + 짧은 추가 프리필"인 append-only 요청이 대부분이고, 가끔 수만 토큰의 신선한 긴 프리필이 섞입니다. 긴 프리필 하나가 인스턴스 내에서 짧은 인터랙티브 턴을 막고(head-of-line blocking), DEP 랭크 간에는 배치 불균형을 만듭니다.

첫 번째 문제의 해법은 간단합니다:

```bash
# 한 요청이 스텝당 스케줄할 수 있는 토큰 수 상한
--long-prefill-token-threshold 512
```

512 토큰 상한을 걸면 긴 프리필이 한 스텝 전체를 독점하지 않아 짧은 턴이 같은 배치에 끼어 들어와 디코딩을 빨리 시작합니다. DeepSeek V4 Pro on B300에서 이 설정만으로 GPU당 초당 총 토큰(TPGS)이 최대 93% 증가했고 P90 인터랙티비티가 약 2.3배 개선됐습니다. 트레이드오프는 긴 요청 자체의 TTFT 상승 — TTFT 민감 배포라면 상한을 크게 잡으면 됩니다.

## 컨트롤 플레인: 로드 밸런싱이 성능을 보장하지 않는다

가장 반직관적인 발견입니다. DEP 배포에서 랭크 간 KV 캐시 사용량 불균형이 커지자, 큐 깊이·실행 토큰 수·KV 사용률 기반으로 요청을 분산하는 정책들을 시도했습니다. 결과: AgentX 실험에서 이 정책 전부가 **단순한 세션 인지 스티키 라우팅보다 못했다**습니다.

이유는 캐시 지역성입니다. 많은 아젠틱 세션의 턴 간 지연이 짧아서, 다음 턴이 도착할 때쯤 이전 턴의 프리픽스가 아직 그 GPU에 상주해 있습니다. 세션을 덜 바쁜 랭크로 옮기면 분산 풀에서 프리픽스를 다시 가져와야 합니다. 전송은 비동기이고 계산과 오버랩되지만 공짜는 아닙니다. 프리페치된 블록이 일시적으로 GPU KV 캐시 용량을 차지해 목적지 랭크가 수용할 수 있는 시퀀스 수가 줄어듭니다. 즉, 큐는 더 균형 잡혔는데 전체적으로 처리하는 동시 요청은 줄어드는 것입니다.

턴 간 지연이 짧은 워크로드에서는 세션 지역성 보존이 순간 부하 분산보다 가치가 큽니다. 라우팅 결정은 큐된 작업량만이 아니라 각 워커에 이미 상주한 상태를 고려해야 합니다.

## 성능과 비용: 숫자로 보는 아젠틱 서빙

AgentX 측정 결과, vLLM은 DeepSeek V4 Pro에서 GPU당 초당 최대 130K 총 토큰, MiniMax M3에서 최대 376 tokens/s의 인터랙티비티를 달성했습니다. 그리고 DeepSeek V4 Pro, MiniMax M3, Kimi K3 전반에서 Opus 5 API 가격 대비 14.6배에서 106배의 서빙 비용 우위를 보였습니다 (TCO 기준, GB300 $2.31/GPU-hour, B300 $2.26/GPU-hour — SemiAnalysis InferenceX 데이터).

특히 DeepSeek V4 Pro의 파레토 곡선이 보여주는 트레이드오프가 흥미롭습니다. 최대 비용 효율 구간(P90 38.8 tokens/s/user, $1당 2.027억 토큰)부터 최대 인터랙티비티 구간(P90 198 tokens/s/user, $1당 110만 토큰)까지 약 185배의 비용 효율 차이가 같은 하드웨어 위의 설정 선택만으로 존재합니다. 아젠틱 서빙에서 '어느 지점에서 운영할 것인가'는 하드웨어 구매만큼이나 중요한 결정입니다.

## 앞으로: 에이전트 구조를 스택에 명시적으로 드러내기

vLLM이 예고하는 방향은 에이전트의 구조를 서빙 스택 전반에 명시적으로 반영하는 것입니다.

- **에이전트 힌트**: 프레임워크가 세션 구조, 분기 지점, 캐시 위치, 도구 호출 지연, 세션 라이프사이클을 요청에 실어 보내면, 엔진이 스케줄링·캐시 축출 등에 활용.
- **프로그래밍 가능한 KV 캐시**: 워크로드별 프리페치·축출·소프트핀 정책을 사용자가 제어하는 인터페이스.
- **세션 기반 KV 캐시 관리**: 턴 사이 공백 시 다음 턴을 서빙할 가능성이 높은 워커로 상태를 미리 이동.

## 정리: 실무자를 위한 체크리스트

- **워크로드를 먼저 측정하라**: 턴 수, 입력/출력 비율, 프리픽스 히트율, 턴 간 지연 분포. 이 네 가지가 서빙 아키텍처 전부를 결정한다. AgentX 트레이스(중앙값 43턴, 142K 입력, 444 출력, 96%+ 히트율)를 자기 트래픽과 비교해보라.
- **프리픽스 재사용은 우연이 아니라 설계다**: 공유 블록 풀 + 분산 KV 캐시 풀(Mooncake 등) + 세션 인지 유지 정책까지 갖춰야 히트율이 실현된다. 이론 히트율과 실현 히트율의 차이는 스케줄링·축출 문제다.
- **병렬성은 모델별로 검증하라**: MLA 단순 모델은 DCP, 복잡한 스파스 어텐션 모델은 DEP+PCP가 나을 수 있다. 남의 벤치마크를 믿지 말고 자기 모델·하드웨어에서 측정하라.
- **로드 밸런싱이 만능이 아니다**: 캐시 지역성이 짧은 턴 간 지연과 만나면 스티키 라우팅이 이긴다. 라우터가 각 워커의 상주 상태를 알아야 한다.
- **비용-인터랙티비티 곡선에서 자기 위치를 골라라**: 같은 하드웨어에서 설정만으로 비용 효율이 100배 이상 달라진다. SLO를 먼저 정하고 그에 맞는 구성점을 찾아라.

첫 단계로 추천하는 것은 자기 트래픽의 프리픽스 히트율을 측정하는 것입니다. vLLM의 메트릭 엔드포인트에서 prefix cache hit rate를 관측하다 보면, 어느 최적화가 자기 환경에서 돈이 되는지 대답이 명확해집니다.
