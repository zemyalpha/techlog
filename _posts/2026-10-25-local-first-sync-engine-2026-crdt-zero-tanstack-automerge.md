# 오프라인에서 병합되는 앱의 원리 — 2026년 로컬-퍼스트 동기화 엔진 선택 가이드

노트 앱에서 할 일 목록 앱까지, "인터넷이 끊겨도 계속 쓰고 나중에 자동으로 합쳐지는" 경험은 이제 사용자가 당연하게 기대하는 수준이 됐다. 그런데 이걸 직접 구현하려는 팀은 곧바로 분산 시스템 문제와 마주한다. 두 대의 기기가 오프라인 상태에서 같은 데이터를 각자 수정했다면, 다시 연결됐을 때 누구의 수정을 살릴 것인가?

2026년 들어 이 질문에 대한 답이 크게 달라졌다. 범용 동기화 엔진들이 안정 버전에 도달했고, CRDT 라이브러리의 치명적인 약점이던 메모리 문제가 해소됐으며, FOSDEM 2026에는 로컬-퍼스트 전용 데브룸이 생길 만큼 생태계가 성숙했다. 이 글에서는 로컬-퍼스트 동기화가 실제로 어떻게 동작하는지 코드로 확인하고, 2026년 시점에 어떤 엔진을 어떤 기준으로 골라야 하는지 정리한다.

## 로컬-퍼스트란 무엇이고, 무엇을 대체하는가

"로컬-퍼스트(local-first)"라는 용어는 2019년 Ink & Switch가 발표한 논문에서 체계화됐다. 핵심은 단순하다. 데이터의 원본은 사용자의 기기에 있고, 네트워크는 의존성이 아니라 동기화 채널이라는 것. 앱은 로컬 저장소에서 즉시 읽고 쓰며, 서버와의 동기화는 뒤에서 조용히 일어난다.

이 구조를 도입하지 않은 팀도 사실 이미 동기화 엔진의 상당 부분을 손으로 만들어 왔다. 응답 캐시와 무효화 규칙, 낙관적 업데이트 핸들러, 실패한 변경사항의 재시도 큐, 엔드포인트마다 제각각인 충돌 처리 규칙, WebSocket 폴링 채널, 재연결 처리, "연결이 불안정합니다" 배너까지. 각 조각은 서로 다른 시기에 다른 개발자가 추가했지만, 모여서 사실상 동기화 엔진의 역할을 하고 있다.

동기화 엔진을 도입한다는 것은 이 손으로 짠 더미를 의존성 하나로 교체하는 일이다. 대가로 브라우저 저장소 축출(eviction), 클라이언트 쪽 스키마 마이그레이션, 권한 모델 아래에서의 부분 동기화 같은 새로운 문제를 떠안게 된다. 즉 동기화 엔진은 복잡성을 없애주는 게 아니라 **재배치**해주는 도구다.

## 2026년에 무엇이 달라졌나

지난 6년간 "이렇게 만들어야 하나?"에 대한 정직한 답은 "분산 시스템 팀을 꾸릴 수 있다면"이었다. 2026년엔 그 전제가 무너졌다. 상징적인 사건 세 가지를 짚는다.

**Automerge 3.0 — CRDT의 메모리 문제가 사라졌다.** CRDT(Conflict-free Replicated Data Type)에 대한 가장 흔한 반론은 정확성이 아니라 문서 이력이 끝없이 커져 클라이언트를 못 쓰게 만든다는 것이었다. Automerge 3.0은 기존에 디스크 저장용으로만 쓰던 압축 칼럼 형식을 런타임에서도 사용하도록 재설계했다. 공식 발표에 따르면 『모비 딕』 전문을 붙여넣었을 때 Automerge 2 문서는 700MB를 소비했지만 3에서는 1.3MB에 그친다. 17시간이 지나도 로딩이 끝나지 않던 큰 이력의 문서가 9초 만에 열리는 사례도 보고됐다. 전체적으로 메모리 사용량이 10배 이상 줄었다.

**Zero 1.0 — 범용 동기화 엔진의 첫 안정 버전.** Rocicorp가 2026년 6월 Zero 1.0을 출시했다. 공식 릴리스 노트는 "약 2년의 개발, 50여 회의 릴리스, 수천 커밋 끝에 안정화를 선언한다"고 밝힌다. Postgres를 소스로 두고 클라이언트에 반응형 로컬 상태를 내려주는 구조로, 기능상으로는 직전 0.26.2와 거의 같고 버전 번호의 상징적 의미가 크다.

**TanStack DB 0.6 — 탭을 닫아도 상태가 남는다.** 2026년 3월 TanStack DB 0.6이 SQLite 기반 영속성을 추가했다. 로컬 상태가 탭 새로고침이 아니라 앱 재시작을 넘겨 살아남으며, 브라우저·Node·React Native·Expo·Cloudflare Durable Objects 등의 런타임에서 동작한다.

생태계 신호도 명확하다. FOSDEM 2026(2월 1일)에는 로컬-퍼스트·동기화 엔진·CRDT를 다루는 전용 데브룸이 열렸고, Yjs·Automerge·ElectricSQL·Loro 등 23개 발표가 하루를 채웠다. 컨퍼런스 트랙은 채택의 후행 지표다. 이미 충분히 많은 팀이 뭔가를 배포했기에 논쟁거리가 생긴 것이다. 또한 ElectricSQL은 사명을 Electric으로 바꾸고 2026년 4월 "동기화 위에 만든 에이전트 플랫폼"을 내놓으며, 동기화의 대상이 협업 앱을 넘어 AI 에이전트 상태로 확장되고 있음을 보여줬다.

## CRDT는 실제로 어떻게 병합되나 — 코드로 확인

CRDT 라이브러리를 직접 쓰는 것(Yjs, Automerge, Loro)과 동기화 엔진을 쓰는 것(Zero, Electric, PowerSync)은 해결하는 문제가 다르다. 전자는 공동 편집·화이트보드처럼 세밀한 동시 편집이 필요한 경우, 후자는 이미 Postgres 기반 앱이 있어서 데이터 레이어를 다시 설계하지 않고 오프라인 읽기·쓰기를 원하는 경우다.

Yjs로 오프라인 병합을 2분 만에 확인할 수 있다. 노트북 두 대가 빈 할 일 목록에서 시작해 각자 오프라인으로 항목을 추가한 뒤, 네트워크에서 일어나는 업데이트 교환을 로컬에서 시뮬레이션한다.

```javascript
// merge-demo.mjs — npm install yjs 후 실행
import * as Y from 'yjs'

const laptopA = new Y.Doc()
const laptopB = new Y.Doc()
const todosA = laptopA.getMap('todos')
const todosB = laptopB.getMap('todos')

// 각자 오프라인에서 추가
todosA.set('buy-milk', { done: false })
todosA.set('walk-dog', { done: true })
todosB.set('buy-milk', { done: false })
todosB.set('call-dentist', { done: false })

// 동기화 프로바이더가 네트워크에서 하는 일:
// 양쪽 업데이트를 교환하고 서로 적용한다
Y.applyUpdate(laptopB, Y.encodeStateAsUpdate(laptopA))
Y.applyUpdate(laptopA, Y.encodeStateAsUpdate(laptopB))

console.log('A 병합 후:', todosA.toJSON())
console.log('B 병합 후:', todosB.toJSON())
// 두 레플리카 모두 세 항목을 갖는다. 병합 로직은 한 줄도 안 썼다.
```

실행하면 두 문서가 항상 같은 세 항목으로 수렴한다. 병합 로직, 충돌 화면, 서버 중재자 — 그 어떤 것도 작성하지 않았다.

다만 실전에서 반드시 알아야 할 함정이 있다. `Y.Map`의 순회 순서는 각 레플리카가 업데이트를 받은 순서를 반영하기 때문에, 복제본 두 개를 `JSON.stringify()`로 비교하면 내용이 같아도 순서가 달라 거짓 불일치가 뜬다. 비교하려면 키를 정렬해야 한다.

```javascript
// 레플리카 동등성 비교 — 순서를 정규화하고 비교한다
const sorted = (m) =>
  JSON.stringify(Object.keys(m.toJSON()).sort()
    .reduce((acc, k) => ({ ...acc, [k]: m.toJSON()[k] }), {}))

console.log(sorted(todosA) === sorted(todosB)) // true
```

이런 세부 동작은 라이브러리 문서에 나오지만, 테스트 코드를 짜다 보면 처음 한 번은 반드시 만나는 유형의 문제다.

## 엔진 선택은 라이브러리 문제가 아니라 충돌 의미론 문제다

여기까지 읽었다면 "그래서 Yjs? Zero? Electric?"을 묻고 싶을 것이다. 그런데 정작 되돌리기 어려운 결정은 라이브러리가 아니라 **데이터가 요구하는 충돌 의미론(conflict semantics)** 쪽이다. 라이브러리는 교체 비용이 치르지 못할 수준이 아니지만, "마지막에 쓴 사람이 이긴다"로 풀지 "문자 단위로 합친다"로 풀지는 제품 전체에 스며들기 때문이다.

선택 기준을 정리하면 다음과 같다.

- **CRDT 라이브러리(Yjs, Automerge 3, Loro)**: 리치 텍스트 공동 편집, 화이트보드, 세밀한 동시 편집이 핵심인 제품. 저장소와 전송 계층은 직접 연결한다. Yjs는 Jupyter의 실시간 협업과 Tiptap·ProseMirror 기반 도구들에 널리 쓰이는 사실상의 표준이다.
- **동기화 엔진(Zero, Electric, PowerSync)**: 이미 Postgres 기반이고 데이터 모델을 바꾸고 싶지 않은 경우. Zero는 2026년 6월 1.0에 도달했고, Electric은 AI 에이전트 상태 동기화로 영역을 넓혔으며, PowerSync는 대기업 프로덕션 사례를 쌓아가는 중이다.
- **반응형 쿼리 레이어(TanStack DB)**: 프레임워크 종속적인 캐싱에서 벗어나 영속성 있는 클라이언트 상태가 필요한 경우. 0.6부터 SQLite 영속성으로 앱 재시작을 넘긴다.

어느 쪽이든 도입 전에 브라우저 저장소 축출 정책, 강제할 수 없는 클라이언트 스키마 마이그레이션, 권한 경계 아래의 부분 동기화, 테스트 스위트가 닿기 어려운 오프라인 경로를 점검해야 한다. 동기화 엔진이 제거해주는 것의 목록을 만들 때처럼, 이번엔 새로 생기는 것의 목록도 만들어 두는 것이 정직한 출발점이다.

## 결론

- 로컬-퍼스트는 네트워크를 의존성이 아닌 동기화 채널로 격하하는 아키텍처로, 2019년 Ink & Switch 논문에서 체계화됐다.
- 2026년의 변화는 세 가지다. Automerge 3.0의 메모리 10배 이상 절감(700MB→1.3MB), Zero의 1.0 안정화, TanStack DB 0.6의 SQLite 영속성이다.
- CRDT 병합은 `Y.applyUpdate` 두 줄로 검증할 수 있지만, 맵 순회 순서처럼 문서에 잘 안 나오는 함정이 실전에 있다.
- 라이브러리 선택보다 되돌리기 어려운 결정은 충돌 의미론이다. 세밀한 동시 편집이면 CRDT 라이브러리, Postgres 자산이 있으면 동기화 엔진이 출발점이다.
- 동기화 엔진은 복잡성을 없애지 않고 재배치한다. 브라우저 저장소 축출, 클라이언트 마이그레이션, 부분 동기화 권한 문제가 그 대가다.

당장 해볼 첫 단계는 위의 Yjs 데모를 로컬에서 돌려보는 것이다. 서버도 계정도 필요 없고, 두 문서가 조용히 수렴하는 걸 눈으로 확인하는 순간 "오프라인 병합"이 추상 개념이 아니게 된다.
