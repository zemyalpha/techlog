# AI 코딩 에이전트는 코드를 30% 늘렸다, 그러나 소프트웨어 출시량은 그대로 — 하버드 718개 기업 연구가 밝힌 '리뷰 병목'

2026년 1월 기준, 분석 대상 소프트웨어 기업의 95% 이상이 AI 코딩 에이전트를 도입했습니다. 그런데 정말 소프트웨어가 더 빨리, 더 많이 출시되고 있을까요? 하버드 대학의 Fiona Chen과 James Stratton 두 경제학자가 엔지니어링 분석 플랫폼 Jellyfish의 데이터로 이 질문에 정면으로 답한 논문을 발표했습니다("Artificial Intelligence in the Firm: Bottlenecks in Software Production"). 결론부터 말하면 — **코드는 30% 늘었는데, 완성된 작업은 통계적으로 늘지 않았고, 그 차이를 설명하는 것은 코드 리뷰 병목입니다.**

## 연구가 다룬 데이터: 3억 개의 작업 이벤트

이 연구가 특별한 이유는 실험실 벤치마크가 아니라 실제 기업의 작업 데이터를 봤다는 점입니다. 연구진은 2021년부터 2026년 3월까지 718개 소프트웨어 기업, 70만 명 이상의 엔지니어에서 수집된 **3억 개의 작업 이벤트**(GitHub 커밋·풀 리퀘스트, Jira 이슈, 캘린더 일정)를 확보했습니다.

각 기업이 AI 코딩 도구를 언제 도입했는지를 식별하고, 도입 시점이 서로 다른 기업들을 비교하는 **staggered difference-in-differences** 회귀로 인과 효과를 추정했습니다. 여기서 '어시스턴트'(자동완성 중심)와 '에이전트'(프롬프트로 자율적으로 코드를 작성·제출)를 구분한 것도 중요합니다. 채택 곡선은 2024년 11월 Cursor Agent와 2025년 2월 Claude Code 출시를 계기로 가파르게 상승해, 2024년 10월 0%에서 2026년 1월 95%를 넘었습니다.

## 핵심 결과: +30% 코드, 그러나 유의미한 변화 없는 출시량

에이전트 도입 후 기업 단위에서 측정된 변화는 다음과 같습니다.

| 지표 | 변화 |
|------|------|
| 코드 라인 수 | +30% |
| 커밋 수 | +20% |
| 풀 리퀘스트 수 | +23% |
| Jira 이슈/에픽 해결량 | 통계적으로 유의미한 변화 없음 |
| 리뷰 완료까지 걸리는 시간 | +49% |
| 변경 요청(change requested)이 달린 PR 비율 | 거의 2배 (0.13 → 0.25) |
| PR당 리뷰 코멘트 수 | +35% |
| 코드 리뷰를 수행하는 근로자 비율 | +14% |

가장 뼈아픈 수치는 출시량 쪽입니다. 연구진은 신뢰구간 분석을 통해 에이전트 도입 시 기업 산출이 12% 이상 증가했다는 가설을 **기각**했습니다. 개인 수준 생산성 게인(+30%)이 기업 수준 산출로 전이(pass-through)되지 않은 것입니다. 어시스턴트는 효과 자체가 작았습니다(코드 라인 +12%, 커밋 +9%, PR +5% — 통계적으로 유의한 것은 커밋뿐). 고용에도 유의미한 변화가 없었습니다.

## 병목의 해부: AI가 빚는 속도, 인간이 치르는 대가

왜 이런 간극이 생길까요? 연구진의 답은 명확합니다. **생산 공정의 하류 제약이 게인을 흡수한다**는 것입니다. 리뷰 시간이 49% 늘고, 변경 요청이 2배가 되고, 코멘트가 35% 늘어난 것이 그 증거입니다. 기업들은 리뷰 담당 비율을 14% 늘리며 인력을 재배치했지만, 그걸로도 부족했습니다.

구조적 배경도 데이터에 있습니다. 엔지니어가 실제로 코드를 '작성'하는 데 쓰는 시간은 활동 데이터 기준 **42%**, 엔지니어 100명 설문 기준으로는 **30%**에 불과합니다. 나머지는 리뷰, 회의, 관리에 소모됩니다. 즉, 코딩 속도를 아무리 끌어올려도 전체 공정의 절반도 못 미치는 지점만 가속하는 셈입니다.

그렇다면 AI가 리뷰도 대신하면 되지 않을까요? 아직 아닙니다. 2026년 3월 기준 약 80% 기업이 리뷰에 AI를 활용했지만, 전체 리뷰 코멘트 중 AI 생성은 **23.3%**, AI 코멘트를 하나라도 받은 PR도 **10.8%**에 그쳤습니다. 검수는 여전히 인간의 영역입니다.

## 실전 대응: 리뷰 병목을 줄이는 4가지 설계

이 연구의 교훈은 "AI를 쓰지 마라"가 아니라 **"측정 지표와 리뷰 공정을 재설계하라"**입니다. 코드량(LOC)이나 커밋 수는 이제 생산성의 그림된 지표입니다. 이슈 해결 리드타임, 리뷰 대기 시간, 변경 요청률을 봐야 합니다. 실무에서 바로 적용할 수 있는 것들입니다.

**1) PR 크기 상한을 강제한다.** 리뷰 시간은 PR 크기에 비례하지 않고 가속합니다. GitHub Actions로 400라인 상한을 걸어두면 에이전트가 만든 거대 PR이 리뷰 큐를 잡아먹는 것을 막을 수 있습니다.

{% raw %}
```yaml
# .github/workflows/pr-size-limit.yml
name: pr-size-limit
on: [pull_request]
jobs:
  check-size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Fail if PR adds more than 400 lines
        run: |
          git fetch origin main
          ADDED=$(git diff --numstat origin/main...HEAD | awk '{s+=$1} END {print s+0}')
          echo "Added lines: $ADDED"
          if [ "$ADDED" -gt 400 ]; then
            echo "::error::PR이 400라인을 초과합니다. 작게 나누세요."
            exit 1
          fi
```
{% endraw %}

**2) 자동 테스트 게이트를 리뷰 앞에 둔다.** 인간 리뷰어가 검증 가능한 것(테스트 통과, 린트, 타입 체크)을 기계에게 넘기면, 리뷰어는 설계와 정확성에만 집중합니다. 변경 요청의 상당수는 사전에 자동으로 걸러집니다.

**3) AI 리뷰봇을 '1차 필터'로 배치한다.** 연구 데이터가 보여주듯 AI 리뷰는 아직 23% 수준이지만, nits·스타일·자명한 버그를 선별해서 인간 리뷰어 부하를 줄이는 용도로는 이미 실용적입니다. 다만 최종 승인 권한은 인간에게 두는 것이 이 연구가 시사하는 바와 부합합니다.

**4) CODEOWNERS로 리뷰를 분산한다.** 리뷰가 병목이 되는 조직의 전형은 특정 시니어에게 리뷰가 집중되는 구조입니다. 디렉터리별 소유자를 지정해 대기열을 분산시키세요.

```text
# .github/CODEOWNERS 예시
/src/auth/       @team-auth
/src/payments/   @team-payments
/infra/          @team-platform
*.tf             @team-platform
```

## 한계를 읽는 눈

이 연구의 데이터는 2026년 3월에 끝납니다. 그 이후 에이전트는 더 좋아졌고, 팀들도 활용법을 배우고 있습니다. 저자들도 지적하듯 코딩 시간 대비 리뷰 시간의 트레이드오프는 팀이 성숙해지며 개선될 여지가 있습니다. 또한 '이슈 해결량'이라는 산출 지표가 소프트웨어의 질·가치를 완전히 담지는 못한다는 점도 한계입니다. 그럼에도 718개 기업, 3억 개 이벤트라는 규모가 주는 통계적 힘은 벤치마크 점수나 개인 경험담과는 비교할 수 없습니다.

## 결론

- AI 에이전트는 코드량을 30% 늘리지만 기업의 기능 출시량은 유의미하게 바꾸지 못했다 — 리뷰 병목이 게인을 흡수했다
- 리뷰 시간 +49%, 변경 요청 2배, 코멘트 +35% — 비용은 검수 단계로 이동했다
- 엔지니어 시간의 코드 작성 비중은 30~42% — 코딩 가속만으로는 전체 공정이 빨라지지 않는다
- 생산성 지표를 LOC에서 '이슈 리드타임·리뷰 대기·변경 요청률'로 바꿔야 한다
- 당장 할 일: PR 크기 상한, 테스트 게이트, AI 1차 필터, CODEOWNERS 분산 — 리뷰 공정 재설계부터
