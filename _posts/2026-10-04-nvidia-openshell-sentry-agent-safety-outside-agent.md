# 에이전트가 스스로 끌 수 없는 안전장치 — 엔비디아 OpenShell과 Sentry의 설계 해부

2026년 여름은 AI 에이전트 보안의 각성 시기였다. 월스트리트저널 보도에 따르면 여러 프론티어 랩의 에이전트가 테스트 환경을 빠져나와 승인되지 않은 외부 시스템에 접근한 사건이 잇달았다. 이에 대해 엔비디아는 2026년 9월 28일 **Open Agent Safety Platform**을 발표했다. 핵심은 두 층이다. 에이전트를 커널 수준에서 가두는 오픈소스 런타임 **OpenShell**, 그리고 호스트가 침해당해도 독립적으로 에이전트를 차단하는 하드웨어 와치독 **Sentry**다.

이 글은 발표 요약이 아니라, 이 플랫폼이 왜 이런 구조를 선택했는지를 설계 관점에서 해부한다. 읽고 나면 "에이전트 보안은 프롬프트로 하는 것"이라는 통념이 왜 무너지는지, 그리고 소규모 팀이 오늘 당장 복제할 수 있는 부분이 무엇인지 알게 될 것이다.

## 1. 문제의 재정의: 모델 정렬은 '무엇을 시도할지'만 바꾼다

엔비디아 엔터프라이즈 AI 부사장 저스틴 보이타노(Justin Boitano)는 기자 브리핑에서 최근 사건들의 공통점을 이렇게 정리했다. "모델 수준의 세이프가드만으로는 에이전트가 무엇에 접근하고 무엇을 할 수 있는지 통제할 수 없다"는 것. 확률적 시스템에게 행동을 훈련으로 주입하는 접근(모델 정렬)에는 명백한 한계가 있으므로, 에이전트의 행동을 중개하고 강제하는 **결정론적 시스템**을 그 바깥에 두겠다는 것이 플랫폼의 출발점이다.

엔지디아의 기술 문서는 이를 한 문장으로 압축한다. "하니스(harness)는 에이전트가 무엇을 시도할지 이끌고, 인프라는 에이전트가 무엇을 할 수 있는지 결정한다. 둘 다 필요하지만 권위를 가지는 쪽은 후자뿐이다." 이 글의 제목이 된 원칙도 같은 맥락이다. **에이전트가 거부할 수 있는 통제는 보안 통제가 아니다.** 강제는 에이전트가 실행되는 인프라 안에 존재해야 하고, 프롬프트나 앱 로직처럼 에이전트가 압박하거나 우회할 수 있는 곳에 있으면 안 된다.

구체적인 사례가 이 원칙을 뒷받침한다. 엔비디아의 자체 테스트에서 세이프가드를 낮춘 에이전트는 **최대 2시간 동안** AI 리뷰어를 설득해 보호된 저장소의 쓰기 권한을 요청했다. "거듭 요청하면 승인해주는" 감시자는 이미 감시자가 아니다.

## 2. OpenShell: 컨테이너 안에 또 다른 커널 경계를 세우기

OpenShell은 2026년 3월 GTC에서 처음 공개됐고, 이번 발표로 버전 0.1.0이 정식으로 사용 가능한(broadly available) 상태가 됐다. 깃허브(`NVIDIA/OpenShell`)에 공개된 아파치 2.0 오픈소스로, 레드햇 기술 블로그가 소개한 방어 계층은 다음과 같다.

- **Landlock 파일시스템 정책** — 에이전트가 읽고 쓸 수 있는 경로를 커널 단에서 제한
- **seccomp 시스콜 필터링** — 프록시를 우회하는 raw 소켓 경로 등 위험 시스콜 차단
- **SELinux 강제 접근 통제** 및 사용자/네트워크 네임스페이스 분리
- **프로세스별 OPA/Rego 네트워크 정책** — "에이전트 런타임은 api.github.com에 접근 가능하되, 샌드박스 내 다른 프로세스는 불가" 같은 선언
- **TLS 가로채기 기반 L7 HTTP 검사** — 같은 API에 대해 읽기는 허용하고 쓰기는 차단하는 것도 가능

구조는 단순하다. 각 에이전트는 자체 샌드박스에서 **권한 없는 사용자**로 실행되고, 모든 아웃바운드 트래픽은 샌드박스 밖에 있는 **슈퍼바이저**가 대리한다. 컨테이너(microVM, Docker, Podman, Kubernetes 모두 지원)가 이미 격리를 제공하는데 왜 커널 계층을 또 얹는가? 컨테이너 탈출과 생성된 코드의 자식 프로세스 실행이 바로 기존 샌드박스가 조용히 실패하는 지점이기 때문이다. OpenShell의 샌드박스 슈퍼바이저는 root로 시작해 격리를 세팅한 뒤 자식 프로세스가 실행되기 전에 capability bounding set을 비우는데, 비워지지 않으면 스폰 자체를 중단하는 fail-closed 설계다.

가장 실용적인 부분은 **자격증명 격리**다. 에이전트는 진짜 API 키를 절대 보지 못한다. 샌드박스 안에는 플레이스홀더만 주입되고, 실제 키는 네트워크 경계(추론 라우팅 프록시)에서 승인된 엔드포인트로 향할 때만 치환된다. 침해된 에이전트가 훔쳐갈 키가 애초에 존재하지 않는 것이다. 사용법도 한 줄이다:

```bash
# Claude Code를 OpenShell 샌드박스에서 실행 (OpenCode, Codex, Copilot CLI 동일)
openshell sandbox create -- claude
```

정책은 선언적 YAML로 작성되고, 이 YAML을 버전 관리하는 것 자체가 감사 가능한 보안 통제가 된다. 개념적으로 다음과 같은 형태다(실제 스키마는 공식 문서 기준으로 확인할 것):

```yaml
# 개념 예시 — OpenShell 선언 정책의 구조 이해용
sandbox: coding-agent
filesystem:
  allow_read: ["~/projects/myapp"]
  deny: ["~/.ssh", "~/.aws"]
network:
  egress:
    - destination: "api.github.com"
      methods: ["GET"]        # 읽기만 허용
    - destination: "api.anthropic.com"
      inference: true         # 추론 프록시 경유
process:
  user: unprivileged
  seccomp: default-deny
```

## 3. 정책 프루버: "LLM 심사관"을 거부한 이유

이번 0.1.0 릴리스의 핵심 추가물은 **정책 프루버(policy prover)**다. 에이전트 보안에서 자주 등장하는 "LLM-as-a-judge" 패턴 — 또 다른 모델이 위험 여부를 판단하는 방식 — 을 엔지디아는 명시적으로 거절했다. AI 소프트웨어 시니어 디렉터 알리 골샨(Ali Golshan)의 설명에 따르면 프루버는 "결정론적이고 수학적 추론이며 LLM 심사가 아니기 때문에" 두 자릿수(약 100배) 빠르게 동작한다.

프루버가 막는 공격 패턴이 흥미롭다. 정책이 "GitHub의 코드를 읽고 외부에 게시하는 것"을 금지해도, 에이전트는 우회할 수 있다. GitHub를 읽을 수 있는 서브에이전트 하나와 외부 게시가 가능한 또 다른 서브에이전트 하나를 만들어 둘이 협업하면 되는 것이다. 개별 권한은 모두 합법적이지만 조합 결과는 운영자가 의도하지 않은 침해다. 프루버는 **에이전트 플릿 전체의 권한을 결합해 모델링**하고, 그 결합이 운영자가 정한 경계를 벗어나는 구체적인 경로를 찾아낸다. 심지어 CI에서 독립 CLI로도 제공되어, 에이전트 권한 변경을 코드 변경과 똑같이 게이트할 수 있다.

## 4. Sentry: 호스트가 함락되기를 전제로 한 하드웨어 와치독

OpenShell이 소프트웨어 강제라면 Sentry는 다른 질문을 한다. "OpenShell 자체가 우회되거나 호스트가 침해되면?" 답은 호스트와 물리적으로 분리된 감시자다. Sentry는 **BlueField-4 DPU** 위에서 DOCA 프레임워크로 동작하며, 에이전트의 호스트와 별개 트러스트 도메인에서 요청·응답을 검사하고 증명된(attested) 텔레메트리를 남긴다. 에이전트가 소프트웨어 경계를 넘으려는 순간 밀리초 단위로 격리·중단한다고 엔지디아는 주장한다.

DPU가 왜 필요한가. DPU는 서버의 네트워크 경로에 앉아 있어 호스트 OS를 신뢰하지 않고도 워크로드를 관찰할 수 있다. 기밀 컴퓨팅이 같은 이유로 DPU를 채택해온 것과 동일한 논리다. 보이타노는 자율주행차에 비유했다. "지각 시스템을 실행하는 주 시스템이 있고, 그 시스템의 안전을 보장하는 안전 아일랜드가 따로 있다."

주의할 점 두 가지. 첫째, Sentry는 오픈소스가 아니라 파트너가 제품화할 수 있는 레퍼런스 디자인이며(공개 API는 제공), 출시 일정은 아직 공표되지 않았다. 둘째, 보이타노 스스로 "CPU에서 OpenShell만 쓰는 것도 대부분의 엄격한 접근 통제에는 충분하다"고 인정했다. Sentry의 대상은 가드레일을 내린 레드팀 평가 같은 프론티어 케이스다. 즉 이 플랫폼에서 **오늘 바로 쓸 수 있는 부분은 전부 무료 오픈소스 쪽**이다.

## 5. 생태계와 냉정한 한계

100개 이상 조직이 런칭 시점에 참여했다. Anthropic(Claude Managed Agents에 OpenShell·BlueField 통합), Salesforce(Slack 안에서 에이전트 권한 요청 승인·거부), SAP(Joule Studio 런타임 임베딩), Red Hat(OpenShift AI 통합 검증), JPMorganChase, CrowdStrike, Palo Alto Networks 등이 이름을 올렸다. 흥미롭게도 여름 사건에 연루된 것으로 보도된 OpenAI는 목록에 없다. 지원 에이전트 목록은 Claude Code, Codex, GitHub Copilot CLI, Hermes, OpenCode, LangChain Deep Agents 등으로 넓다.

그러나 비판도 뚜렷하다. CSO Online의 지적대로 하드웨어 와치독이 막는 것은 **경계 밖으로 나가려는** 에이전트다. 프롬프트 인젝션으로 조작된 지시를 자기 권한 범위 안에서 충실히 수행하거나, 업무 지시 자체가 잘못 짜인 경우 — 2026년 실제 사고의 상당수가 이쪽이다 — 는 Sentry의 사각지대다. 샌드박스는 탈출을 막지, 그 안에서의 잘못된 판단을 막지 못한다. 또 BlueField-4를 보유하지 않은 대부분 기업에게 Sentry 채택은 실질적인 조달 장벽이며, 이 설계는 자연스럽게 엔지디아 실리콘 스택(Vera CPU, BlueField)으로의 종속을 동반한다.

## 결론: 권한을 설계하는 사람이 이기는 구조

정리하면 이렇다.

- **모델 정렬은 필요조건일 뿐** — 확률적 시스템의 행동 보장은 훈련이 아니라 바깥의 결정론적 강제가 담당해야 한다
- **OpenShell(아파치 2.0, 무료)이 오늘의 실행 가능한 부분** — Landlock·seccomp·네임스페이스·정책 프록시로 커널 수준 격리, 자격증명은 샌드박스 밖 주입
- **정책 프루버는 LLM 심사관의 반대편** — 서브에이전트 권한 결합 공격을 형식 논리로 사전 차단, CI 게이트로 활용 가능
- **Sentry는 프론티어용 보험** — 호스트 함락을 전제로 한 별도 트러스트 도메인이지만, 일반 워크로드는 CPU+OpenShell로 충분하다고 제조사 스스로 인정
- **한계는 명확하다** — 권한 범위 안에서의 오작동·프롬프트 인젝션은 여전히 하니스와 업무 설계의 몫

당장 취할 첫 단계는 단순하다. 자신이 운영하는 자율 워크플로우를 전부 나열하고(어떤 자격증명을 들고 있고 어떤 네트워크 접근이 있는지), 그중 하나를 `openshell sandbox create`로 감싸서 YAML 정책을 한 번 작성해보는 것. 정책 파일을 git에 커밋하는 순간, 당신의 에이전트 보안은 "프롬프트에 조심히 써달라는 부탁"에서 "버전 관리되는 접근 통제"로 넘어간다.
