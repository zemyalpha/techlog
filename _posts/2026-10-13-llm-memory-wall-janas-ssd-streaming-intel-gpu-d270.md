# RAM 32GB 노트북에서 80B 모델을 돌리는 법 — Janas의 SSD 엑스퍼트 스트리밍과 Intel GPU D270이 무너뜨리는 메모리 월

로컬 LLM 사용자라면 누구나 부딪히는 벽이 하나 있다. 모델이 메모리보다 크면 그냥 돌아가지 않는다는 것. 양자화를 더 세게 하거나, 더 작은 모델로 내려가거나, 아니면 클라우드로 돌아가야 했다. 그런데 2026년 10월 12일, 이 벽을 정면에서 공략하는 소식 두 건이 같은 날 나왔다. 하나는 소프트웨어고, 하나는 하드웨어다.

하나는 **Janas**다. 순수 C로 작성된 오픈소스 추론 엔진으로, RAM 32GB 노트북에서 48.4GB 크기의 Qwen3-Next-80B-A3B 모델을 초당 24토큰(초안 모델 동반 시 37토큰)으로 실행한다. 같은 모델을 llama.cpp로 돌리면 초당 2.8토큰이었다. 다른 하나는 **Intel GPU D270**이다. OCP 글로벌 서밋에서 정식 공개된 이 카드는 HBM 대신 LPDDR5X를 써서 최대 480GB의 메모리를 얹는다. 흥미로운 건 두 접근이 완전히 다른 방향에서 출발해 결국 같은 질문으로 수렴한다는 점이다 — "메모리 부족을 계층 구조로 풀 수 없는가?"

이 글에서 두 접근의 작동 원리를 각각 해부하고, 왜 지금 이런 시도들이 동시에 터져 나오는지, 그리고 실제로 써먹으려면 무엇을 알아야 하는지를 정리한다.

## 1. 문제의 본질: MoE 시대의 메모리 월

최근 공개되는 오픈웨이트 모델 상당수가 Mixture-of-Experts(MoE) 구조다. MoE의 핵심은 희소성(spar­city)이다. 모델 전체 파라미터는 수백억 개지만, 토큰 하나를 처리할 때 실제로 활성화되는 엑스퍼트는 일부다. Qwen3-Next-80B-A3B의 이름 뒤에 붙은 A3B가 그 뜻이다. 총 80B 파라미터 중 토큰당 활성 파라미터는 약 3B라는 뜻이다.

그런데 기존 추론 엔진의 메모리 전략은 이 희소성을 반영하지 못했다. 모델 전체를 RAM이나 VRAM에 올리는 게 원칙이었고, 안 되면 mmap으로 페이지 캐시에 맡겼다. 페이지 캐시는 운영체제가 범용으로 관리하는 것이라 LLM 추론의 접근 패턴 — 어떤 엑스퍼트가 자주 쓰이는지 — 에 맞춰 최적화되어 있지 않다. 결과는 스래싱(thrashing). 디스크에서 읽는 데 시간을 다 쓰는 것이다.

메모리 월은 데이터센터 쪽에서도 마찬가지다. HBM은 대용량으로 올리기에 비싸고 수급도 빠듯하다. 이것이 Intel이 LPDDR5X라는 이례적 선택을 한 배경이기도 하다.

## 2. Janas: SSD를 메모리 계층으로 만드는 소프트웨어

### 2-1. 작동 원리

Janas는 모델 가중치를 디스크에 둔 채, 각 토큰이 필요로 하는 엑스퍼트만 NVMe SSD에서 읽어 온다. 자주 쓰이는 엑스퍼트는 RAM의 인메모리 캐시에 남기고, 나머지는 필요할 때 디스크에서 읽는다. 저자의 설명에 따르면 80B 모델 기준 캐시는 약 19GB까지 자라며, 나머지는 디스크에서 읽힌다.

기술적으로 눈여겨볼 장치가 세 가지다.

**첫째, `O_DIRECT`와 `io_uring`.** 엑스퍼트 읽기가 운영체제 페이지 캐시를 우회한다. 무엇을 RAM에 둘지를 엔진 스스로 제어하겠다는 것이다. 페이지 캐시에 맡기면 제어권이 OS에 있어서 LLM의 접근 패턴에 맞는 캐싱이 어렵다.

**둘째, 엑스퍼트 리드어헤드(read-ahead).** 캐시가 부족할 때는 다음 레이어의 라우터를 미리 적용해, 현재 레이어가 계산하는 동안 필요한 엑스퍼트를 미리 디스크에서 읽어 온다. 긴 프롬프트도 블록 단위로 같은 방식으로 처리한다. 저자 측정으로 4GiB 캐시에서 80B 모델이 4,096토큰을 초당 42.0토큰으로 읽는데, 리드어헤드가 없으면 36.8토큰이라고 한다.

**셋째, 캐시 조건부 라우팅(cache-conditional routing).** 캐시가 전체 엑스퍼트의 5분의 1 미만을 담고 있을 때만, 라우터가 가볍게 판정한 엑스퍼트를 디스크에서 읽지 않고 건너뛰며 그 가중치를 다른 엑스퍼트에 분배한다. Skliar 등이 TMLR 2025에 제안한 기법을 적용한 것이라고 저자는 밝힌다. 4GiB 캐시의 80B 모델에서 초당 20.7토큰이 27.7토큰로 올라가는 대가로, llama.cpp의 최빈 토큰과의 일치율이 400토큰 중 393개에서 384개로 소폭 내려간다. 정확도와 속도의 트레이드오프를 수치로 공개한 점이 인상적이다.

### 2-2. 벤치마크: 저자의 단일 머신 측정

다음 수치는 개발자 본인의 머신(Core Ultra 9 185H, RAM 32GB, NVMe SSD)에서 측정된 것으로, 저자가 공개한 값이다. 검증은 한 대의 머신에만 근거했음을 감안해야 한다.

| 모델 | Janas 읽기/쓰기 (tok/s) | llama.cpp 읽기/쓰기 (tok/s) |
|------|--------------------------|------------------------------|
| Qwen3-Next-80B-A3B (48.4GB) | 62 / 24 (초안 포함 37) | 16 / 2.8 |
| Qwen3-30B-A3B | 135 / 32 | 122 / 15 |
| Qwen3-4B | 193 / 27 | 164 / 18 |
| Qwen3-0.6B | 939 / 130 | 670 / 45 |

읽을 거리가 있는 건 80B 행이다. 모델이 실제로 RAM을 초과하는 유일한 경우이고, 여기서 격차가 열 배 가까이 벌어진다. 반면 RAM에 넉넉히 들어가는 작은 모델에서는 격차가 줄어든다. 증명되는 것은 단순하다. 메모리가 부족할 때의 추론 속도는 엔진이 얼마나 똑똑하게 I/O를 하느냐가 결정한다. 저장소 읽기 튜닝에 한 번도 신경 쓰지 않은 범용 엔진(llama.cpp)과, 그것만을 위해 설계된 엔진(Janas)의 차이다.

### 2-3. 직접 돌려보기

Janas는 C 컴파일러와 curl 외에 아무것도 요구하지 않는다. 우분투 22.04 이상 또는 데비안에서 루트 권한 없이 다음 한 줄로 빌드·테스트·벤치마크가 가능하다.

```bash
git clone https://github.com/prabanta-dev/janas && cd janas
./tools/janas-try.sh
```

이 스크립트는 빌드 후 모델을 내려받아 SHA-256을 검증하고, 변환 결과를 공개된 지문과 대조한 뒤, 온도 0에서의 출력이 다른 머신들과 동일한지 비교하고, 마지막으로 속도를 측정해 보고서를 만든다. 세 가지 난이도(quick 2.5GB / medium 22GB / full 약 52GB 다운로드)를 제공한다.

모델은 허깅페이스의 `prabanta-dev` 계정 하에 `.jns` 형식으로 사전 변환되어 배포되며(글쓴 시점 기준 14개 리포지토리), `janas-get` 명령이 무결성 검증까지 해 주며 내려받는다. 일상 사용용으로는 `janas-chat`(채팅), OpenAI 호환 HTTP 서버인 `janas-server`, MCP 서버인 `janas-mcp`가 포함되어 있어 기존 도구 체인에 붙일 수 있다.

```bash
# 빌드 + 자동 검증 + 속도 측정 (quick 단계: Qwen3-4B, 약 2.5GB 다운로드)
git clone https://github.com/prabanta-dev/janas && cd janas
./tools/janas-try.sh

# 여유 메모리가 부족한 머신에서는 --cache 플래그로 엑스퍼트 캐시 상한 지정,
# 내장 GPU를 아예 쓰지 않으려면 환경변수 JANAS_GPU=0 설정
```

### 2-4. 반드시 알아야 할 한계

저장소(리포지토리 README)는 스스로를 "실험이지 제품이 아니다(an experiment, not a product)"라고 못 박는다. 구체적인 한계는 다음과 같다.

- **측정 근거가 단일 머신이다.** AMD CPU, AVX-VNNI 없는 인텔 CPU, 분리형 GPU, SATA SSD, 16GB 이하 머신에서의 성능은 미검증이다. 저자는 `janas-bench` 리포트를 공개적으로 요청하고 있다.
- **자원 사용이 공격적이다.** 여유 메모리를 엑스퍼트 캐시로 채우고 디스크를 최대 속도로 읽는다. 여유가 부족한 머신에서는 스왑으로 시스템이 느려질 수 있고, 저자 자신도 GPU 사용 중 드라이버 리셋으로 데스크톱이 다운된 사례 한 건을 인정한다.
- **API와 명령행이 수시로 바뀐다.** 안정성을 약속하는 것은 `.jns` 모델 형식뿐이다.

그래도 2026년 9월 20일 저장소가 만들어진 뒤 한 달도 되지 않아 스타 100개를 넘기고 해커뉴스 프론트페이지에 올랐다는 건, "메모리 월을 I/O 문제로 바꾼다"는 발상 자체에 대한 수요의 증거다.

## 3. Intel GPU D270: 하드웨어로 푸는 같은 문제

소프트웨어로 디스크를 메모리 계층으로 끌어들이는 Janas와 달리, 인텔은 아예 메모리 계층 자체를 재설계한 칩을 내놨다. 10월 12일 OCP 글로벌 서밋에서 공개된 **Intel GPU D270**이다. 작년까지 '크레센트 아일랜드(Crescent Island)'라는 코드명으로 알려졌던 제품이 GPU D 시리즈의 첫 칩으로 이름을 확정했다.

### 3-1. 스펙

인텔이 이번 서밋에서 확정 공개한 사양은 다음과 같다.

| 항목 | Intel GPU D270 |
|------|----------------|
| 아키텍처 | Xe3P (Xe3 강화판) |
| Xe 코어 / XMX 엔진 | 32 / 256 (클록 약 2.5GHz) |
| 피크 매트릭스 처리량 (FP8) | 1.3 PFLOPS |
| 피크 벡터 처리량 (FP64) | 10.2 TFLOPS |
| 메모리 (최대) | 480GB LPDDR5X (ODM) / 160GB (인텔 자체 설계) |
| 메모리 대역폭 | 1.5TB/s (약 9,375Mbps × 1280비트) |
| L2 캐시 | 32MB |
| 인터페이스 | PCIe Gen5 x16 |
| TDP / 폼팩터 | 350W / PCIe CEM 공랭 |

이 칩의 승부수는 계산 성능이 아니라 메모리 용량이다. FP8 1.3 PFLOPS는 엔비디아 블랙웰 울트라나 AMD MI455X 같은 최상위 칩보다 낮다. 인텔도 이를 숨기지 않는다. 대신 더 작고 저렴하게 만들고, 희소한 HBM을 쓰지 않음으로써 첨단 패키징 수급 경쟁을 피하고 대용량을 확보한다. LPDDR5X는 HBM만큼 빠르진 않지만(1.5TB/s) 용량당 비용이 훨씬 낮고 공급이 안정적이다. 추론 워크로드는 학습만큼 대역폭에 목숨 걸 필요가 없고, 컨텍스트가 커질수록 KV 캐시가 먹는 메모리가 늘어나므로 '느리지만 많은' 메모리는 실용적인 조합이다. 480GB 카드 여덟 장이면 한 서버에 3.8TB의 GPU 메모리를 얹을 수 있다.

의미도 크다. 이것은 인텔이 2021년 폰테 베키오 이후 내놓는 첫 상용 AI 데이터센터 GPU다. 그 사이 후속작 두 개(2023년 리알토 브리지, 2025년 팰컨 쇼어)가 연달아 취소됐던 인텔의 재기 시도이기도 하다. 보도에 따르면 고객 샘플링이 진행 중이며 본격 공급은 2027년 목표다.

## 4. 두 접근이 말해 주는 것: 계층화된 희소성

Janas와 D270은 표면적으로 아무 상관 없어 보이지만, 사실 같은 원리의 소프트웨어 구현과 하드웨어 구현이다.

**핵심 원리: 필요한 것만 가까이 두고, 나머지는 아래 계층에 둔다.**

- Janas는 모델 수준에서 이걸 한다. 토큰당 활성 엑스퍼트(A3B라면 약 3B 파라미터어치)만 RAM 캐시에 두고, 나머지 77B는 SSD에 둔다. 핫 엑스퍼트가 캐시에 머물면 디스크 읽기는 튕겨 나가듯 캐시에서 처리된다.
- D270은 서버 수준에서 이걸 한다. 자주 쓰는 데이터는 480GB LPDDR5X와 32MB L2에 두고, 나머지는 호스트 메모리와 스토리지에 둔다.

둘 다 전제하는 조건도 같다. **추론 워크로드의 접근이 균등하지 않다는 것.** MoE 라우팅은 특정 엑스퍼트에 편중되고, 토큰 생성은 어텐션에서 최근 컨텍스트에 편중된다. 이 편중을 이용하면 전체를 빠른 메모리에 올리지 않고도 속도를 유지할 수 있다. 반대로 접근이 고르게 흩어지면 둘 다 무너진다. Janas의 경우 캐시 미스가 늘면 디스크가 병목이 되고, D270의 경우 대역폭 부족이 드러난다.

일상에 주는 교훈은 명확하다. 로컬 LLM을 쓸 때 "이 모델이 RAM에 들어가나?"만 묻는 시대는 끝나고 있다. "활성 파라미터는 얼마고, 내 저장소 대역폭은 얼마인가?"가 새로운 질문이다. NVMe SSD가 5~7GB/s를 내는 요즘, MoE 모델의 활성 엑스퍼트 몇 GB를 실시간으로 받아내는 건 물리적으로 가능한 일이 된 것이다.

## 5. 결론: 메모리 월은 무너지고 있는가

- 같은 날(10월 12일) 발표된 Janas와 Intel GPU D270은 LLM 추론의 최대 병목인 메모리를 각각 소프트웨어와 하드웨어로 공략한다.
- Janas는 `O_DIRECT`·`io_uring` 기반 엑스퍼트 캐시와 리드어헤드로, RAM 32GB 노트북에서 48.4GB 80B 모델을 llama.cpp 대비 열 배 가까이 빠른 초당 24~37토큰으로 실행했다(저자 단일 머신 측정).
- Intel GPU D270은 HBM 대신 LPDDR5X 480GB를 얹어 용량당 비용을 낮춘 추론 전용 GPU다. FP8 1.3 PFLOPS, 1.5TB/s, 350W 공랩 PCIe 카드로 2027년 본격 공급이 목표다.
- 두 접근의 공통 원리는 계층화된 희소성 — 자주 쓰는 것만 빠른 계층에 두는 것 — 이며, 이는 MoE와 KV 캐시라는 추론 워크로드의 편중 덕분에 성립한다.
- 당장 시도해 볼 것은 한 줄이다: `git clone https://github.com/prabanta-dev/janas && cd janas && ./tools/janas-try.sh`. quick 단계(2.5GB)면 커피 한 잔 시간에 자기 머신에서 검증할 수 있다.

메모리 월이 완전히 무너졌다고 하기엔 이르다. Janas는 한 대의 머신에서 측정된 실험 단계 프로젝트고, D270은 아직 샘플링 중인 미출시 칩이다. 그러나 벽에 금이 가는 소리는 확실히 들린다. 모델 크기가 RAM 문제에서 I/O 문제로, HBM 수급 문제에서 메모리 계층 설계 문제로 바뀌는 순간, 로컬에서 돌릴 수 있는 모델의 상한은 다시 정해진다.
