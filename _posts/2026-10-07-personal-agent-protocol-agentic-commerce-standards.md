# 에이전트가 대신 사는 시대의 관문 — Personal Agent Protocol은 무엁을 바꾸려 하나

2026년 들어 개인 AI 에이전트는 검색에 답을 내놓는 단계를 지나, 예약을 하고 물건을 사고 주문을 취소하는 단계로 넘어갔다. 그런데 정작 그 에이전트들이 기업 웹사이트에 도착하는 방식은 놀랍게도 원시적이다. 사람처럼 페이지를 로드하고, 폼을 클릭하고, 안 되면 고객센터에 전화를 건다. Meta의 개인 에이전트 Muse가 쇼핑몰에서 제대로 자신을 식별하지 못하자 아마존이 접근을 차단했다는 보도가 있었고, TechCrunch 보도에 따르면 델타항공은 제3자 에이전트용 예약 통합을 두고 있지 않으며 유나이티드항공은 이용약관상 사전 서면 허가 없는 자동화 접근을 금지하고 있다.

문제는 기술이 아니라 **관문(gate)** 이다. 기업 입장에서는 "지금 들어온 이 에이전트가 누구를 대신하고, 무슨 권한이 있으며, 무엇을 하려는지" 알 방법이 없다. 이 관문의 설계도를 두고 2026년 가을, 표준 경쟁이 시작됐다.

## 1. 시초: 여섯 은행이 먼저 판을 깔았다

9월 22일, ASB 뱅크·뱅크오브아메리카·캐피탈원·호주 커먼웰스뱅크·ING·네트웨스트 그룹 여섯 글로벌 은행은 「Building Trust in Agentic Commerce」라는 공동 원칙 문서를 발표했다. 다섯 가지 축이다.

- **투명성**: 거래에 에이전트가 개입했는지, 누구를 대신하는지 모든 당사자가 알아야 한다. 후원(sponsored) 상품을 우선 노출하는지도 공개되어야 한다.
- **안전성**: 소비자가 에이전트에게 위임한 권한을 조회·관리할 수 있어야 하고, 결제 승인은 안전하고 감사 가능한 방식으로 이뤄져야 한다.
- **프라이버시와 데이터**: 고객 지시·인증·구매 의도·결과에 대한 감사 가능한 기록을 남기고 데이터 접근을 제한할 것.
- **선택**: 소비자와 가맹점이 부당한 제약 없이 서비스를 고를 수 있어야 한다.
- **상호운용성**: 핵심 신뢰 기능에는 공통 접근을, 차별화 영역에는 다양성을 허용할 것.

눈여겨볼 대목은 책임 원칙이다. 문서는 분쟁 시 책임이 "리스크나 오류가 유입된 지점"을 반영해야 한다고 적었다. 카드 결제 생태계에서 갑신·을신 사이에 정착했던 책임 배분 논리를 에이전트 거래로 확장하겠다는 것이다. 다만 이 문서는 자발적·비구속적이며 구현 로드맵은 후속 문서로 미뤄둔 상태다.

## 2. 본론: Personal Agent Protocol, 10월 6일

2주 뒤인 10월 6일, Sierra Summit에서 Sierra와 Meta가 **Personal Agent Protocol(PAP)** 발표했다. 공동 참여사는 Genesys, Instinct, Rocket, Shopify, Stripe, Walmart. 브렛 테일러(전 Salesforce 공동 CEO, 현 OpenAI Group 이사장)와 클레이 베이버가 공동으로 발표했으며, 누구나 구현할 수 있는 개방형 표준을 표방한다. v0.1 사양은 10월 중 공개 예정이고, 디자인 워크숍과 레퍼런스 구현체 공개도 함께 계획돼 있다.

핵심 설계는 의외로 담백하다. 새로운 인증 체계를 발명하는 대신 **기존의 OAuth를 그대로 세운 것**이다.

1. **발견**: 개인 에이전트가 기업 웹사이트에서 회사가 제공하는 것과 연결 방법을 발견한다.
2. **세션 시작**: 게스트로 시작할 수 있다. 재고 확인이나 반품 정책 문의 정도는 로그인 없이도 가능하다.
3. **승격**: 계정 접근이 필요한 작업이면 기업 페이지에서 로그인하거나 에이전트에 저장된 자격 증명을 쓴다. 소비자는 읽기 전용(read-only)인지 쓰기(write) 권한인지 직접 결정한다.
4. **경로 선택**: 이후 작업은 기업이 판단한 최적 경로로 진행한다 — 기업의 **웹사이트**, **API(MCP·OpenAPI 기반)**, 또는 **기업 자체 에이전트**와의 대화. 보증 청구 같은 대화형 업무는 기업 에이전트가, 단순 조회는 API가 맡는 식이다.

요약하면 권한의 방향이 양쪽에서 정해진다. **소비자는 에이전트의 접근 범위를 정하고, 기업은 그 에이전트가 할 수 있는 일을 정한다.** 세션은 채널을 넘어 유지되어, 로그인 전에 물었던 질문과 로그인 후의 주문 변경이 같은 방문으로 이어진다.

Stripe의 케빈 밀러(결제 책임자)는 "고객이 에이전트를 보낼 때도 본인이 왔을 때와 같은 서비스를 기대한다"며 표준 참여 이유를 밝혔고, 로켓의 CTO는 에이전트가 집 탐색부터 모기지 승인까지 실시간으로 이동하는 시나리오를 언급했다.

## 3. 같은 날 나온 경쟁자: Decagon PACT

표준 경쟁이라 부른 이유가 있다. PAP 발표와 같은 날, CS 자동화 기업 Decagon도 **PACT(Personal Agent Consent and Trust)** 프로토콜을 오픈소스로 공개했다. Decagon은 10월 1일 자사 행사에서 이미 Personal Agent Gateway — 상대가 사람인지 에이전트인지 감지하는 게이트웨이 — 를 소개했고, PACT는 그 권한 검증 계층이다.

두 표준의 지향은 다르다. PAP가 "에이전트가 기업에 **어떻게 접속하는가**"(인증·경로·권한 위임)를 다룬다면, PACT는 "기업이 에이전트를 **어떻게 검증하고 감사하는가**"(동의 증명·권한 확인·감사 기록)에 방점을 둔다. Decagon을 인용한 업계 정리는 두 발표가 몇 시간 차이로 나왔다고 전했다. 상충하기보다는 스택의 다른 층을 채우는 관계에 가깝고, Decagon도 PAP 작업에 합류한 것으로 알려져 있다.

## 4. 서비스 담당자가 지금 할 수 있는 일

v0.1 사양이 아직 공개 전이므로 특정 구현을 맞추는 것은 이르다. 그러나 방향은 OAuth와 MCP라는 이미 검증된 표준 위에 서 있으므로, 지금 준비할 것은 명확하다.

**첫째, 트래픽 로그로 실태부터 파악한다.** 에이전트가 이미 사이트를 긁고 있는지 확인한다:

```bash
# 에이전트성 접근 흔적을 웹로그에서 대략 확인 (nginx 예시)
grep -Ei "GPTBot|ClaudeBot|Perplexity|agent" /var/log/nginx/access.log \
  | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

**둘째, 읽기와 쓰기를 분리한 권한 모델을 미리 설계한다.** PAP의 핵심 구분은 read-only vs write다. OAuth 스코프 관점에서 미리 정리해두면 사양 공개 후 대응이 빨라진다:

```yaml
# 에이전트 권한 스코프 초안 (예시)
agent_scopes:
  catalog: read        # 재고·가격 조회
  orders: read         # 주문 상태 조회
  orders.modify: write # 주문 변경·취소 (명시적 동의 필요)
  payment: deny        # 결제 수단 조회는 기본 거부
```

**셋째, MCP 엔드포인트 노출을 검토한다.** PAP가 웹사이트·API·기업 에이전트 세 경로를 공식 경로로 명시했으므로, API를 MCP로 감싸 노출하는 것은 셋 중 가장 통제 가능한 선택이다. 응답 형식·레이트리밋·감사 로그를 기업이 정의할 수 있기 때문이다.

**넷째, 감사 기록 설계.** 은행 연합이 명시한 대로 "고객이 에이전트에게 무엇을 지시했고, 어떤 권한을 줬고, 무엇이 일어났는지"는 분쟁 대응의 기반이다. 에이전트 세션에도 사용자 세션과 동등한 감사 로그를 남기는 구조를 지금 만들어야 한다.

## 5. 남은 질문들

표준이 나왔다고 끝나는 건 아니다. 첫째, **참여 유무가 곧 생태계다.** 은행 연합도, PAP도 자발적 참여를 전제로 한다. 아마존·항공사처럼 접근을 막는 기업이 표준에 합류할지가 관건이다. 둘째, **책임 배분의 실효성.** "오류가 유입된 지점에 책임이 따른다"는 원칙은 그 지점을 증명할 감사 데이터가 있어야만 작동한다. 셋째, **표준 난립 리스크.** PAP와 PACT가 공존하는 현재 구도가 통합으로 수렴할지, 소비자 에이전트와 기업 에이전트로 계층이 갈라질지는 v0.1 공개 이후에 판가름 난다.

## 결론

- 여섯 은행의 신뢰 원칙(9/22)이 방향을 제시했고, Personal Agent Protocol(10/6)이 OAuth 기반의 구체적 접속 설계로, Decagon PACT가 동의·감사 계층으로 뒤를 이었다.
- PAP의 핵심은 발명이 아니라 합의다 — OAuth 인증, read/write 권한 분리, 웹사이트·API(MCP/OpenAPI)·기업 에이전트 세 경로라는 이미 존재하는 부품의 조립.
- 서비스 담당자가 지금 할 일은 사양이 아니라 기초 공사다: 에이전트 트래픽 실태 파악, 읽기/쓰기 분리 권한 설계, MCP 노출 검토, 감사 로그 구조화.
- v0.1 사양이 10월 중 공개 예정이므로, OAuth 스코프와 MCP 인터페이스를 미리 다듬어 둔 팀이 첫 달에 유리하다.

첫 단계는 작다. 오늘 자신의 웹로그에서 에이전트 흔적을 확인하는 것부터 시작해보면 된다.
