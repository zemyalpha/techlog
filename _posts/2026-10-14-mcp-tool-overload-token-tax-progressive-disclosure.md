# 도구 30개가 에이전트를 멍청하게 만든다 — MCP 툴 정의의 '토큰 세금'과 이를 없애는 두 가지 패턴

MCP 서버를 여러 개 붙인 에이전트를 운영해 본 사람이라면 이상한 경험을 한다. 컨텍스트 창은 반도 안 찼는데 비용은 폭증하고, 도구를 잘못 고르는 빈도가 눈에 띄게 늘어난다. 모델이 나빠진 게 아니다. **모델이 일을 시작하기도 전에 도구 정의가 컨텍스트를 갉아먹고 있기 때문이다.**

Anthropic의 자체 문서는 이 문제에 숫자를 붙였다. GitHub, Slack, Sentry, Grafana, Splunk 다섯 개 서버를 연결하는 "전형적인" 멀티서버 구성만으로 도구 정의에 약 55,000 토큰이 소모된다는 것이다. 20만 토큰 컨텍스트 기준으로 모델이 사용자 질문 한 글자도 읽기 전에 이미 예산의 4분의 1 이상이 지출되는 셈이다. Anthropic은 내부 에이전트 구성에서 최대 134K 토큰의 도구 정의를 관측했다고 밝혔다.

이 글에서는 이 '토큰 세금'이 왜 생기는지, 왜 비용만이 아니라 정확도까지 무너뜨리는지, 그리고 2025년 11월 이후 업계가 수렴한 두 가지 해결 패턴 — **도구 검색(deferred loading)**과 **코드 실행으로 도구 호출** — 을 실전 코드와 함께 정리한다.

## 1. 토큰 세금의 정체: 매 요청마다 다시 내는 정의 비용

LLM API에서 도구는 공짜가 아니다. 도구의 이름, 설명, 인자 스키마, 인자별 설명이 전부 프롬프트 접두사에 직렬화되어 매 요청마다 모델 앞에 놓인다. Anthropic이 공개한 측정값을 보면 서버별 규모가 감이 온다.

- **GitHub MCP 서버**: 도구 35개, 약 26,000 토큰
- **Slack MCP 서버**: 도구 11개, 약 21,000 토큰
- **5개 서버 합산**: 약 55,000 토큰 (사용자 입력 0바이트 상태)

핵심은 이 비용이 **매 턴마다 반복 청구**된다는 점이다. 에이전트가 10턴 대화를 하면, 그중 단 한 번도 호출하지 않는 도구의 정의 토큰도 10번 지불한다. 프롬프트 캐싱으로 원가는 줄일 수 있어도 컨텍스트 창이라는 물리적 예산은 그대로 소모된다. 도구 정의는 캐시 히트 여부와 무관하게 창을 차지하는 점유 비용이다.

## 2. 비용보다 심각한 문제: 30~50개 임계점에서 무너지는 선택 정확도

토큰 세금은 청구서에 보이지만, 진짜 문제는 에러율에 보인다. Anthropic 문서는 도구가 30~50개를 넘어서면 모델이 올바른 도구를 고르는 능력이 유의미하게 저하된다고 명시한다. 학계 측정도 방향이 같다. RAG-MCP 논문은 검색 계층 없이 100개 도구에서 13.62%였던 도구 선택 정확도가, 카탈로그 앞에 검색 계층을 두자 43.13%로 오른다고 보고했다.

즉 "도구를 많이 달수록 에이전트가 똑똑해진다"는 직관은 30개 부근에서 깨진다. MCP 서버 몇 개를 합치면 200개 이상의 도구 카탈로그는 금방 만들어지므로, 멀티서버 에이전트는 기본 구성만으로 이미 임계점을 지난 상태로 출발한다.

## 3. 패턴 1: 도구 검색(tool search) — 정의를 나중에 불러오기

첫 번째 해결 패턴은 단순하다. **도구 정의를 컨텍스트에 미리 싣지 말고, 모델이 필요할 때 검색해서 로드하게 한다.**

Anthropic은 2025년 11월 베타로 출시했던 tool search tool을 현재 별도의 베타 헤더 없이 정식 제공한다. 메커니즘은 API 요청의 `tools` 배열에 검색 도구 하나를 추가하고, 나머지 도구에 `defer_loading: true`를 표시하는 것뿐이다.

```python
response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=2048,
    messages=[{"role": "user", "content": "서울 날씨 어때?"}],
    tools=[
        {
            "type": "tool_search_tool_regex_20251119",
            "name": "tool_search_tool_regex",
        },
        {
            "name": "get_weather",
            "description": "특정 위치의 날씨를 조회한다",
            "input_schema": {
                "type": "object",
                "properties": {"location": {"type": "string"}},
                "required": ["location"],
            },
            "defer_loading": True,  # 정의가 컨텍스트에 실리지 않음
        },
    ],
)
```

동작 방식: 모델은 컨텍스트에서 검색 도구(약 500 토큰)만 본다. 도구가 필요해지면 정규식(`tool_search_tool_regex_20251119`)이나 자연어 BM25(`tool_search_tool_bm25_20251119`)로 카탈로그를 검색하고, 매칭된 도구가 `tool_reference` 블록으로 확장되어 비로소 정의가 컨텍스트에 들어온다. 검색 대상은 도구 이름·설명·인자 이름·인자 설명 전부다.

효과는 Anthropic 엔지니어링 포스트와 문서에서 각각 측정됐다.

| 측정 | 적용 전 | 적용 후 | 변화 |
|---|---|---|---|
| 측정 환경의 도구 정의 프리앰블 | 약 77,000 토큰 | 약 8,700 토큰 | -85% |
| 로드되는 도구 수 | 전체 | 검색당 3~5개 | — |
| 도구 선택 정확도 (Opus 4) | 49% | 74% | +25%p |
| 도구 선택 정확도 (Opus 4.5) | 79.5% | 88.1% | +8.6%p |

운영상 제약도 관대한 편이다. 요청당 최대 10,000개까지 도구를 지연 로드할 수 있고, 검색 한 번에 최대 5개의 매칭을 반환한다. 정규식은 200자, BM25 쿼리는 500자 제한. 한 가지 하드 룰은 최소 한 개의 도구는 지연 없이 남겨야 한다(보통 검색 도구 자체)는 것 — 전부 지연시키면 `All tools cannot be deferred` 400 에러가 난다.

**주의할 점**도 분명하다. 도구 이름과 설명이 성기면 검색 자체가 실패한다. "지연 로드는 도구 설명 품질에 대한 보증"이라는 말이 과언이 아니다. Anthropic도 도구가 10개 미만이거나, 모든 요청에서 모든 도구를 쓰거나, 정의 합계가 100 토큰 미만이라면 이 기능을 쓰지 말라고 권한다. 10개 이상 + 정의 1만 토큰 초과 + MCP 다중 서버 집계 상황에서 빛을 본다.

## 4. 패턴 2: 코드 실행으로 도구 호출 — 중간 결과를 모델 밖으로

두 번째 패턴은 더 급진적이다. **모델이 도구를 직접 호출하지 말고, 도구를 호출하는 코드를 작성하게 하라.**

기존 흐름에서는 모델이 도구 결과를 읽고, 가공해 다음 호출의 인자로 쓴다. 데이터가 모델을 왕복할 때마다 컨텍스트가 부풀어 오른다. Anthropic의 예시인 "Google Drive 회의록을 Salesforce로 복사" 작업에서 모델은 회의록을 받으려고 한 번 다 읽고, 보내려고 다시 쓴다. 2시간 짜리 영업 회의 녹취라면 모델이 내용을 이해할 필요도 없으면서 50,000 토큰을 추가 처리하는 셈이다.

코드 실행 패턴에서는 모델이 도구 카탈로그를 타입이 붙은 함수의 파일시스템처럼 취급하고, 샌드박스에서 실행될 스크립트를 작성한다. 중간 결과는 코드 안에서 흐르고 모델 컨텍스트에는 최종 출력만 들어온다. Anthropic 엔지니어링 포스트는 이 패턴으로 특정 워크플로우의 컨텍스트 소모가 150,000 토큰에서 2,000 토큰으로, 98.7% 감소했다고 보고했다. Cloudflare도 같은 해 9월 "Code Mode"라는 이름으로 같은 아이디어를 발표하며 "LLM은 MCP를 직접 호출하는 것보다 MCP를 호출하는 코드를 작성하는 데 더 뛰어나다"고 요약했다.

이 패턴의 API 버전이 programmatic tool calling이다. Anthropic 측정으로 복잡한 리서치 태스크의 평균 토큰 사용량이 43,588에서 27,297으로 37% 감소했고, 에이전트 검색 벤치마크(BrowseComp, DeepSearchQA)에서는 평균 11% 성능 향상과 24% 적은 입력 토큰을 동시에 달성했다. 성능과 비용이 반대 방향으로 움직이는 드문 개선이다.

다만 공짜는 아니다. 순차적인 단일 호출로 끝나는 태스크에서는 오히려 코드 생성 오버헤드가 크고, 일부 벤치마크에서는 실행 시간이 길어지는 트레이드오프가 보고된다. 또한 모델이 작성한 코드가 도구의 자격증명에 접근하는 샌드박스는 아키텍처에서 가장 특권적인 프로세스가 되므로, 격리 경계 설계가 전제 조건이다.

## 5. 도구와 스펙의 수렴: 이제 플랫폼 차원의 기본값이 되었다

이 두 패턴은 이미 개발자 도구와 프로토콜 스펙으로 침투했다.

- **Claude Code 2.1.x**는 MCP 도구 정의가 컨텍스트 창의 일정 비중을 넘으면 도구 검색으로 지연 로드하는 것을 기본 동작으로 켰다(`ENABLE_TOOL_SEARCH` 환경변수로 제어). 단일 도구 결과가 10,000 토큰을 넘으면 경고를 띄우고 25,000 토큰 기본 상한을 둔다.
- **MCP 2026-07-28 스펙**은 서버가 `tools/list`를 결정론적 순서로 반환해 프롬프트 캐시 히트율을 높이고, 결과에 `ttlMs` 캐시 힌트를 붙이도록 권한다. 8월 로드맵에는 서버 주도 "progressive tool discovery"가 올라와 있다.
- 클라이언트 진영도 각자 필터를 갖췄다. Gemini CLI는 `includeTools`/`excludeTools`, Cursor는 URL/커맨드 패턴 기반 허용 목록, Claude Code는 관리자용 `allowedMcpServers`/`deniedMcpServers` 정책을 제공한다.

Cloudflare, Anthropic, Cursor가 서로 조율 없이 같은 결론에 도달했다는 점이 이 패턴의 신뢰도를 보여준다. **미리 다 싣지 말고, 필요할 때 찾아서 불러라.** 파일시스템과 bash가 40년간 증명한 progressive disclosure를 에이전트가 다시 배운 것이다.

## 결론: 도구 카탈로그는 창고지기처럼 운영하라

- MCP 서버 5개 병합만으로 도구 정의 55,000 토큰이 매 요청 소모된다. 이것은 비용 문제이기 전에 컨텍스트 예산 문제다.
- 도구 30~50개를 넘으면 선택 정확도가 무너진다. "모델이 멍해졌다"고 느껴지면 먼저 도구 수부터 세보라.
- 1차 처방은 `defer_loading: true` + tool search다. 정의 토큰 85% 감소, 정확도 +25%p(Opus 4)가 보고됐다. 단, 도구 10개 미만이면 쓰지 않는다.
- 데이터가 크게 흐르는 워크플로우는 코드 실행 패턴을 검토하라. 98.7% 컨텍스트 감소 사례가 있지만, 샌드박스 격리 설계가 전제다.
- 첫 단계는 간단하다. 오늘 운영 중인 에이전트의 도구 정의가 몇 토큰인지 측정하는 것부터다. API 응답의 `usage` 필드에 도구 없이는 존재하지 않았을 프리앰블이 그대로 찍혀 나온다.
