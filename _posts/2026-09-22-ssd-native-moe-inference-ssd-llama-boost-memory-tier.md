# RTX 5090 한 장에 1조 파라미터 MoE를 올리는 방법 — SSD-LLaMA의 3계층 캐시와 BOOST의 대역폭 합산

2026년의 오픈 웨이트 프론티어 모델은 거의 예외 없이 Mixture-of-Experts(MoE) 구조다. 토큰마다 전체 전문가 중 일부만 활성화되므로 연산량은 적지만, 문제는 저장이다. 라우터가 어떤 전문가를 고를지는 실행해봐야 알기 때문에, 로컬 추론이라도 **전체 전문가 풀을 전부 갖고 있어야 한다**. DeepSeek-V4-Flash는 284B 중 13B만 활성화하지만 저장은 142GB(4비트 기준)가 필요하고, Kimi-K2.7-Code는 1조 파라미터라 500GB가 넘는다.

소비자용 VRAM은 32GB가 한계다. RAM을 가득 채워도 부족하다. 그런데 2026년 9월 arXiv에 발표된 두 논문이 이 전제를 각각 다른 방향으로 무너뜨렸다. 하나는 SSD를 1급 메모리 계층으로 끌어올린 **SSD-LLaMA**(arXiv:2609.18110)이고, 다른 하나는 데이터센터 쪽에서 HBM과 호스트 메모리의 대역폭을 **동시에** 쓰는 **BOOST**(arXiv:2609.13592)다. 이 글에서 두 논문의 핵심 메커니즘과 실험 수치를 짚고, 로컬에서 거대 MoE를 돌리려는 사람이 당장 적용할 수 있는 원칙을 정리한다.

## 1. SSD는 이제 '느린 디스크'가 아니다

SSD-LLaMA 논문이 출발하는 관찰은 단순하다. 현재 PCIe 5.0 SSD의 순차 대역폭은 **14.8 GB/s**로, 싱글채널 DDR3-1600(12.8 GB/s)을 넘고 싱글채널 DDR4-1866(14.9 GB/s)과 거의 같다는 것이다. 즉 SSD는 몇 세대 전 DRAM 한 채널과 맞먹는 대역폭을 가진, 그러면서 용량당 가격은 수십 분의 일인 저장 계층이 됐다.

논문이 제시하는 기가바이트당 비용 비교(2026년 8월 가격 스냅샷)가 설득력의 핵심이다.

| 저장 매체 | 용량당 가격 |
|---|---|
| VRAM (32GB GPU) | $62.47/GB |
| DDR5 RAM | $14.75/GB |
| PCIe 5.0 SSD | $0.34/GB |

이 표를 Kimi-K2.7-Code(500GB 필요)에 적용하면 VRAM으로 담으려면 약 $31,984, RAM으로 $7,552, SSD로는 $340다. 100배 가까운 비용 차이가 MoE 전문가 풀 같은 '차가운(cold) 대용량 데이터'를 SSD로 보낼 강한 동기가 된다.

물론 SSD에만 있으면 안 된다. 전문가 하나가 선택됐을 때 SSD → RAM → VRAM으로 전달되는 파이프라인의 병목을 풀어야 실제 토큰 속도가 나온다. SSD-LLaMA의 기여는 정확히 이 지점이다.

## 2. SSD-LLaMA의 세 가지 설계: expert-pack, 3계층 캐시, CPU-GPU 분배

### 2-1. GGUF 레이아웃 재배치 (expert-pack)

llama.cpp의 기존 GGUF 레이아웃에서는 한 전문가의 gate, up, down 세 텐서가 서로 다른 파일 영역에 흩어져 있다. 전문가 하나를 읽으려면 여러 번의 분산 파일 접근이 필요하고, 이는 순차 읽기가 생명인 SSD에서 치명적이다. SSD-LLaMA는 전문가 전체(gate-up-down 블록)를 하나의 연속된 '전문가 팩'으로 SSD에 다시 배치한다. 논문의 절제 실험(ablation)에서 팩 형태로 읽는 범위를 늘릴수록 SSD 트래픽이 유의미하게 줄어드는 것으로 확인됐다.

### 2-2. SSD-RAM-VRAM 3계층 전문가 캐시

같은 프롬프트 안에서 전문가 접근은 극단적으로 치우쳐 있다(skewed). 소수의 핫(hot) 전문가가 반복 선택되고 나머지는 가끔만 쓰인다. 기존의 '레이어 단위' 배치 정책은 이를 활용 못 한다 — 레이어 전체를 VRAM에 두면 콜드 전문가까지 자리를 차지하고, 내리면 핫 전문가를 반복해서 전송하게 된다.

SSD-LLaMA는 **전문가 하나를 캐시 단위**로 삼아 SSD→RAM→VRAM 3계층 캐시를 운영한다. 캐시 미스 시에도 손실 압축(lossless compression)으로 전송 바이트를 줄이고, SSD 읽기·H2D 전송·GPU 연산을 비동기로 겹친다. 측정 결과 RTX 5090 시스템에서 22GiB의 VRAM 전문가 캐시가 **80.1% 히트율**을 기록했다.

### 2-3. CPU-GPU 분배: 측정이 직관을 이겼다

흥미로운 부분은 하이브리드 실행 실험이다. RAM에 상주한 전문가를 CPU에서 실행하면 SSD→VRAM 전송을 피할 수 있지 않겠냐는 것이 KTransformers류 접근의 논리다. 그러나 논문의 측정에서는 어떤 CPU-GPU 분할도 all-GPU 경로를 이기지 못했다 — 전문가당 전송 지연이 실행 시간보다 길어 파이프라인 거품이 생기는 구조다(논문은 GLM-5.2에서 전송 지연의 약 5%만 숨길 수 있다고 측정했다). 최종 구성에서 CPU는 SSD 읽기 제출과 캐시 관리만 담당하고, 어텐션·밀집 연산·라우팅·선택된 전문가 연산은 전부 GPU에서 실행된다.

### 결과

llama.cpp, KTransformers, Colibri 세 베이스라인과의 비교에서 세 개 프론티어 MoE(DeepSeek-V4-Flash, Kimi-K2.7-Code, GLM-5.2)에 걸쳐:

- 프리필 토큰 레이트 **1.52배~4.19배** 개선
- 디코드 토큰 레이트 **2.10배~15.58배** 개선
- **1조 파라미터 초과 모델(Kimi-K2.7-Code, Q4 양자화)을 RTX 5090 한 장 + 32GB RAM으로 초당 1토큰 이상**의 디코드 속도로 실행

모든 선택된 전문가를 프루닝이나 대체 없이 실행한다(lossless)는 점도 품질 관점에서 중요하다. 스펙이 비슷한 기존 기법 중 일부는 전문가를 버리거나 근사하는 방식으로 속도를 냈기 때문이다.

## 3. BOOST: 데이터센터에서는 대역폭을 '합친다'

같은 달에 나온 BOOST(미국 대학 연구진과 NVIDIA Research의 공동 연구, arXiv:2609.13592)는 같은 문제를 데이터센터 관점에서 푼다. Grace Hopper 같은 시스템은 HBM이라는 1차 계층과 인터커넥트로 연결된 호스트 메모리라는 2차 계층을 가진다. 기존 서빙 시스템은 이를 위계적으로만 쓴다 — 데이터가 HBM에 들어가면 HBM만 쓰고, 안 들어가면 사용 전에 호스트 메모리에서 HBM으로 프리페치한다. 두 경우 모두 **호스트 메모리 대역폭은 제대로 쓰이지 않는다**. 프리페치는 용량은 늘리지만 HBM에 쓰는 데 대역폭을 빼앗겨 수요 로드가 느려진다.

BOOST의 핵심 통찰: 두 계층의 대역폭을 모두 쥐어짜려면 GPU 스레드블록의 각 '웨이브(wave)'가 두 계층에 **대역폭 비율에 비례해 동시에** 접근해야 한다. 기존의 대역폭 비례 배치 전략이 실패한 이유는 GPU 웨이브와 2MB라는 큰 GPU 페이지 크기를 인식하지 못했기 때문이다. BOOST는 커널 접근 패턴을 이용해 페이지 할당과 런타임 데이터 관리를 웨이브 인식형(wave-aware)으로 만든다. 정적 모델 가중치에는 모듈로 기반 페이지 배치로 접근 비율 분산을 없애고, 동적으로 할당되는 어텐션 KV 페이지 풀도 웨이브를 인식하게 만든다. **커널 수정 없이** vLLM에 통합됐다는 점이 실용성의 핵심이다.

Grace Hopper 시스템에서의 측정 결과:

- 동일 배치 크기에서 TPOT(출력 토큰당 시간) **4.3% 개선** — 같은 조건의 프리페칭은 오히려 6% 악화
- 고처리량 서빙에서 평균 **31% 처리량 증가**, 프리페칭 대비 15% 우위

## 4. 두 논문이 공통으로 말하는 것

다른 하드웨어, 다른 스케일이지만 두 연구의 결론은 하나로 수렴한다.

**메모리 계층은 위계가 아니라 풀이다.** "빠른 쪽에 넣고 넘치면 느린 쪽으로"라는 전통적 캐시 관점에서는 각 계층의 대역폭을 하나씩만 쓴다. SSD-LLaMA는 SSD를 전문가 캐시의 1급 시민으로, BOOST는 호스트 메모리를 HBM의 병행 파트너로 만들어, 계층 전체의 대역폭과 용량을 동시에 활용한다.

**접근 패턴을 아는 자가 이긴다.** SSD-LLaMA는 '전문가 단위'의 치우친 접근 분포를, BOOST는 'GPU 웨이브'라는 하드웨어 스케줄링 단위를 각각 잡아냈다. 둘 다 계층 관리의 정밀도를 파일이나 레이어 수준에서 훨씬 미세한 단위로 내린 것이 성능의 직접 원인이다.

**측정 없는 직관은 버려라.** SSD-LLaMA 팀은 CPU-GPU 하이브리드가 유리할 거라는 통념을 직접 측정으로 반례했다. BOOST 팀도 '프리페치면 충분하다'는 통념이 TPOT을 악화시킨다는 사실을 보여줬다. 메모리 계층 설계에서 정답은 워크로드와 하드웨어의 조합에 따라 달라지며, 본인 환경의 프로파일링을 대신할 수 없다.

## 5. 로컬에서 거대 MoE를 돌리기 전에 확인할 것

이 논문들을 읽고 일반 사용자가 바로 적용할 수 있는 체크리스트다.

**① SSD가 PCIe 5.0인지, 순차 읽기가 어느 정도인지.** 14.8 GB/s급 대역폭이 SSD-LLaMA 결과의 전제 조건이다. PCIe 4.0 SSD(약 7 GB/s)라면 기대 속도가 크게 내려간다. 전문가 팩은 순차 읽기로 소비되므로 랜덤 성능보다 순차 대역폭이 중요하다.

**② 디코드 속도의 이해.** 초당 1토큰은 채팅용으로는 아슬아슬하고, 배치 추론이나 문서 요약처럼 긴 출력을 비동기로 소비하는 작업에 적합한 속도다. 프론트엔드에 스트리밍을 붙이고 '백그라운드 작업'으로 취급하는 설계가 체감을 좌우한다.

**③ 총 소유 비용 계산은 직접 하라.** 논문의 $62.47/GB 같은 수치는 2026년 8자 스냅샷이고 구성(완성된 32GB GPU, 16GB DDR5 모듈, 1TB SSD 단위로 올림)에 따라 달라진다. 간단한 비용 비교 스크립트는 이렇다:

```python
# 목표: 500GB 웨이트를 저장하는 매체별 용량 비용 추정
targets = {
    "VRAM (32GB GPU 단위)": (62.47, 32),
    "DDR5 RAM (16GB 모듈)": (14.75, 16),
    "PCIe 5.0 SSD (1TB)":   (0.34, 1024),
}
need_gb = 500
for name, (per_gb, unit_gb) in targets.items():
    units = -(-need_gb // unit_gb)  # 올림
    print(f"{name}: ${units * unit_gb * per_gb:,.0f} ({int(units)}단위)")
```

**④ 밴더 의존 없는 경로.** SSD-LLaMA는 llama.cpp 기반이므로 특정 벤더 SDK에 묶이지 않는다. 공식 양자화 체크포인트(DeepSeek-V4-Flash는 FP8+MXFP4, Kimi-K2.7-Code와 GLM-5.2는 Q4_0)를 그대로 쓴다는 점도 사용자 입장에서 확인 포인트다.

## 결론

- SSD의 순차 대역폭(14.8 GB/s)이 구세대 DRAM 채널에 도달하면서, MoE의 '전체 전문가 풀 저장' 문제는 VRAM/RAM 예산 문제에서 SSD 파이프라인 설계 문제로 바뀌었다.
- SSD-LLaMA는 전문가 팩 재배치 + 전문가 단위 3계층 캐시 + 전부-GPU 실행으로 1조 파라미터 모델을 RTX 5090 한 장에서 1 tok/s 이상으로 돌렸다.
- BOOST는 웨이브 인식 페이지 배치로 HBM과 호스트 메모리의 대역폭을 동시에 쥐어짜 데이터센터 서빙 처리량을 평균 31% 올렸다 — 커널 수정 없이, vLLM에 통합해서.
- 두 연구 모두 '계층을 위계가 아닌 풀로 다루고, 접근 패턴을 미세 단위로 인식하는 것'을 핵심 원칙으로 보여준다.
- 당장 할 일: 로컬 MoE 실험을 계획 중이라면 PCIe 5.0 SSD 확보가 우선이고, 기대치는 '배치 작업 속도'로 잡아야 한다. 채팅 실시간성이 필요하면 활성 파라미터 수가 비슷한 dense 모델이나 더 작은 MoE가 여전히 현실적인 선택이다.

두 논문 모두 2026년 9월 arXiv 프리프린트라 아직 커뮤니티 검증 초기 단계임은 염두에 두자. 특히 15.58배 같은 상한 수치는 특정 모델·워크로드 조합에서 나온 값이므로 자기 워크로드로 재측정하는 것이 원칙이다.
