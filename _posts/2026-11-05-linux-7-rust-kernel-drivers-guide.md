# 리눅스 커널 7.0에서 Rust가 정식 언어가 되었다 — '실험 종료'가 실제로 의미하는 것과 드라이버 작성 실전 가이드

"리눅스 커널에 Rust가 들어간다"는 이야기는 이제 4년째 다니는 뉴스다. 2022년 12월 Linux 6.1에 초기 Rust 인프라가 머지된 이후, 매 릴리스마다 "이번엔 진짜 쓸 만해졌다"는 보도가 반복됐다. 그리고 2026년 4월, Linux 7.0은 이야기의 성격을 바꿨다. `CONFIG_RUST`에서 "실험(experimental)" 딱지가 떨어져 나갔고, Rust로 드라이버를 쓰는 것이 "용인되는 일"이 아니라 "지원되는 일"이 된 것이다.

문제는 이 선언이 실무자에게 무엇을 바꾸고 무엇을 안 바꾸는지 설명하는 글이 드물다는 점이다. 이 글은 그 간극을 정리한다. 어떤 서브시스템에서 Rust를 쓸 수 있고, 왜 아직도 대부분의 서브시스템에서는 못 쓰는지, 그리고 실제로 최소 드라이버를 짜려면 무엇이 필요한지 코드 레벨까지 내려가서 본다.

## 왜 커널에 Rust인가 — 근거부터

Rust 도입의 근거는 취향이 아니라 통계에서 나온다. Microsoft MSRC(보안 대응 센터)는 2019년 분석에서 자사 제품 CVE의 약 70%가 메모리 안전성 문제(use-after-free, 버퍼 오버플로 등)였다고 밝혔다. 이 수치는 이후 Google이 안드로이드와 Chromium에서 Rust 도입 확대와 함께 메모리 안전 취약점 비중을 낮췄다는 후속 분석들로도 뒷받침됐다.

C로 짜인 커널에서 이런 버그는 에러 처리 경로에서 `kfree`를 빠뜨리는 것만큼 사소한 실수로 태어난다. Rust의 소유권 모델은 이 클래스의 버그를 안전한 코드에서는 원천적으로 만들 수 없게 만든다. 물론 커널의 Rust가 전체 CVE의 70%를 없애준다는 뜻은 아니다. Rust는 오직 "Rust로 작성된 코드"에서만 효과가 있다. 커널의 대부분은 여전히 C이므로, 효과는 새로 들어오는 코드의 비율에 비례해 천천히 축적된다.

## 6.1에서 7.0까지 — 사실 확인된 타임라인

흐름을 정확히 잡기 위해 주요 이정표만 짚는다. 아래는 모두 공식 문서나 복수의 독립 매체로 교차 확인된 사실이다.

- **Linux 6.1 (2022년 12월)** — 초기 Rust 인프라 머지. 언어 기반 코드와 빌드 지원만 들어갔고, 실제 드라이버는 없었다.
- **Linux 6.8 (2024년 초)** — 블록 계층의 첫 Rust 드라이버인 rnull(null block 드라이버)이 머지되며 "실제 동작하는 Rust 드라이버가 메인라인에 존재하게 된" 시점이 됐다. 테스트용 가짜 장치지만, 블록 API의 Rust 추상화가 이걸 위해 다듬어졌다.
- **Linux 6.15 (2025년)** — NVIDIA가 Rust로 작성한 GPU 드라이버 **Nova**의 코어(nova-core)가 머지됐다. 튜링 이후 GPU를 대상으로 하며, kernel.org의 공식 문서 트리에도 등재됐다. 하드웨어 벤더가 자사 드라이버를 Rust로 메인라인에 올린 첫 사례라는 점에서 상징성이 크다.
- **Linux 6.19 → 7.1 (2026년)** — Rust 기반 그래픽(DRM) 추상화가 본격 확장됐고, DRM 서브시스템은 Rust 그래픽 드라이버 개발을 위한 별도 `drm-rust` 트리를 운영하기 시작했다. Nova도 릴리스마다 기능이 추가되는 중이다.
- **Linux 7.0 (2026년 4월)** — Rust 지원에서 "실험" 표기가 제거되고 표준 설정 옵션으로 편입됐다.

핵심은 이 타임라인이 "커뮤니티가 Rust를 좋아하게 됐다"가 아니라 "Rust 추상화가 필요한 서브시스템부터 하나씩 갖춰져 왔다"는 이야기라는 점이다.

## '정식 지원'이 바꾸는 것과 안 바꾸는 것

Linux 7.0의 변화를 흔히 오해하는 두 지점을 짚는다.

**바뀐 것**은 안정성 기대치다. 이전까지 Rust 추상화는 예고 없이 깨질 수 있었고, 드라이버 수용도 사례별 판단이었다. 이제 Rust 추상화에도 일반 커널 코드와 같은 유지 관리 의무가 따르고, Rust는 새 드라이버를 작성하는 인정된 방법 중 하나가 됐다.

**안 바뀐 것**이 더 중요하다. 첫째, 기존 C 코드를 Rust로 강제 이전하는 정책은 없다. 커널의 공식 입장은 공존(coexistence)이다. 새 코드는 Rust로, 기존 서브시스템은 C로 유지되며 강제 마이그레이션은 없다. 둘째, 어떤 C 서브시스템 관리자도 자기 서브시스템에 Rust를 받아들이거나 리뷰할 의무가 생긴 것은 아니다. 그래서 실무 제약은 그대로다. **"커널이 Rust를 지원한다"와 "내가 쓰려는 서브시스템에서 Rust를 쓸 수 있다"는 다른 문장**이다.

## 실제 제약: 추상화가 있는 곳에서만 쓸 수 있다

커널 Rust는 crates.io의 세계가 아니다. `std`도, async 런타임도, 서드파티 크레이트도 없다. 커널 자체의 라이브러리(`kernel` 크레이트)와 각 서브시스템의 C API를 감싼 안전 추상화만 사용할 수 있다. 드라이버를 Rust로 쓸 수 있는지는 전적으로 "내 서브시스템의 안전 추상화가 존재하는가"에 달려 있다.

현재 Rust 추상화가 갖춰진 대표적인 영역은 블록 계층(rnull이 증명), GPU/DRM(Nova가 증명), 일부 플랫폼 디바이스와 안드로이드 관련 코드 등이다. 반대로 추상화가 없는 서브시스템에서 Rust 드라이버를 쓰겠다면, 드라이버를 쓰기 전에 추상화 레이어부터 만들어야 한다. 커널 커뮤니티에서 실제 일감의 대부분이 드라이버 작성이 아니라 이 추상화 구축에 들어가는 이유다.

## 최소 드라이버 모양새 — 코드로 보기

그럼 실제로 커널 Rust 드라이버가 어떻게 생겼는지 보자. 최소 모듈의 뼈대는 다음과 같다.

```rust
use kernel::prelude::*;

module! {
    type: MinimalDriver,
    name: "minimal_driver",
    author: "Your Name",
    description: "A minimal example driver",
    license: "GPL",
}

struct MinimalDriver {
    buffer: KVec<u8>,
}

impl kernel::Module for MinimalDriver {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("minimal_driver: loading\n");

        // 커널에서는 할당이 실패할 수 있다: 조용한 OOM 중단이 없다.
        let mut buffer = KVec::new();
        buffer.push(0u8, GFP_KERNEL)?;

        Ok(MinimalDriver { buffer })
    }
}

impl Drop for MinimalDriver {
    fn drop(&mut self) {
        pr_info!("minimal_driver: unloading, {} bytes\n", self.buffer.len());
    }
}
```

이 짧은 코드에 커널 Rust의 논점이 압축돼 있다. 첫째, 할당이 실패 가능(fallible)하다. `push`가 GFP 플래그를 받고 `Result`를 반환한다. 사용자 공간 프로그램처럼 메모리 부족에 조용히 죽을 수 없는 커널의 조건이 타입 시스템에 드러난다. 둘째, `Drop` 트레잇이 언로드 경로의 정리를 자동화한다. C에서 에러 경로마다 `kfree`를 빠뜨려 use-after-free CVE를 만들어내던 바로 그 지점을 언어 차원에서 닫는 것이다. 대신 `Vec`이 아니라 `KVec`, `?` 연산자와 `kernel::Result`처럼 커널만의 규약을 배워야 한다.

빌드는 외부 모듈과 같은 방식으로 이뤄진다.

```make
# Kbuild
DRIVER := minimal_driver

$(DRIVER)-y := $(src)/main.o
obj-m := $(DRIVER).o
```

```bash
# 커널 트리가 요구하는 rustc 버전이 맞는지 확인한 뒤
make -C ~/linux-7.0 LLVM=1 M=$PWD modules
```

전제 조건이 하나 있다. 대상 커널 설정에서 `CONFIG_RUST=y`가 활성화돼 있어야 하며, 커널 빌드가 요구하는 특정 rustc 버전을 맞춰야 한다. 버전이 어긋나면 빌드 단계에서 명확히 거부된다.

## 다음 드라이버, Rust로 쓸 것인가

판단 기준은 단순하다. (1) 대상 서브시스템에 안전 추상화가 이미 존재하는가 — 특히 GPU/DRM과 블록 계층이라면 그렇다. (2) 새로 쓰는 코드인가 — 기존 C 드라이버를 고치는 것이라면 Rust 전환은 별도의 대규모 프로젝트다. (3) 장기 유지보수 주체가 있는가 — 커널에 올리는 이상 리뷰와 유지 의무가 따른다. 세 가지가 다 "예"라면 Rust는 이제 실험이 아니라 정당한 선택지다.

마지막으로 관찰 포인트 하나. DRM/GPU 서브시스템이 `drm-rust` 전용 트리를 따로 운영하며 Nova 같은 실제 하드웨어 드라이버를 앞세워 추상화를 확장하고 있다. 그래픽이 커널 Rust의 실험장 구실을 하고 있고, 여기서 검증된 패턴이 다른 서브시스템으로 번질 가능성이 크다. 커널 Rust의 다음 5년을 보고 싶다면 범용 논쟁이 아니라 이 트리의 커밋을 보면 된다.

## 핵심 요약

- Linux 7.0(2026년 4월)에서 Rust 지원의 "실험" 표기가 제거되며 정식 지원 언어로 편입됐다.
- 그러나 강제 마이그레이션은 없다. 정책은 공존: 새 코드는 Rust, 기존 서브시스템은 C.
- 실질 제약은 언어가 아니라 서브시스템 추상화다. 블록(rnull, 6.8), GPU/DRM(Nova, 6.15)이 앞서 있다.
- 메모리 안전성 근거는 MSRC의 "CVE 약 70%가 메모리 안전성 문제" 분석(2019) 등에 뿌리를 둔다.
- 첫 삽은 간단하다. 커널 문서의 Rust 샘플 드라이버를 빌드해 보고, 자신의 서브시스템에 추상화가 있는지 `rust.docs.kernel.org`에서 확인하는 것부터 시작하면 된다.
