# 알리바바 Zvec과 sqlite-vec — 온디바이스 RAG를 위한 임베디드 벡터 DB 실전 비교

RAG 파이프라인을 로컬에서 돌리는 개발자라면 한 번쯤 이런 고민을 한다. "Milvus나 Qdrant를 띄우기엔 너무 무겁고, Faiss만 쓰자니 스칼라 필터링·CRUD·크래시 복구를 전부 직접 만들어야 한다." 온디바이스 AI가 흥행하면서 이 간극을 노리는 임베디드 벡터 DB가 빠르게 성장하는 중이다. 그중 2026년 가장 주목받는 것이 알리바바가 Apache 2.0으로 공개한 **Zvec**이다.

이 글에서는 Zvec의 설계 철학과 실제 사용법을 정리하고, 같은 니치에서 널리 쓰이는 SQLite 확장인 **sqlite-vec**과 어떤 차이가 있는지 비교한다. 마지막에는 로컬 문서 검색 프로토타입을 몇 분 만에 띄우는 코드까지 담았다.

## Zvec은 무엇이 다른가 — "벡터 DB의 SQLite"를 문장 그대로 구현

Zvec은 알리바바 통의 연구조직(Tongyi Lab)에서 오래 다듬어온 고성능 벡터 엔진 **Proxima**를 기반으로 만든 인프로세스(in-process) 벡터 데이터베이스다. 공식 문서는 스스로를 "The SQLite of Vector Databases"라고 부르는데, 이 말에는 구체적인 약속이 담겨 있다.

- **서버가 없다.** 네트워크 통신도, 별도 프로세스도, 설정 파일도 없다. 라이브러리로 임베드되어 CLI 도구, 데스크톱 앱, 모바일 클라이언트 어디에든 들어간다.
- **데이터베이스 기능이 온전하다.** WAL(Write-Ahead Log) 기반 영속화, 크래시 자동 복구, 전체 CRUD를 갖춰서 Faiss처럼 "인덱스만" 주는 라이브러리와 다르게 주변 공학이 거의 필요 없다.
- **검색 기능이 벡터 네이티브다.** Dense/Sparse 임베딩 동시 지원, HNSW·IVF·DiskANN·RaBitQ 같은 다양한 인덱스와 양자화 옵션, 그리고 키워드 전문검색(FTS)까지 하나의 쿼리에서 융합하는 하이브리드 검색을 제공한다.

성능 측면에서 자체 발표 벤치마크에서는 VectorDBBench의 Cohere 10M 데이터셋 기준으로 동일 리콜 수준에서 **8,000 QPS 이상, 당시 리더보드 1위였던 ZillizCloud 대비 2배 이상**을 기록했다고 밝혔다. 이 수치는 어디까지나 Zvec 팀이 게시한 것이라 절대값보다는 "엣지 환경에서도 클라우드 서비스급 처리량을 낸다"는 방향성으로 이해하는 것이 안전하다.

2026년 11월 6일 현재 최신 버전은 **v0.8.1**이며, v0.8.0부터 Intel Mac·Windows ARM64 빌드가 추가되고 DiskANN이 Windows·Android·iOS로 확장되는 등 플랫폼 커버리지가 빠르게 넓어지고 있다. GitHub 스타는 공개 후 짧은 기간에 1.6만 개를 넘겼다.

## 실전: 3분 만에 로컬 시맨틱 검색 만들기

Python SDK는 `pip install zvec` 한 줄로 설치한다. 핵심 API는 세 단계뿐이다.

```python
import zvec

schema = zvec.CollectionSchema(
    name="notes",
    vectors=zvec.VectorSchema("embedding", zvec.DataType.VECTOR_FP32, 768),
)

collection = zvec.create_and_open(path="./notes_db", schema=schema)

collection.insert([
    zvec.Doc(id="doc_1", vectors={"embedding": emb_1}),
    zvec.Doc(id="doc_2", vectors={"embedding": emb_2}),
])

results = collection.query(
    queries=zvec.Query("embedding", vector=query_emb),
    topk=10,
)
```

여기서 눈여겨볼 점은 `VECTOR_FP32` 같은 데이터 타입 선언이다. 저장 시점에 FP16, INT4 같은 양자화를 명시적으로 고를 수 있어서, 메모리 예산이 빠듯한 모바일 환경에서 원본 정밀도와 인덱스 크기를 직접 트레이드오프할 수 있다. 전문검색 필드와 스칼라 필터를 같은 스키마에 정의하면 벡터 유사도 + 키워드 매치 + 태그 필터를 한 쿼리로 묶는 하이브리드 검색이 된다.

## 엣지 환경의 진짜 문제 — 메모리와 스레드 제어

임베디드 벡터 DB가 풀어야 할 가장 어려운 문제는 속도가 아니라 **예측 가능성**이다. HNSW 같은 그래프 인덱스는 빌드 중 원본 데이터의 수 배에 달하는 메모리를 순간적으로 쓸 수 있고, 모바일에서는 곧바로 OOM 킬이나 ANR으로 이어진다. Zvec이 아키텍처 레벨에서 제공한다는 세 겹의 방어가 인상적이다.

```python
collection = zvec.create_and_open(
    path="./notes_db",
    schema=schema,
    enable_mmap=True,        # OS가 필요한 페이지만 물리 메모리에 적재
)

# 전역 설정: 빌드/쿼리 스레드 상한으로 포그라운드 반응성 보호
# zvec.optimize_threads = 2
# zvec.query_threads = 2
# memory_limit_mb 로 하드 상한(실험적) 지정도 가능
```

1. **스트리밍 청크 쓰기** — 기본적으로 64MB 단위로 나눠 써서 전체 데이터를 메모리에 올리지 않는다.
2. **mmap 온디맨드 로딩** — `enable_mmap=True`면 데이터 총량이 RAM보다 커도 필요한 페이지만 적재된다.
3. **하드 메모리 한도(실험적)** — mmap 없이 쓸 때 프로세스 수준 메모리 풀에 `memory_limit_mb`로 상한을 건다.

또한 인덱스 빌드와 쿼리 각각에 스레드 수 상한(`optimize_threads`, `query_threads`)을 걸 수 있어서, 데스크톱 앱에서 벡터 인덱싱 때문에 UI가 버벅이는 문제를 프로세스 격리 없이 잡을 수 있다. 이런 세부 컨트롤은 클라우드용 서버 DB에서는 아예 신경 쓸 필요가 없던 것들이고, 오히려 엣지에서는 결정적인 차이를 만든다.

## sqlite-vec과 비교하면

같은 "라이브러리로 쓰는 벡터 검색" 니치의 대표 주자인 sqlite-vec은 SQLite 확장 형태로 동작한다. 방향성이 꽤 다르다.

| 구분 | Zvec | sqlite-vec |
|------|------|------------|
| 형태 | 독립 임베디드 벡터 DB | SQLite 확장(EXTENSION) |
| 저장/복구 | 자체 WAL, 크래시 자동 복구 | SQLite 엔진에 의존 |
| 인덱스 | HNSW, IVF, DiskANN, RaBitQ 등 + 양자화 | 브루트포스 중심, ANN(IVF, DiskANN)은 개발 중 |
| 검색 | 벡터+전문검색+필터 하이브리드 | 벡터 검색 + SQL 조인 |
| 스타(2026-11 기준) | 약 16,200 | 약 8,200 |
| 성숙도 | v0.8.1 | pre-v1 |

sqlite-vec의 최대 강점은 **SQL 생태계와의 결합**이다. 이미 SQLite로 데이터를 관리하고 있다면 조인, 트리거, 풍부한 드라이버를 그대로 재사용하면서 `vec0` 가상 테이블만 얹으면 된다. 데이터 규모가 수만~수십만 건 수준의 개인 도구라면 브루트포스 스캔도 충분히 빠르고, 복잡한 인덱스 튜닝이 없다는 것이 오히려 장점이 된다.

반대로 백만 건 이상의 벡터, 양자화로 메모리를 줄여야 하는 상황, 전문검색과의 하이브리드 랭킹이 필요하다면 Zvec 쪽이 설계 목적에 더 맞다. 다만 Zvec은 아직 1.0 이전이라는 점, **쓰기는 단일 프로세스만 가능하고 읽기만 멀티프로세스 동시 접근을 지원**한다는 점은 도입 전에 확인해야 할 제약이다.

## 주의사항

- **자체 벤치마크는 참고용으로.** QPS 수치는 하드웨어·리콜 설정에 따라 크게 달라지므로, 도입 전에 자기 워크로드로 반드시 재측정하자.
- **스키마 변경 비용.** 임베디드 DB는 서버형과 달리 마이그레이션 도구를 기대하기 어렵다. 임베딩 모델을 바꾸면 차원이 달라지므로 재색인 전략을 처음부터 설계해야 한다.
- **v0.x의 의미.** v0.8.x는 빠르게 개선 중이지만 API가 바뀔 수 있다. 프로덕션 도입 시 버전 고정과 업그레이드 테스트가 필요하다.

## 결론

- Zvec은 Faiss의 성능과 SQLite의 운영 단순함 사이를 노린, 온디바이스 RAG 특화 임베디드 벡터 DB다. Apache 2.0 라이선스로 자유롭게 쓸 수 있다.
- 엣지 환경의 핵심은 QPS보다 **메모리/스레드 예산의 예측 가능성**이며, Zvec은 청크 쓰기·mmap·하드 리밋·스레드 상한으로 이를 아키텍처에서 해결한다.
- sqlite-vec은 SQL 생태계 재사용이 무기다. 소규모 개인 도구라면 여전히 최선의 선택일 수 있다.
- 첫 단계 추천: `pip install zvec` 후 공식 원-미닛 예제를 돌려보고, 자신의 임베딩으로 10만 건 수준의 로컬 문서 검색 프로토타입을 만들어 보라. mmap 옵션 하나 켜고 끄는 것만으로 메모리 프로파일이 어떻게 달라지는지 직접 관찰하는 것이 가장 빠른 학습 경로다.
