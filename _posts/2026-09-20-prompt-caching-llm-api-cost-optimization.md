# LLM API 비용 90% 절감의 정석 — 프롬프트 캐싱 원리와 손익분기 계산법

에이전트 워크로드의 특징은 반복이다. 2만 토큰짜리 시스템 프롬프트와 도구 정의를 수십 번의 스텝에 걸쳐 다시 보내고, RAG 파이프라인은 매 쿼리마다 같은 문서 코퍼스를 첨부하며, 챗봇은 대화가 길어질 때마다 전체 히스토리를 재전송한다. 이 토큰들은 이미 한 번 계산해서 비용을 지불한 것들이지만, 캐싱 없이는 매번 처음부터 다시 계산되어 정가로 청구된다.

프롬프트 캐싱(prompt caching)은 이 낭비를 구조적으로 없앤다. 품질 저하 없이, 모델 출력이 바이트 단위까지 동일한 상태에서 입력 비용만 최대 90% 줄일 수 있다. 양자화나 증류 같은 품질 트레이드오프가 전혀 없다는 점이 이 기법의 결정적 장점이다. 이 글에서는 동작 원리, 2026년 현재 3개 주요 제공자의 공식 요금, 캐싱이 오히려 손해인 경우를 판별하는 손익분기 계산, 그리고 실제 프로덕션에서 적중률을 끌어올린 사례를 다룬다.

## 1. 캐시는 토큰이 아니라 KV 텐서를 저장한다

트랜스포머가 프롬프트를 처리하는 prefill 단계에서 모든 토큰은 어텐션 레이어마다 key(K)·value(V) 행렬로 투영되어 저장된다. 디코딩 시 새 토큰은 이 KV 캐시를 참조하므로 이전 토큰의 투영을 다시 계산하지 않는다. 제공자 수준의 프롬프트 캐싱은 이 메커니즘을 요청 경계 너머로 확장한 것이다.

핵심 조건은 **정확한 접두사(prefix) 일치**다. 캐시는 토큰 시퀀스 그 자체를 키로 삼기 때문에, 캐시 경계 앞쪽에서 단 한 글자가 바뀌면 그 지점 이후의 모든 블록이 미스 처리된다. OpenAI 공식 문서도 "전체 렌더링된 프리픽스가 일치해야 하며, 브레이크포인트 이전에 내용이나 관련 설정이 바뀌면 그 이후 프리픽스는 매칭될 수 없다"고 명시한다. 도구 정의, 개발자 메시지, 대화 히스토리까지 포함해 렌더링된 컨텍스트 전체가 캐시 키에 들어간다.

반드시 기억할 규칙 하나: **캐싱은 입력 토큰만 할인한다.** 어느 제공자도 출력 토큰 비용을 건드리지 않는다. 절감액 추정을 출력 지출까지 외삽하면 계산 자체가 틀린 것이다.

## 2. 2026년 3사 요금 구조 — 공식 문서 기준

세 제공자는 서로 다른 구조를 쓴다.

**Anthropic** — 명시적 브레이크포인트 방식. `cache_control` 마커로 캐시 지점을 직접 지정하거나, 요청 최상위에 한 번 넣는 자동 캐싱(대화가 길어지면 마지막 캐시 가능 블록까지 자동으로 캐시 지점이 전진)을 쓸 수 있다. TTL은 5분과 1시간 두 종류.

**OpenAI** — 자동 캐싱 방식. 지원 모델에서 기본 활성화되어 있고 별도 설정이 없다. 사용량 대시보드에서 캐시 적중률을 모니터링할 수 있고, 캐시 미스 진단 도구도 제공한다.

**Google Gemini** — 2.5 모델부터 설정 없이 적용되는 암시적(implicit) 캐싱과, 캐시 객체를 명시적으로 만드는 방식이 공존한다.

공식 문서에서 확인한 주요 수치는 다음과 같다 (1M 토큰당, USD).

| 제공자 | 기준 입력 | 캐시 읽기 | 캐시 쓰기 프리미엄 | 최소 접두사 |
|---|---|---|---|---|
| Anthropic (Opus 5) | $5.00 | $0.50 (0.1×) | 5분 1.25× / 1시간 2× | 1,024토큰 |
| Anthropic (Sonnet 5) | $2.00 | $0.20 (0.1×) | 5분 1.25× / 1시간 2× | 1,024토큰 |
| OpenAI (gpt-6-astra) | $10.00 | $1.00 (0.1×) | $12.50 (1.25×) | 1,024토큰 |
| Gemini 2.5 Flash (암시적) | $0.30 | $0.03 (75% 할인) | 없음 | 1,024토큰 |

읽기 할인은 Anthropic과 OpenAI 모두 기본 입력가의 0.1배, 즉 90% 할인이다. OpenAI 요금 페이지는 캐시 쓰기가 추가 요금이 아니라 "입력 토큰이 비캐시·캐시·캐시쓰기 요금 중 하나로 청구된다"는 점도 명시한다. Gemini의 암시적 캐싱은 Google 개발자 블로그 공식 발표 기준 75% 할인으로, 3사 중 할인율은 낮지만 쓰기 프리미엄이 없고 설정이 필요 없다.

## 3. 손익분기는 1.4회 — 직접 계산해보자

캐싱이 무조건 이득은 아니다. 쓰기에 1.25배를 내고 읽기에 0.1배만 내므로, 같은 접두사를 몇 번 재사용하느냐가 관건이다. Anthropic 5분 TTL 기준으로 손계산해보면:

- 재사용 없음: 1.0배 (그냥 정가 입력)
- 캐싱 후 1회 재사용: 1.25 + 0.1 = 1.35배 → **오히려 35% 손해**
- 캐싱 후 2회 재사용: 1.25 + 0.2 = 1.45배 vs 비캐시 3.0배 → 52% 절감
- 손익분기: 1.25 ÷ (1 − 0.1) ≈ **1.39회**

즉 같은 접두사를 대략 두 번 이상 재사용할 것 같으면 이미 이득이고, 1시간 TTL(쓰기 2배)은 약 2.2회부터 본전이다. 참고로 5분 TTL의 수명은 요청 시작 시점부터 측정되며 응답 생성 시간도 카운트에 포함된다. 응답이 4분 걸리면 후속 요청은 응답 완료 후 약 1분 안에 시작되어야 히트다. 재사용 간격이 5분을 넘는 저빈도 워크로드라면 1시간 TTL이나 OpenAI의 확장 보존 옵션을 검토해야 한다.

구체적 예시로 마무리하면: 2만 토큰 시스템 프롬프트를 Sonnet 5(입력 $2/MTok)로 에이전트 루프에서 10회 재전송하는 경우, 비용은 다음과 같다.

```text
캐싱 없음: 20,000 × $2/1M × 10        = $0.400
캐싱 사용: 20,000 × $2/1M × (1.25 + 0.2×9) = $0.086
→ 입력측 78% 절감 (출력 비용은 변동 없음)
```

## 4. 적중률을 좌우하는 것은 프롬프트 순서다

정확한 접두사 매칭이라는 제약 때문에, 캐싱의 성패는 **프롬프트를 어떤 순서로 쌓느냐**가 결정한다. 원칙은 변하지 않는 것부터 쌓는 것이다.

```text
[도구 정의] → [시스템 프롬프트] → [참고 문서] → [대화 히스토리] → [실사용자 쿼리]
   안정적 ←──────────────────────────────────────────────→ 매번 변경
```

Anthropic은 `tools`, `system`, `messages` 순서로 프롬프트 전체를 캐시 프리픽스로 참조하므로, 중간에 동적 데이터가 끼어들면 그 뒤 전체가 무효화된다. 가장 흔한 실수는 시스템 프롬프트 안에 현재 시각이나 세션별 상태를 박아 넣는 것이다. 매 요청 달라지는 값은 프롬프트 맨 끝의 사용자 메시지로 옮겨야 한다.

Anthropic 자동 캐싱의 사용법은 단순하다:

```python
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},  # 최상위 한 줄이면 자동 캐싱
    system="반복되는 긴 시스템 프롬프트...",
    messages=[
        {"role": "user", "content": "매번 달라지는 실제 질문"},
    ],
)
print(response.usage)  # cache_read_input_tokens 로 적중 확인
```

미세 제어가 필요하면 특정 콘텐츠 블록에 `cache_control`을 직접 붙이는 명시적 브레이크포인트 방식으로 전환하면 된다. OpenAI는 자동 캐싱이라 코드 변경이 아예 없고, 사용량 대시보드의 Prompt Caching 섹션에서 적중률을 확인한 뒤 프롬프트 구조만 다듬으면 된다.

## 5. 실제 사례: 7%에서 84%로

보안 스캐너로 유명한 ProjectDiscovery가 공식 블로그에서 공개한 사례가 이 모든 이론을 현실에서 확인시켜준다. 이 팀은 초기에 캐시 적중률이 7%에 불과했다. 원인은 시스템 프롬프트 안에 매 스텝마다 갱신되는 작업 메모리(working memory)를 넣어뒀기 때문이다. 접두사가 매번 바뀌니 캐시가 계속 무효화됐던 것이다.

해결책은 앞 절의 원칙 그대로였다. 동적 작업 메모리를 시스템 프롬프트에서 빼내어 프롬프트 맨 끝의 사용자 메시지로 이동시켰더니 적중률이 7%에서 84%로 올라갔고, 전체 LLM 비용이 59% 절감됐으며 98억 개 토큰을 캐시에서 서빙했다. 모델을 바꾸거나 증류한 것이 아니라 프롬프트의 구조만 바꿔서다.

이 사례에서 뽑을 수 있는 실무 교훈:

- 적중률이 안 나오면 제공자를 탓하기 전에 프롬프트 어느 위치에 동적 데이터가 있는지 먼저 점검한다. 안정적인 프롬프트에서 적중률 60% 미만은 구조적 문제의 신호다.
- `usage` 필드의 캐시 읽기 토큰 수를 모니터링 대상에 넣는다. 이 숫자가 캐싱 투자의 실제 수익률이다.
- 세션 유지가 캐시 히트를 보장하지는 않는다. OpenAI 문서도 명시적으로 경고하는 부분이다.

## 결론

- 프롬프트 캐싱은 KV 텐서를 재사용해 입력 토큰을 최대 90% 할인받는 기법으로, 품질 트레이드오프가 전혀 없다.
- Anthropic·OpenAI는 읽기 0.1배, 쓰기 1.25배(Anthropic 1시간 TTL은 2배), Gemini 암시적 캐싱은 75% 할인에 쓰기 프리미엄 없음 — 모두 공식 문서 확인 수치다.
- 손익분기는 약 1.4회(1시간 TTL은 2.2회) 재사용. 단 한 번만 재사용할 접두사를 캐시하면 오히려 35% 손해다.
- 적중률의 열쇠는 순서다: 도구 정의 → 시스템 프롬프트 → 문서 → 히스토리 → 동적 쿼리. 시스템 프롬프트에 타임스탬프를 넣는 순간 캐시는 죽는다.
- 오늘 바로 할 수 있는 첫 단계: API 응답의 `usage`에서 캐시 읽기 토큰 비율을 측정하는 로그 한 줄을 추가하는 것이다. 측정 없이는 어디가 새는지 알 수 없다.
