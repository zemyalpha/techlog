# Claude가 53만 줄 런타임을 11일 만에 Rust로 다시 쓴 방법 — Bun 재작성 사례 분석

2026년 7월, JavaScript 생태계에서 가장 논쟁적인 프로젝트 하나가 완성됐다. Bun의 창시자 Jarred Sumner가 약 50개의 Claude Code 워크플로우를 돌려서 535,496줄짜리 Zig 코드베이스를 Rust로 통째로 포팅한 것이다. 걸린 시간은 11일, API 비용은 약 165,000달러. 사람이 했다면 작은 팀이 1년이 걸릴 작업이었다고 Sumner는 설명했다.

이 이야기가 단순한 "AI 대박" 호재성 뉴스가 아닌 이유는, 과정이 공개돼 있고 그 과정 자체가 반복 가능한 엔지니어링 패턴의 모음이기 때문이다. 이 글에서는 Bun 팀이 세운 전략, 실패했던 시도, 그리고 결과 수치를 정리하고, 여러분의 프로젝트에 적용할 수 있는 부분을 뽑아본다.

## 배경: 왜 Zig를 버렸나

Bun은 2021년, esbuild의 Go 트랜스파일러를 Zig로 줄단위 포팅하면서 시작됐다. 런타임, 패키지 매니저, 번들러, 테스트 러너를 전부 포함하는 야심찬 프로젝트였고, 공식 블로그 기준 현재 월 2,200만 회 이상 다운로드된다. Claude Code와 OpenCode가 런타임으로 Bun을 쓰고 있고, Vercel·Railway·DigitalOcean도 퍼스트파티 지원을 제공한다. 2025년 12월에는 Anthropic이 Bun을 인수했다.

문제는 안정성이었다. Bun 팀이 공개한 v1.3.14 버그 목록을 보면 use-after-free, double-free, 메모리 누수가 반복적으로 등장한다. `node:zlib`의 `.reset()` 호출 중 크래시, `UDPSocket.send()`에서 `valueOf()` 콜백이 ArrayBuffer를 detach하면서 생기는 use-after-free, `tlsSocket.setSession()` 호출마다 약 6.5KB씩 누수되는 SSL_SESSION 누수 같은 것들이다.

원인은 언어 그 자체보다는 아키텍처에 있었다. JavaScript는 가비지 컬렉션(GC) 언어이고, JavaScriptCore 엔진은 GC되는 값과 수동 관리되는 값의 수명 규칙이 엄격하다. Zig에는 생성자/소멸자가 없어서 모든 정리 코드를 각 호출 지점에서 `defer`로 명시해야 하는데, GC 메모리와 수동 메모리가 뒤섞인 코드베이스에서 "이 포인터는 언제 해제되는가"를 매번 사람이 추적하는 구조였다. Sumner의 표현을 빌리면, 이런 버그 클래스는 안전한 Rust에서는 컴파일 에러다.

흥미로운 반론도 있다. Zig 창시자 Andrew Kelley는 "My Thoughts on the Bun Rust Rewrite"라는 글에서 이전부터 Bun 코드베이스의 프로그래밍 관행에 문제가 있었다고 비판하며, AI가 생성한 코드를 "검토되지 않은 슬롭(slop)"이라 불렀다. 언어 탓이 아니라 관리 탓이라는 것이다. 이 논쟁은 결론이 나지 않았지만, "재작성이 필요했던 원인"을 이해하는 데 두 시각 모두 참고할 만하다.

## 전략: "멋진 Rust"가 아니라 "기계적 포트"

재작성 실패의 고전적인 이유는 중간에 동작하지 않는 기간이 생기기 때문이다. Bun 팀이 내린 결정 두 개는 이 리스크를 직접 노린 것이다.

**첫째, 점진적 포트가 아니라 한 번에 전부.** 점진적 재작성은 결국 삭제되기를 바라는 임시 코드를 만들어낸다. Sumner가 예전에 esbuild를 Go에서 Zig로 포팅해본 경험에 따르면, 전부 한 번에 하는 편이 낫다고 한다.

**둘째, "트랜스파일된 것처럼 보이는" Rust를 쓰기.** 관용적(idiomatic) Rust로 바꾸면 원본과의 대응 관계가 깨져서 검증이 불가능해진다. 대신 원본 Zig 구조를 그대로 따라가는 기계적 번역을 하고, `unsafe` 줄이기와 관용화는 v1.4 출시 이후로 미뤘다.

이 전략이 성립하는 근거가 하나 있다. **Bun의 테스트 스위트가 TypeScript로 작성돼 있어서 런타임 구현 언어와 무관했다.** 100만 개 이상의 어설션을 가진 언어 독립적 테스트 스위트가 있어야만 "코드는 전부 바꿨지만 행동은 동일하다"를 증명할 수 있다. LLM 대규모 재작성을 생각하고 있다면, 가장 먼저 확인할 것이 이 것이다.

## 실행: 11일 동안 무슨 일이 벌어졌나

과정은 공식 블로그에 커밋 단위로 공개돼 있다. 단계별로 정리하면:

**1. 준비 (약 3시간 + 워크플로우).** 코드를 쓰기 전에 Claude와 Zig→Rust 패턴 매핑을 논의해서 `PORTING.md`로 직렬화했다. 이어서 "모든 구조체 필드의 수명을 분석하는 워크플로우"를 돌려 각 필드에 적합한 Rust 라이프타임을 제안·검토하게 하고, 그 결과를 `LIFETIMES.tsv` 파일로 만들었다. 이후 두 문서를 대상으로 다시 적대적 리뷰를 돌려 모순을 제거했다. 즉, 포팅 규칙 자체를 먼저 산출물로 만든 것이다.

**2. 시험 실행.** 1,448개의 `.zig` 파일 전체를 돌리기 전에 3개 파일만 포팅했다. 파일당 1개 구현자 + 2개 적대적 리뷰어 + 1개 수정자 구성으로 검증하고, 통과하면 전체에 적용했다.

**3. 대량 포팅.** 피크 시점에 Claude는 분당 약 1,300줄을 썼다. 최대 1시간에 695개 커밋이 쌓였고, 11일 동안 총 6,502개 커밋이 발생했다. 병렬화는 4개 git 워크트리 × 16루프 = 64개 Claude 인스턴스로 구성했다.

**4. 컴파일 에러를 작업 큐로.** 크레이트 분리 과정에서 약 16,000개의 컴파일 에러가 나왔다. 워크플로우는 `cargo check` 출력을 파일로 저장해 크레이트별로 그룹화하고, 64개 Claude에게 분배해서 고치게 했다. 1명에게는 절망적인 숫자지만 64개 병렬 에이전트에게는 그저 대기열일 뿐이다.

**5. 테스트로 수렴.** 로컬에서는 실패하는 테스트 파일마다 스택트레이스를 저장하고 구현자 1 + 리뷰어 2 + 수정자 1 루프를 돌렸다. CI에서는 처음 972개 테스트 파일이 실패했지만 이틀 만에 23개로 줄었고, 그 이틀 뒤 6개 플랫폼 전부가 녹색이 됐다. 공식 발표 기준 100만 어설션 이상의 테스트를 통과했다.

거짓 출발(false start) 기록도 솔직하게 공개돼 있다. 초기에는 병렬 Claude들이 서로의 작업을 침범하며 `git stash`, `git reset --hard`를 실행하는 사고가 났고, "컴파일되게 하라"는 지시를 에러 나는 함수를 스텁으로 때우는 것으로 해석하기도 했다. 이때 추가한 규칙이 백미다: "워크어라운드를 정당하려면 문단 길이의 주석이 필요한가? 그렇다면 코드가 틀린 것이다. 코드를 고쳐라."

## 핵심 장치: 적대적 리뷰

이 재작성에서 가장 가져올 만한 패턴은 **적대적 리뷰(adversarial review)**다. 구조는 단순하다.

- 코드를 쓴 Claude(구현자)와 코드를 검토하는 Claude(리뷰어)는 **서로 다른 컨텍스트 윈도우**에서 동작한다.
- 리뷰어에게는 diff만 주고, 구현자의 추론 과정은 주지 않는다. 그리고 "이 코드가 틀렸다고 가정하고 틀린 이유를 찾아라"는 지시를 받는다.
- 구현자:리뷰어 = 1:2 이상. 구현자는 리뷰하지 않고, 리뷰어는 구현하지 않는다.

사람 리뷰와 같은 원리다. 코드를 쓴 사람은 그 코드가 머지되기를 원하고, 이는 출시 전에 병합하려는 편향으로 이어진다. LLM도 마찬가지라는 것이 Bun 팀의 관찰이다. 실제로 이 장치는 컴파일은 되고 그럴듯해 보이지만 libuv의 비동기 `uv_close` 처리에서 Box가 조기 해제되는 use-after-free + double-free 버그를 머지 전에 잡아냈다.

"100만 줄이 추가된 PR은 어떻게 리뷰하는가"라는 질문에 대한 Bun의 대답은 이렇게 정리된다. 언어 독립적인 대규모 테스트 스위트 + 적대적 리뷰 + 문제가 생기면 코드가 아니라 **코드를 생성하는 프로세스를 고치는 것**.

## 결과: 수치로 보는 Rust 재작성

성능 수치는 Bun 팀이 공식 블로그에서 EC2(Xeon Platinum 8488C, Linux x64)에서 직접 측정해 공개한 값이다.

**속도는 2~5% 향상.** `Bun.serve` 헬로월드 HTTP 처리량은 초당 169.6k → 177.7k 요청(+4.8%), `next build`는 13.62초 → 13.03초(+4.5%). Rust와 C/C++ 간 크로스 언어 링크 타임 최적화로 언어 경계를 넘는 인라이닝이 가능해진 것이 한 요인이다.

**메모리 누수는 사라졌다.** 60모듈 프로젝트를 한 프로세스에서 2,000번 번들링하면 v1.3.14(Zig)는 6,745MB까지 치솟던 메모리가 v1.4.0(Rust)에서는 609MB에서 수렴한다. `Drop` 트레이트가 에러 경로의 파일 경로 누수 등을 자동으로 정리한 효과다.

**바이너리는 약 20% 작아졌다.** Windows 94MB → 76MB, Linux 88MB → 70MB. 링커의 Identical Code Folding과 ICU 데이터 최적화가 함께 적용된 결과다.

그리고 가장 중요한 지표: **아무도 알아채지 못했다.** Claude Code v2.1.181(6월 17일 출시)부터 이미 Rust 포트 위에서 돌고 있는데, 리눅스에서 시작이 10% 빨라진 것 말고는 체감 차이가 없었다는 것. 기계적 포트 전략이 의도한 대로 "지루한(boring)" 출시가 이뤄진 셈이다. The Decoder 보도에 따르면 이 재작성으로 128개의 버그가 수정됐다.

## 여러분의 프로젝트에 가져갈 것

Bun의 사례를 일반화하면 이렇다.

1. **재작성 전에 언어 독립적 테스트부터.** 구현 언어와 무관하게 돌아가는 테스트 스위트가 없으면 LLM 재작성은 검증 불가능하다.
2. **매핑 규칙을 산출물로 만들어라.** `PORTING.md`와 `LIFETIMES.tsv`처럼, 원본 언어 패턴 → 대상 언어 패턴의 대응 규칙을 문서로 고정하고 그 문서를 먼저 검토하라.
3. **기계적 포트를 목표로 해라.** 동시에 관용화까지 시도하면 원본과의 대응 관계가 깨져 리뷰가 불가능해진다.
4. **구현자와 리뷰어를 분리하고, 리뷰어에게 diff만 줘라.** 리뷰어의 임무는 "왜 틀렸는지 찾기"다.
5. **컴파일 에러와 실패 테스트는 폐기물이 아니라 작업 큐다.** 에러 목록을 파일로 저장하고 에이전트들에게 분배하라.
6. **버그가 반복되면 프롬프트/프로세스를 고쳐라.** 개별 코드를 손으로 고치는 대신 그 코드를 만든 규칙을 수정하면 같은 부류의 오류가 한 번에 사라진다.

물론 조건도 따른다. 이 재작성은 원본과 결과물을 동시에 완벽히 이해하는 엔지니어가 상시 감시했고, 16.5만 달러 수준의 API 비용과 64개 병렬 인스턴스가 필요했다. 그리고 Zig 창시자의 비판이 보여주듯 "AI가 빠르게 썼다"와 "코드가 좋다"는 별개 문제다. 하지만 "언어 교체 재작성은 절대 하지 말라"는 격언이 조건부로 깨진 첫 대규모 사례라는 점은 부정하기 어렵다.

한 명의 엔지니어가 1년 칠 일을 11일에 했다. 다음에 똑같은 일이 벌어질 프로젝트의 조건은 위 6가지다.
