# SQLite는 진실을 맡고 ZVec은 속도를 맡는다 — 알리바이 임베디드 벡터 DB 실전 해부

로컬 LLM이 보편화되면서 개발자들이 마주하는 의외의 병목은 모델이 아니라 검색이다. 노트북에서 도는 RAG 어시스턴트, CLI 코드 검색 도구, 에이전트의 장기기억 저장소 — 이런 애플리케이션은 모두 벡터 유사도 검색을 필요로 하지만, Milvus나 Qdrant 같은 서버형 벡터 DB를 옆에 붙이는 순간 "로컬 퍼스트"라는 전제가 무너진다. 반대로 SQLite에 벡터를 BLOB으로 넣고 전수 스캔하는 방식은 간단하지만 데이터가 커지면 쿼리 하나에 수백 밀리초가 걸린다.

알리바이가 이 틈을 노리고 있다. 2026년 1월 20일 공식 블로그에서 "The SQLite of Vector Databases"를 표방하며 오픈소스로 공개한 **ZVec**(`alibaba/zvec`)은 프로세스 안에 내장되는(embedded) 벡터 데이터베이스다. 이 글에서는 ZVec의 설계, 실제 벤치마크 수치, 그리고 실제 프로젝트가 선택한 아키텍처 패턴을 정리한다.

## ZVec은 무엇이 다른가

ZVec은 알리바이 통의연구소(Tongyi Lab)에서 개발한 고성능 벡터 엔진 **Proxima**를 기반으로 만들어졌으며, 알리바이 그룹 내부 프로덕션 워크로드에서 검증된 뒤 Apache 2.0 라이선스로 공개되었다. 핵심 설계 원칙은 세 가지다.

- **임베디드**: 네트워크도, 별도 서비스 프로세스도, 설정 파일도 없다. 라이브러리로 링크되어 앱 안에서 동작한다. Python 3.10–3.14, Node.js, Go, Rust, Dart/Flutter 공식 SDK가 제공되며 Linux(glibc/musl), macOS, Windows, Android, iOS에서 돈다.
- **벡터 네이티브**: 희소·조밀 벡터, 멀티 벡터 쿼리, 인덱스 타입(HNSW, DiskANN, IVF-RaBitQ 등)과 양자화(INT8, PQ) 옵션을 처음부터 갖췄다. 키워드 전문검색(FTS)과 스칼라 필터를 섞은 하이브리드 검색도 한 쿼리로 처리한다.
- **프로덕션 준비 완료**: WAL(Write-Ahead Log)로 크래시 시 데이터를 보존하고, 멀티 프로세스 읽기 + 단일 프로세스 쓰기 동시성을 지원한다. 휴대폰·CLI·차량용처럼 무인 운영(zero-ops) 환경을 명시적으로 타깃으로 삼는다.

공식 소개 글은 기존 선택지의 공백을 이렇게 짚는다. Faiss는 인덱스 라이브러리일 뿐 스칼라 저장·하이브리드 쿼리·크래시 복구 같은 DB 기본기가 없고, DuckDB-VSS는 인덱스 선택지와 양자화, 리소스 제어가 제한적이며, Milvus 같은 서비스형은 별도 프로세스와 네트워크 통신 때문에 CLI 도구나 모바일 앱에 심을 수 없다는 것. 즉 ZVec의 경쟁 상대는 서버형 벡터 DB가 아니라 "임베디드 벡터 검색"이라는 카테고리 자체의 부재다.

## 3분 퀵스타트

설치와 검색까지의 거리가 짧다는 것이 ZVec의 첫 번째 판매점이다. README의 원-미닛 예제는 다음과 같다.

```python
import zvec

schema = zvec.CollectionSchema(
    name="example",
    vectors=zvec.VectorSchema("embedding", zvec.DataType.VECTOR_FP32, 4),
)

collection = zvec.create_and_open(path="./zvec_example", schema=schema)

collection.insert([
    zvec.Doc(id="doc_1", vectors={"embedding": [0.1, 0.2, 0.3, 0.4]}),
    zvec.Doc(id="doc_2", vectors={"embedding": [0.2, 0.3, 0.4, 0.1]}),
])

results = collection.query(
    zvec.Query(field_name="embedding", vector=[0.4, 0.3, 0.3, 0.1]),
    topk=10,
)
```

`create_and_open` → `insert` → `query` 세 단계로 끝난다. 서버 실행, 포트 관리, 컨테이너가 전혀 없다. 문서에는 시맨틱 검색 외에 콜렉션 단위 스트리밍 순회를 위한 DocIterator, MCP 서버, 에이전트 스킬 패키지도 문서화되어 있어, LLM 에이전트의 로컬 검색 백엔드로 쓰는 시나리오를 공식적으로 밀고 있음을 알 수 있다.

## 성능: 공식 수치와 독립 검증

### 공식 벤치마크

ZVec 팀은 Zilliz(Milvus 개발사)가 만든 오픈소스 벤치마크 프레임워크 **VectorDBBench**로 측정했고, 방법론과 재현 명령어를 공개했다. Cohere 768차원 1,000만 건 데이터셋, 16 vCPU / 64GB RAM 인스턴스, INT8 양자화 + HNSW(m=50, ef-search=118) 구성에서 **8,000 QPS 이상**을 기록했으며, 공식 블로그는 "동일 리콜 수준에서 기존 리더보드 1위였던 ZillizCloud의 2배 이상"이라고 주장한다. 경쟁사 프레임워크로 경쟁사 클라우드와 비교했다는 점은 흥미롭지만, 어디까지나 **자체 측정 주장**이므로 실제 도입 전 자체 워크로드로 재검증하는 것이 원칙이다. 재현 명령어가 문서에 그대로 공개되어 있어 검증이 불가능한 벤치마크는 아니다.

### 독립 베이크오프: SQLite 전수 스캔 vs ZVec

더 흥미로운 데이터는 서드파티다. 로컬 퍼스트 검색 도구를 개발하는 Context Harness 팀이 2026년 6월 실제 프로젝트 코퍼스(문서 202개, 청크 4,917개, 384차원)로 직접 비교한 결과다.

| 항목 | SQLite 전수 스캔 | ZVec HNSW |
|------|------|------|
| 중위 쿼리 시간 | 112.56 ms | 0.77 ms |
| 평균 쿼리 시간 | 128.13 ms | 0.80 ms |
| 인덱스 빌드 시간 | — | 250.61 ms |
| 인덱스 크기 | — | 약 13.9 MB |

약 **146배** 빠르고, 상위 k 후보의 SQLite 정확 스캔 대비 겹침(overlap)은 0.988이었다. 다만 저자가 스스로 명시한 중요한 한계가 있다 — 이 테스트는 의미 임베딩이 아닌 결정론적(deterministic) 벡터를 사용했으므로 인덱스·검색 성능은 증명하지만 엔드투엔드 시맨틱 품질은 증명하지 않는다는 것. 좋은 벤치마크 리포트의 표본이라 할 수 있다.

## 아키텍처 교훈: 진실은 SQLite, 속도는 ZVec

Context Harness 팀이 벤치마크 후 내린 결정이 이 글의 핵심 메시지다. ZVec이 빠르다고 해서 기존 저장소를 갈아엎은 것이 아니라, **역할 분리**를 선택했다.

```
app-data/
  ctx.sqlite        # 정규(canonical) 저장소: 문서, 청크, FTS5, 임베딩 메타데이터
  vector-index/     # 파생(derived) ZVec 사이드카: 재구축 가능한 벡터 인덱스
```

SQLite는 진실의 원천(source of truth)으로 남고, ZVec 인덱스는 언제든 삭제하고 다시 빌드할 수 있는 파생물이 된다. 사이드카가 없거나 손상되면 SQLite 전수 스캔으로 폴백한다. 설정은 이렇게 단순하다.

```toml
[vector_index]
backend = "auto"   # ZVec 사용 가능하면 쓰고, 아니면 SQLite 폴백
path = "auto"
metric = "cosine"
index = "hnsw"
fallback = "sqlite"
```

이 패턴이 주는 교훈은 두 가지다. 첫째, 임베디드 벡터 DB의 가치는 "기존 DB 대체"가 아니라 **기존 DB 옆의 가속기**로서의 가치다. 둘째, 파생 인덱스는 정규 저장소가 있기 때문에 오히려 안전하게 실험할 수 있다 — 인덱스가 깨져도 데이터는 그대로다.

## 모바일·CLI를 위한 리소스 거버넌스

HNSW 같은 그래프 인덱스는 빌드·쿼리 중 원본 데이터의 수 배에 달하는 메모리를 순간적으로 쓸 수 있다. 데스크톱에서는 곤란하고, 모바일에서는 OOM 킬러가 앱을 종료시킨다. ZVec이 이 문제를 구조적으로 다루는 방식이 인상적이다.

- **청크 단위 스트리밍 쓰기**: 기본적으로 64MB 청크로 나눠 써서 전체 데이터를 메모리에 올리지 않는다.
- **mmap 온디멘드 로딩**: `enable_mmap=true` 시 벡터·인덱스 데이터를 OS가 필요할 때만 물리 메모리에 페이징한다. 총 데이터가 RAM보다 커도 OOM 없이 동작한다.
- **하드 메모리 상한(실험적)**: mmap 미사용 시 격리된 프로세스 레벨 메모리 풀을 두고 `memory_limit_mb`로 예산을 명시적으로 제한한다.
- **스레드 제어**: 인덱스 빌드 스레드 수(`optimize_threads`)와 쿼리 스레드 수(`query_threads`)를 각각 상한 설정할 수 있어, GUI 앱에서 백그라운드 인덱싱이 포어그라운드 반응성을 굶기는 일을 막는다.

"인덱스가 빠르다"와 "제한된 환경에서 예측 가능하게 동작한다"는 다른 문제인데, 후자를 API 레벨에서 다루고 있다는 점이 실제 프로덕션 경험이 배어 있는 설계다.

## v0.7.0에서 달라진 것

2026년 8월 24일 릴리스된 v0.7.0은 ZVec의 지향점을 잘 보여준다.

- **DiskANN 프로덕션화**: Linux ARM64 / macOS ARM64 지원과 `io_uring` 비동기 I/O 백엔드가 추가됐고, 최적 I/O 옵션으로 자동 폴백된다. 디스크 기반 인덱스로 수십억 규모 벡터를 RAM 제약 하에 다루는 그림이다.
- **IVF-RaBitQ 인덱스 + PQ-INT8 양자화**: RaBitQ는 런타임에 AVX2/AVX512를 자동 선택해 같은 바이너리가 CPU별 최적 경로를 탄다.
- **zvec-grep(`zg`)**: ripgrep + BM25 + 벡터 검색을 하나의 CLI로 합친 로컬 워크스페이스 검색 도구. 사람보다 AI 에이전트를 위해 설계했다고 명시한다.
- **ReMe 통합**: 에이전트 메모리 관리 킷인 ReMe의 파일 저장소 백엔드로 채택됐다. 에이전트 장기기억 시장을 노린 움직임이 명확하다.
- N-gram 토크나이저 추가(구문·코드·짧은 텍스트 검색 강화), musl/Alpine 지원, macOS arm64 C API 라이브러리 크기 37→22MB(-40%) 등 배포 경험도 다듬었다.

참고로 이 글을 쓰는 시점(2026년 10월) 기준 최신 릴리스는 10월 16일자 v0.8.0-alpha로, Windows ARM64(MSVC) 빌드 지원과 turbo quantizer 등이 추가되며 개발 속도가 유지되고 있다.

## 그래서 언제 뭘 써야 하나

- **수천만 건 이상, 다중 클라이언트, 운영팀이 있는 환경** → 여전히 Milvus, Qdrant 같은 서버형이 맞다. ZVec은 단일 프로세스 쓰기 모델이다.
- **인덱스 연구·커스텀 파이프라인** → Faiss가 여전히 가장 유연하다. 단, 저장·복구·하이브리드 쿼리는 직접 만들어야 한다.
- **노트북·모바일·CLI의 로컬 RAG, 에이전트 메모리** → ZVec이 현재 가장 완성도 높은 선택지다. sqlite-vec도 훌륭한 가벼운 옵션이지만 인덱스 다양성과 디스크 스케일, 리소스 거버넌스에서 ZVec이 앞선다. GitHub 토론에서도 사용자들이 이 차이를 놓고 비교하고 있다.

## 결론

- ZVec은 알리바이가 내부 프로덕션에서 검증한 Proxima 엔진을 Apache 2.0으로 연 임베디드 벡터 DB로, "벡터 DB의 SQLite" 포지션을 정면으로 겨냥한다.
- 공식 VectorDBBench에서 Cohere 10M 기준 8,000 QPS 이상(ZillizCloud의 2배 이상)을 주장하고, 서드파티 실측에서는 SQLite 전수 스캔 대비 약 146배(112.56ms → 0.77ms)가 확인됐다.
- 실전에서 검증된 패턴은 대체가 아니라 분리다 — SQLite는 정규 저장소로, ZVec은 재구축 가능한 벡터 사이드카로.
- 64MB 청크 쓰기, mmap, 하드 메모리 상한, 스레드 상한 같은 리소스 거버넌스가 모바일·CLI 환경에서의 차별점이다.
- v0.7.0의 DiskANN/io_uring, zvec-grep, ReMe 통합은 로컬 에이전트 인프라로의 확장을 명확히 하고 있다.

당장 시도해볼 첫 단계는 간단하다. 기존 프로젝트에서 벡터를 BLOB으로 저장해 전수 스캔하는 부분만 찾아, `pip install zvec` 후 사이드카 패턴으로 교체하고 폴백 경로를 남겨두는 것. 기존 저장소를 건드리지 않으므로 리스크는 거의 없고, 코퍼스가 커질수록 차이는 극적으로 벌어진다.
