# 음성 에이전트 데모와 프로덕션을 가르는 세 숫자 — 680ms, 분당 0.07달러, 62% 컨테인먼트

2024년까지 "음성 AI 에이전트"의 대부분은 접착제로 붙인 데모였다. 전화번호 하나, Whisper 트랜스크립트, LLM 호출 한 번, TTS 왕복. 발화가 끝나고 2초 뒤에야 "잠시만요"가 나오는 그런 데모. 그런데 2026년에는 이것이 하나의 카테고리가 됐다. 관문이 된 변화는 모델 성능이 아니라 세 가지 인프라 요소다. 오케스트레이션 프레임워크가 턴 테이킹·인터럽션·전화 연동을 기본 프리미티브로 제공하기 시작했고, TTS의 첫 오디오까지 걸리는 시간이 100ms 이하로 내려왔으며, 실제 트래픽을 처리하는 배포가 쌓이면서 "어떤 숫자를 맞춰야 하는지"가 명확해졌다.

이 글은 어떤 플랫폼이 좋냐는 질문 대신, 프로덕션 트래픽에서 실측된 세 숫자 — 응답 레이턴시, 분당 비용, 컨테인먼트율 — 를 기준으로 설계 결정을 정리한다.

## 세 숫자의 기준선

DestiLabs가 2026년 6월 공개한 벤치마크는 10개 이상의 라이브 음성 에이전트 배포(헬스케어, 핀테크, 부동산, 이커머스 등)에서 실제 통화 트래픽의 텔레메트리를 뽑은 것이다. 벤더 데모가 아니라 운영 중인 시스템의 숫자라는 점이 중요하다. 핵심 수치는 다음과 같다.

- **응답 레이턴시**: 발화 종료 → 에이전트 응답 시작 기준으로 중앙값(p50) 680ms, p95 1,180ms
- **분당 비용**: 통화 연결 1분당 전체 비용(전화망 + STT + LLM 토큰 + TTS + 오케스트레이션 합산) 0.07~0.21달러
- **컨테인먼트율**: 사람에게 넘기지 않고 에이전트가 끝까지 해결한 통화 비율, 범위가 잘 정의된 에이전트 기준 62~88%

여기서 주목할 부분은 분포다. p50이 600ms 미만인 프로젝트는 30%, 600~800ms가 40%, 800~1,000ms가 20%, 1,000ms 초과가 10%였다. 즉 시장의 70%가 "자연스럽다"고 느껴지는 구간(800ms 이하)에 들어가 있고, 1초를 넘기면 발화자가 에이전트의 말을 끊고 말하기 시작한다.

또 하나의 통찰은 p50보다 p95가 체감을 결정한다는 것이다. p50이 650ms여도 p95가 2,500ms면, 20턴에 한 번 꼴로 어색한 정적이 찾아오고 이것이 "느리다"는 인상을 만든다. 운영 관점에서 실질적인 기준선은 p50 680ms보다 **p95 1,400ms 이하**이며, 튜닝 노력의 대부분은 중앙값을 깎는 게 아니라 꼬리를 당기는 데 들어간다. 꼬리의 주범은 세 가지로 측정됐다. 턴 중간의 동기적 도구/RAG 호출(느린 CRM·캘린더 조회), 콜드 스타트 LLM 요청, 긴 응답 전문을 받아야 시작하는 TTS. 그리고 가장 효과가 컸던 수정은 응답 전문을 기다리지 않고 **첫 문장부터 스트리밍 재생**하는 것이었다.

## 캐스케이드 vs 스피치 투 스피치: 하나의 결정이 전부를 바꾼다

2026년에 음성 팀이 내리는 가장 큰 설계 결정은 캐스케이드 파이프라인(STT → LLM → TTS, 세 모델의 체인)이냐, 스피치 투 스피치(오디오 입력 → 오디오 출력, 단일 모델)냈다. 둘은 미묘하게 다른 게 아니라 레이턴시 프로파일, 디버깅 가능성, 비용 곡선, 실패 모드가 전부 다르다.

**캐스케이드가 프로덕션의 기본값이다.** 각 컴포넌트가 독립적으로 관측 가능하고, 전사 transcript가 남아 컴플라이언스 감사에 쓸 수 있으며, 공급자를 단계별로 교체할 수 있다. 비용도 예측 가능하다(약 0.0095~0.17달러/분, 모델 조합에 따라). 대신 레이턴시 예산이 촉박하다. 각 단계의 전형적인 범위는 다음과 같다.

| 단계 | 전형적 레이턴시 |
|------|----------------|
| STT (스트리밍) | 100~500ms |
| LLM (첫 토큰까지) | 350~1,000ms |
| TTS (첫 오디오까지) | 75~200ms |
| 벤더 간 네트워크 | 50~200ms |

단순 합산은 575~1,900ms지만, 실제로는 각 단계를 스트리밍으로 겹치게 만들어 대부분을 병렬화한다. 다만 설정이 엉성하면 그대로 800ms~2초의 종단 레이턴시로 나타난다.

**스피치 투 스피치는 빠르지만 좁다.** OpenAI Realtime API(2025년 8월 GA, gpt-realtime 계열), Gemini Live 같은 모델은 텍스트 계층을 건너뛰고 턴 테이킹, 운율, 도구 호출을 한 번의 왕복으로 처리한다. 운율과 감정 전달이 눈에 띄게 낫다. 그 대가는 세 가지다. 첫째, 비용이 공급자별로 최대 182배까지 벌어진다(Gemini 2.0 Flash Live는 분당 약 0.00165달러, GPT-4o Realtime은 분당 약 0.30달러로 보고됨). 둘째, 정규 transcript가 없어 감사 로그가 얇다. 셋째, 공급자 선택지가 소수로 좁아지고 모델 교체가 설정 변경이 아니라 재작성이다. 실무 권장안은 하이브리드다. 잡담·인사 표면은 스피치 투 스피치로, transcript가 중요한 도구 호출 경로는 캐스케이드로.

## 여섯 개 컴포넌트와 그중 진짜 걸림돌

플랫폼의 접착제를 걷어내면 프로덕션 음성 에이전트는 어디서나 같은 여섯 조각이다. 전송 계층(WebRTC/SIP), VAD와 턴 검출, STT, LLM, TTS, 오케스트레이션. 그중에서 실제 장애를 만드는 지점은 두 곳이다.

**턴 검출은 VAD만으로는 안 된다.** 에너지 기반 VAD(예: Silero)는 사용자가 말하고 있는지를 판단하고, 시맨틱 턴 검출 모델은 사용자가 말을 *끝냈는지*를 판단한다. 규칙 기반 VAD만 쓰는 시스템은 상대가 생각하는 중간에 끼어들어 최악의 실패를 만든다. LiveKit의 적응형 턴 검출, Pipecat의 Smart Turn 같은 별도 모델 계층이 이 실패를 한 자릿수 줄인다.

**TTS는 첫 오디오까지의 시간(TTFA)이 전부다.** TTS는 파이프라인의 마지막 단계라 여기서 낭비된 밀리초는 그대로 체감 지연이 된다. 2026년 기준 Cartesia Sonic 계열은 서드파티 벤치마크에서 첫 오디오까지 약 40ms로 측정됐다(모델 세대에 따라 ~90ms까지 분포하며, 2026년 10월 현재 최신 모델 ID는 sonic-3.6, 한국어 포함 44개 언어 지원). ElevenLabs Flash v2.5는 약 75ms, Deepgram Aura-2는 서브 200ms(튜닝 시 ~90ms)로 알려져 있다. 그리고 청크 단위 스트리밍과 재생 중 취소(mid-stream cancellation) 지원은 선택이 아니라 필수다. 이게 없으면 사용자가 끼어들 때(barge-in) 에이전트가 말을 멈추지 못한다.

다음은 LiveKit Agents(Python 1.5.x)에서 이 여섯 조각을 조립하는 실제 모양이다. STT는 Deepgram Nova-3로 임시 결과(interim results)를 켜고, LLM 토큰을 TTS 청커로 바로 흘려보내며, 에너지 VAD 위에 시맨틱 턴 검출을 얹는 구성이다.

```python
# pip install "livekit-agents[deepgram,openai,cartesia,silero,turn-detector]~=1.5"
from livekit.agents import Agent, AgentSession, JobContext, WorkerOptions, cli, function_tool
from livekit.plugins import deepgram, openai, cartesia, silero
from livekit.plugins.turn_detector.multilingual import MultilingualModel

class SupportAgent(Agent):
    def __init__(self) -> None:
        super().__init__(
            instructions=(
                "당신은 Acme 상담 에이전트입니다. 짧게 답하세요. "
                "상대가 말하는 중에는 끼어들지 마세요. 주문 조회는 "
                "반드시 도구를 사용하고 주문번호를 지어내지 마세요."
            ),
        )

    @function_tool
    async def lookup_order(self, order_id: str) -> dict:
        """주문번호(6~12자리)로 주문을 조회한다."""
        return await orders_client.fetch(order_id)

async def entrypoint(ctx: JobContext):
    session = AgentSession(
        stt=deepgram.STT(model="nova-3", interim_results=True),
        llm=openai.LLM(model="gpt-4.1-mini"),
        tts=cartesia.TTS(model="sonic-3.6", voice="a0e99841-..."),  # 한국어 지원, 저지연
        vad=silero.VAD.load(),                      # 에너지 기반: 말하고 있는가
        turn_detection=MultilingualModel(),          # 시맨틱: 말을 끝냈는가
    )
    await session.start(agent=SupportAgent(), room=ctx.room)
    await session.generate_reply(instructions="인사하고 무엇을 도와줄지 물으세요.")

if __name__ == "__main__":
    cli.run_app(WorkerOptions(entrypoint_fnc=entrypoint))
```

세 가지를 눈여겨보자. TTS가 OpenAI가 아니라 저지연 벤더라는 점, 턴 검출이 VAD와 별개 모델이라는 점, 도구 호출이 장식된 평범한 Python 함수라는 점이다. 같은 에이전트를 SIP 트렁크에 붙이는 것은 코드 변경이 아니라 디스패치 룰 설정이다.

## 비용의 실체: 표면 가격은 진짜 가격이 아니다

관리형 플랫폼의 표면 가격은 대략 Vapi가 분당 0.05달러 스타터(프로덕션에서 0.20~0.33달러), Retell이 분당 0.07달러 스타터(프로덕션에서 0.13~0.31달러)로 알려져 있다. 그러나 앞서 본 실측치가 말해주듯 진짜 비용은 전화망, STT, LLM 토큰, TTS가 얹혀서 정해진다. 스타터 가격에 LLM 토큰 비용이 포함되지 않는 구조라면, 도구를 많이 쓰는 긴 통화일수록 표면 가격과 실제 청구액 사이가 벌어진다. 분당 비용 산정은 반드시 "연결된 분당 총비용" 기준으로 직접 계산해야 한다.

참고로 업계 보고서들은 음성 AI 1통화 비용을 약 0.40달러, 인간 상담원 1통화를 7~12달러로 추정한다. 이 격차가 조직을 움직이는 동력이지만, 컨테인먼트율이 낮으면 사람 중계가 섞이면서 단가가 급격히 악화된다. 범위가 잘 정의된(예: 주문 조회, 예약 변경) 에이전트가 62~88% 컨테인먼트를 내는 반면, 범위가 넓은 에이전트는 이 숫자를 못 채운다. 음성 에이전트의 성공은 모델이 아니라 **태스크 범위 설계**가 결정한다는 뜻이다.

## 결론: 데모에서 프로덕션으로 넘어가는 체크리스트

- **p50이 아니라 p95를 SLA로 삼아라.** 기준선은 p95 1,400ms 이하. 꼬리의 주범은 동기 도구 호출, 콜드 스타트, 전문 대기 TTS다.
- **첫 문장 스트리밍 재생이 최고 레버리지다.** 레이턴시 튜닝에서 가장 효과가 컸던 단일 수정으로 측정됐다.
- **감사가 필요하면 캐스케이드, 운율이 제품이면 스피치 투 스피치.** 둘 다 필요하면 하이브리드로 표면과 도구 경로를 분리하라.
- **VAD 위에 시맨틱 턴 검출을 얹어라.** 끼어듦 실패는 음성 에이전트가 받는 최악의 항의다.
- **비용은 연결 분당 총비용으로 계산하라.** 스타터 가격과 프로덕션 청구액 사이에는 3~6배 차이가 난다.
- **범위를 좁혀라.** 컨테인먼트 62~88%는 "잘 정의된 태스크"의 성과다. 범용 상담은 아직 아니다.

당장 시도해볼 첫 단계는 간단하다. 기존 에이전트가 있다면 발화 종료부터 응답 시작까지의 시간을 턴 단위로 로깅하는 것 하나로 시작하라. 그 로그의 p50과 p95를 보면 다음에 무엇을 고쳐야 하는지가 숫자로 말해준다.
